# 架构层关注点

任务粒度在「系统/模块/服务级」时——你需要画框图、定模块边界、考虑跨进程通信——文档应**额外**关注以下章节。

## 边界与目标

系统**做什么** + 系统**不做什么**。"不做什么"和"做什么"同等重要——它定义了边界，避免后续 scope 漂移。

成功判据：怎么算「系统能用」？

## 组件清单

| 组件 | 职责 | 关键依赖 |
|---|---|---|

每行不超过一句话讲清职责。详细的接口形状放在「数据流」或单独 ADR 里。

## 数据流

核心场景下数据怎么流：请求 → 谁处理 → 写到哪 → 回什么。
**至少画 2 条**：一条成功路径 + 一条主要失败路径。

## 失败模式

列**真实可能发生**的失败：触发条件 → 系统行为 → 用户感知。

| 失败 | 触发 | 系统行为 | 用户感知 |
|---|---|---|---|

## 依赖治理（按需）

外部依赖（上游服务、数据库、消息队列、第三方 API）：

- 同步 / 异步
- 必需 / 可选（可选 = 挂了系统能降级运行）
- 超时、重试、熔断、缓存策略

---

写架构层文档时，**减少**对接口实现细节的描述——那是开发层的事。架构文档要让 reviewer 能从俯瞰视角判断系统设计是否合理。
