# 复杂 Bug 修复

⚠️ 大多数 bug 修复用 `superpowers:debugging` skill，**不需要**设计文档。
仅在以下情况下才用本 skill 写文档：

- 跨多模块的 bug（修一处会影响多处）
- 需要分阶段修复 + 阶段性回滚
- 影响用户数据 / 需要事故复盘性质的记录
- 修复方案本身有多种选择，需要 decision 决策（这种情况优先用 `intent/decision.md`）

主线节：

## Bug 现象

可复现步骤、影响范围、首次出现时间（如已知）。给具体的：错误信息、报错日志、被影响的用户/数据量。

## 根因分析

为什么发生？根因 + 触发条件。可以引用 debugging skill 的产出。

> 写「为什么这次没拦住」——是测试漏了？是边界条件没考虑？是依赖变更？根因不只是「代码哪里错了」，是「我们的流程哪里漏了」。

## 修复方案

做什么改动？涉及哪些文件/模块？分几步？

## 回归预防

新增什么测试 / 监控 / 校验防止复发？这一节的存在意义是把"我们今后不会再犯这种错"写实。
