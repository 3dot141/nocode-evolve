# 重构 / 改造老代码

改老代码、不改外部行为时，文档主线节：

## 现状（Pain Point）

现在长什么样？哪里痛？**用具体的代码引用、bug 数据、性能指标说话**，不要泛泛说「难维护」「技术债」。

> 反例：「auth 模块代码混乱，难维护」  
> 正例：「`auth/session.go` 1200 行，混合密码校验/token 签发/session 持久化/IP 限流四种职责。3 个月内因冲突 PR 重做 5 次。新人 onboard 平均 2 天才能改通一个 auth 小需求。」

## 目标状态

重构后长什么样？同样要具体——文件结构、模块边界、接口签名。

## 不属于本次重构

明确**这次不做什么**，否则 scope creep 会让重构永远做不完。

- 例：「不动 SSO 集成那部分」「不改前端调用方」

## 迁移路径

分步走，每步完成后系统**仍可用**。

| 步骤 | 动作 | 完成判据 |
|---|---|---|

> 避免"大爆炸"重构——每步要能独立 ship、独立回滚。

## 回滚预案（按需）

任意一步失败怎么回滚？需要 feature flag / 双跑 / 数据回填吗？跨多文件 / 涉及生产数据时**强烈建议写**。
