# PRD: Ledgerly 团队协作

> 状态: 草稿

> 日期: 260624
> 调研: docs/nocode/prds/3dot141/research-report-team-collab.md

## 问题

Ledgerly 现在是纯单人记账。**主因**：付费用户里 38% 在工单里问"能不能和合伙人共享账本" [SOURCE: research-report 市场信号]，他们目前靠共享账号密码绕过，导致操作无法追溯、改错无法归因。**辅因**：共享账号让多端登录频繁触发风控登出（本 PRD 不直接解决，但协作功能落地后会缓解）。

## 用户故事

- **US-1** 作为 账本所有者, 我想要 邀请成员加入我的账本, 以便 合伙人能一起记账不用共享密码 `[CONFIRMED]`
- **US-2** 作为 被邀请成员, 我想要 通过邮件链接接受邀请, 以便 不用注册流程就能加入 `[CONFIRMED]`
- **US-3** 作为 账本所有者, 我想要 给成员设只读/可编辑权限, 以便 会计只看不改、合伙人能改 `[CONFIRMED]`
- **US-4** 作为 任意成员, 我想要 看到每笔记录是谁改的, 以便 出错能追溯到人 `[ASSUMED]` — 审计需求是从工单痛点推断，待用户核验是否本期做

## 业务领域与使用路径

### 成员管理
> 关注点: 账本成员的邀请、加入、移除全生命周期

**使用路径**
- 成员.P1: 所有者邀请成员 [所有者] [CONFIRMED]
  来源: US-1
  账本设置页 → 输入成员邮箱 → 生成邀请链接 → 系统发邮件 → 显示"邀请已发出"
  | 异常: 邮箱已是成员、邀请数超上限
  | 边界: 邮件发出后进入「邀请接受」领域
- 成员.P2: 成员接受邀请 [被邀请人] [CONFIRMED]
  来源: US-2
  点邮件链接 → 校验 token → 已登录直接加入 / 未登录先登录再加入 → 进入账本
  | 异常: token 过期、token 已使用、token 被撤销
  | 边界: 加入成功后该用户出现在成员列表
- 成员.P3: 所有者移除成员 [所有者] [ASSUMED]
  来源: US-1
  成员列表 → 选成员 → 移除 → 确认 → 该成员失去访问
  | 异常: 不能移除所有者自己
  | 边界: 移除后该成员的历史记录保留，仅失去访问权

### 权限控制
> 关注点: 成员的角色与可执行操作的映射

**使用路径**
- 权限.P1: 所有者设置成员角色 [所有者] [CONFIRMED]
  来源: US-3
  成员列表 → 选成员 → 选角色(viewer/editor) → 保存 → 即时生效
  | 异常: 不能修改所有者自己的角色
  | 边界: 角色变更后该成员下次操作按新权限校验
- 权限.P2: viewer 尝试编辑被拦截 [viewer] [CONFIRMED]
  来源: US-3
  viewer 打开记录 → 编辑按钮置灰 / 调用写接口返回 403
  | 异常: —
  | 边界: 前端拦截 + 后端兜底双层

### 操作审计
> 关注点: 记录的变更归因

**使用路径**
- 审计.P1: 成员查看记录修改人 [任意成员] [ASSUMED]
  来源: US-4
  打开某笔记录 → 看到"最后修改人 + 时间"
  | 异常: 协作功能上线前的旧记录无修改人，显示"系统迁移"
  | 边界: 仅展示，不做完整操作日志

## 跨领域路径

- 跨域.1: 从邀请到协作记账全流程 [所有者 + 被邀请人] [CONFIRMED]
  成员.P1 → 成员.P2 → 权限.P1 → 审计.P1
  | 异常: 任一环节失败（邀请发不出 / token 失效 / 权限设置失败）的回退与提示

## 系统路径

- 系统.1: 邀请 token 过期清理 [CONFIRMED]
  定时任务（每日）→ 扫描超 7 天未接受的邀请 → 标记过期 → 释放该邀请占用的成员名额
  | 异常: 清理任务失败需告警，不可静默
- 系统.2: 邀请邮件发送回调 [ASSUMED]
  邮件服务商 webhook → 校验签名 → 更新邀请状态（已送达 / 退信）→ 退信则提示所有者重发
  | 异常: 签名校验失败、重复回调、回调丢失

## 约束

- 约束.1: 一个账本的成员数不超过设定上限（防滥用） [CONFIRMED]
- 约束.2: viewer 角色在任何路径下都不能产生写操作 [CONFIRMED]
- 约束.3: 邀请 token 一次性使用，接受后立即失效 [CONFIRMED]
- 约束.4: 移除成员不删除其历史记录（归因不可丢失） [CONFIRMED]

## 投入上限

2 周封顶。理由：协作是留存功能不是增长功能，超过 2 周的投入应先验证付费转化再追加。超时则砍 US-3（权限分级）先上邀请+共享。

## 方向草图

账本增加 members 关联表；邀请走"生成带 token 的邀请链接 + 邮件发送"；权限用 owner/editor/viewer 三档枚举。草图级，详细设计交 dev-design。

## 竞品分析

[来自 research-report Feature Matrix] 竞品 YNAB 无协作、Monarch 有共享但无权限分级、QuickBooks 有完整权限但太重。差异化空间：轻量三档权限。

## 成功指标

- Primary: 协作功能上线 30 天内，≥15% 付费账本至少邀请 1 名成员 `[CONFIRMED]`
- Secondary: 共享账号导致的风控登出工单下降 ≥50% `[ASSUMED]`
- Guardrail: 单人用户的记账核心流程 P95 延迟不恶化（协作查询不拖慢主路径）`[CONFIRMED]`

（注: PRD 不分配 SC 编号，SC-N 由 Define 阶段统一分配并绑定路径）

## 风险与不确定性

- 实时协同编辑（多人同时改一笔）→ 技术不确定性高，本期用乐观锁"后写覆盖 + 提示"即可 [推断]
- 邀请 token 的安全性（过期/撤销/重放）→ 需 dev-design 的 threat model 覆盖 [代码探索]

## 不做的事

- 不做实时协同光标/在线状态（over-engineering，小团队用不上）
- 不做超过 3 档的权限体系（企业级 RBAC 不在本期）
- 不做跨账本的组织/团队层级（一个账本一组成员，不做 workspace 概念）
