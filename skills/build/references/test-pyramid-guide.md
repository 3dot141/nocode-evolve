# 测试金字塔指南

5b Test First 选层级时用。**默认 unit**，按需向上升级。

## 测试金字塔

```
        /\        e2e        少 —— 慢、脆、贵，只覆盖关键用户旅程
       /  \
      /----\    integration  中 —— 跨模块/外部依赖的真实协作
     /      \
    /--------\     unit       多 —— 快、稳、便宜，覆盖绝大多数逻辑
```

底层多、顶层少。倒金字塔（一堆 e2e、几乎没有 unit）= 慢且脆，是反模式。

## Test Sizes（按隔离程度，而非按概念命名）

更可操作的分类是看测试**碰什么**：

| Size | 碰什么 | 速度 | 何时用 |
|---|---|---|---|
| **Small** | 单进程内存，无 I/O、无网络、无真实文件系统、无 sleep | 毫秒级 | 默认。纯函数、单组件、单类逻辑 |
| **Medium** | 本机多进程 / localhost / 真实文件系统 / 测试 DB | 百毫秒~秒 | 模块间集成、本地 DB 查询、HTTP handler |
| **Large** | 跨机器 / 外部服务 / 完整环境 | 秒~分钟 | 端到端旅程、跨服务契约 |

优先写 Small；只有验收标准本质上要求真实依赖才升 Medium；只有要验证完整用户旅程才升 Large。

## 何时选哪层

- **默认 unit / Small**：业务逻辑、纯函数、数据转换、单个组件渲染与交互、边界条件。
- **升 integration / Medium** —— 当且仅当涉及外部依赖：
  - 数据库读写、ORM 查询行为
  - HTTP/RPC handler 的请求-响应链路
  - 文件系统、消息队列、缓存等进程外资源
  - 多个内部模块的真实协作（mock 掉就测不到的契约）
- **升 e2e / Large** —— 当且仅当要验证完整旅程：
  - 关键用户路径（登录→下单→支付）端到端可用
  - 跨服务的契约在真实环境成立

## 升级判断口诀

> 能用 mock 隔离掉外部依赖、仍能验证这个验收标准吗？
> - 能 → 留在 unit。
> - 不能（被测的恰恰是与外部依赖的真实交互）→ 升 integration。
> - 要验证的是"多个真实组件串起来对用户可用"→ 升 e2e。

## 反模式

- 用 e2e 测本可以 unit 覆盖的逻辑分支（慢、定位难）
- unit 测里 mock 到测的全是 mock 自己的行为（没测到真东西）
- 一个测试同时跨多层、断言一大堆（失败时不知道哪坏了）
- 测试依赖真实网络/外部服务却没标成 Large（CI 里随机挂）
