# Source-Driven 实现指南

核心原则：**实现里的每个事实性判断都要有来源。** 记忆不是来源。

## 来源标注规范

实现/注释/PR 描述里涉及"X 的行为/签名/约定是 Y"时，标出依据：

| 标注 | 含义 | 用法 |
|---|---|---|
| `[Read path:line]` | 直接从代码读到的事实 | 引用项目内或依赖内的具体行 |
| `[Doc URL]` | 官方文档/规范确认 | 框架 API、协议、标准库行为 |
| `[推断]` | 没有直接依据的推断 | 必须显式标，不许伪装成事实 |
| `UNVERIFIED` | 应该核对但当前无法核对 | 离线/文档不可达时的诚实标记 |

**底线**：宁可标 `[推断]` 也不要把猜测写成肯定句。一个被标出的推断可以被复核，一个伪装成事实的推断会变成 bug。

## 何时必须查来源

- 调用框架/库的 API（参数顺序、返回类型、副作用、异常）
- 依赖某个配置项的默认值
- 假设某个文件/模块的导出接口
- 跨模块的调用约定、数据契约
- 任何"我记得是这样"的时刻——记忆触发查证

## 官方文档查询方式

按优先级：

1. **专用文档工具**：`Skill(find-docs)` / `Skill(deepwiki)` 查库与框架文档与 API。
2. **Web 搜索**：`mcp__exa__web_search_exa` / `mcp__exa__get_code_context_exa`（全局规则里 Exa 为首选）。
3. **官方仓库**：用 `Skill(deepwiki)` 直接查目标 GitHub repo 的文档。

查到后把链接落进标注 `[Doc URL]`，便于后续复核。

## 离线降级规则

当文档不可达（无网络 / 工具不可用 / 内网环境）：

1. 标 `UNVERIFIED`，说明"文档不可达，离线降级"。
2. **退回本地源码**：读已安装包的源码确认真实行为——
   - JS/TS：`node_modules/<pkg>/`（看 `.d.ts` 类型定义和实现）
   - Python：已安装包目录 / `site-packages/`
   - 其他：项目锁定的依赖版本源码
3. 本地源码读到的结论用 `[Read node_modules/...:line]` 标注，比纯推断可信。
4. 实在无从核对的判断，保留 `UNVERIFIED` 标记到 commit/PR，提醒后续复核——**不要悄悄当成已确认**。

## 反模式

- "这个 API 应该是这样用的"——没标来源，没查证
- 把官方文档的旧版本行为当成当前版本（注意版本号）
- 离线时直接凭记忆写，不退回本地源码
- 复制网上代码片段不核对它针对的版本
