# workflow — 每阶段怎么做

## 阶段串行，gate 不进则停

每个阶段结尾都有一个明确的通过条件。没满足就不许进入下一阶段——跳过 gate 的代价是整段返工。

---

## S0 · 工具选择

**做什么**：列出当前可用的设计类 skill 与「手工」选项，问用户用哪个产出方向。

**怎么问**：给 2–3 个具体选项，写清各自擅长什么、这次场景适合谁。不要替用户决定，也不要因为"看起来都差不多"跳过。

**产出**：`tool-choice.md`

```markdown
# 工具选择
- 选定：<skill 名 / 手工>
- 理由：<一句话>
- 备用：<如果选定的产出不满足要求，换谁>
```

**gate**：用户明确选了一个。

---

## S1 · 现状

**有代码时读什么**（按顺序，读到能回答"这个页面现在长什么样、有什么问题"为止）：

1. 路由 / 页面结构——有哪些页面、怎么进出
2. 组件目录——已有哪些可复用块
3. 样式入口——现有的颜色、字号、间距在哪定义
4. 现有截图——如果项目里已有截图目录，直接看

**产出：问题清单**。每条必须带证据：

```markdown
| 位置 | 现象 | 证据 | 影响 |
|---|---|---|---|
| 首页搜索框 | 全页唯一重灰块，与纸底冲突 | r5motion-01-home.png 顶部 | 破坏"无容器"主张 |
| 快记 footer | 「取消」是绿字白胶囊 | CaptureSheet.swift:74 | 绿色语义被用在次要操作 |
```

**gate**：问题清单里每一条都有可验证的证据位置（截图或 `文件:行号`）。没有证据的条目删掉或补证据。

**卡点**：容易写成"整体不够精致"这类无法验证的判断。判据是——别人拿着你的清单，能不能只凭证据复现这个问题。

---

## S2 · 方向

**做什么**：用 S0 选定的工具，产出三个真实初稿。

**"真实初稿"的标准**：
- 是能打开的 HTML 或可看的图，不是文字描述
- 三个方向在**结构或视觉语言**上有实质差异，不是换色
- 每个方向至少覆盖主界面，能看出整体气质

**摆出来就停**：展示完等用户选，不要在同一回合里继续做下一个阶段。

**产出**：`direction-approved.md`

```markdown
# 方向确认
- 三方向：<路径>
- 用户选择：<原话>
- 不可动约束：<用户明确的限制，如"绿色只给主操作">
```

**gate**：用户明确选了方向，且约束被记录下来。

**卡点**：用户可能边看边提修改（"这个按钮再大点"）——这些是方向内的调整，不是新方向；记下来在 S4 落实即可，不要因此重做三方向。

---

## S3 · 系统

在选定方向上定义三件事。这一阶段决定后面所有页面文档的一致性。

### 1. Design Token

从选定方向里**提取**而不是发明：色板取实际用到的色值、字阶取实际用到的字号。每项写值、用途、使用规则。

规则要能裁决冲突。例如"绿色只给主操作，一屏最多一个绿色实心块"——有了这条，快记的绿色取消按钮就能被立刻判为违规。

### 2. Design Widget

把界面里重复出现的块抽成组件。判断标准：**在两个以上页面以相同形态出现**。

每件一个独立文件，index 聚合。分类用通用组件库分法，不要自创分类。

**唯一来源原则**：组件定义只存在于 `design-widget/`；页面文档只写"本页用了哪几个、各自干什么"，不重复写尺寸。

### 3. 交互地图

两层：

- **聚合层**：把所有跨页动作按起点排开，每条写清「起点 → 动作 → 终点 → 跳转类型」
- **页面卡片**：每页一张，卡片内用虚线分成「页面间」（谁进来、我出去）与「页面内」（状态切换）

**页面内不算跳转**：分段切换、多选、展开菜单这些不产生返回栈，不进页面间流转。

**gate**：三件产出都在，且 Token 的每条规则都能用来裁决一个具体争议。

---

## S4 · 页面

每页四段式，顺序固定：UI → UX → Design Widget → Design Token。

### 先做样板

选一个**结构最完整**的页面做样板（不是最简单的）。样板要能体现：多屏、有菜单/浮层、有列表与空态。

样板完成后给用户看，确认三件事：

1. 四段结构对不对
2. UI 的保真度够不够（真实尺寸、真实字号 vs 缩略示意）
3. UX 的原型形态对不对（前后对照 vs 单图）

**这三件事没确认就批量，等于把错误复制 N 份。**

### 再批量

页面数 > 3 时派子 agent，见 `parallel.md`。

### gate

- 样板已确认
- 每份四段齐全
- 每份的 UI 段都是真实尺寸原型，不是缩略示意
- 每份的 Widget 段只引用不定义

**卡点**：
- "缩略图也是原型"——不是。字号不反映真实层级、间距不代表真实密度、看不出遮挡。
- "组件在页面里再写一遍方便阅读"——两处定义必然分叉，只允许引用。
- "先全写完再统一调"——批量前样板没定死，调的时候要改 N 份。

---

## S5 · 验收

完整流程见 `verification.md`。核心三条：

1. 跑结构检测，不抽样
2. 主 agent 亲自看，不接受子 agent 自报
3. 有问题的记进对齐清单，不默默通过

**产出**：`alignment.md`——设计与现有实现的差异逐条列出，供后续落地时核对。

---

## 迭代环

用户在任何阶段给出反馈时：

1. **定位到最小单元**：哪一屏、哪个组件、哪份文档
2. **只改那一处**，不整份重做
3. **重渲染**受影响的 PNG
4. **复检**：改动处 + 相邻区域（改动常把别处挤坏）

如果反馈涉及结构（比如"文档应该改成四段式"），说明当前处在错误的阶段——回到对应 stage 的 gate 重新确认，而不是在原结构上打补丁。

**判断标准**：改完之后，用户再指同一个地方，就是修错了。
