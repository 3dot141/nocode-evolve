# Reference: quick-view (骨架速查锚点)

骨架速查 reference——把整个系统/管线/矩阵/状态机的**整体结构**摆在文档前部，让读者前 3 屏就能 grasp"这个东西长什么样"，再看后续章节的决策推演和实施细节。

> 本 reference 是 `dev-design-refine` 的**可选增强**——适合骨架驱动型内容（矩阵/管线/状态机/协议），与现有 doc-type 主轴正交（Design Doc / RFC 类型可在「目标」节后加 quick-view 锚点节）。**不替代 doc-type 选择**，只在合适时加为一个章节。

## 何时用这个 reference

**强烈推荐**（适合骨架驱动型内容）：
- 评测体系 / benchmark / rubric 系统 → 4 类 task × 3 层打分 是矩阵
- 路由表 / dispatcher / pipeline → N 阶段串联的管线
- 状态机 / lifecycle → 节点 + transition 矩阵
- 协议 / 多层架构 → layer × responsibility 二维表

**不要用**：
- 单一架构决策（ADR）—— 决策本身就是结论，没有骨架可锚
- 决策驱动型 feature design —— 「背景 → 方案对比 → 结论」线性叙事，骨架本身就是结论

## 为什么需要这个锚点

线性叙事的 design-doc（背景 → 架构 → 实现）适合**决策驱动**叙事——读者跟着"问题 → 方案对比 → 结论"线性推进。

但**骨架驱动**内容里：
- 多个"问题"是平行**维度**（评测体系的 4 个问题 = 入口/任务/打分/过程，4 个并列轴），不是独立决策
- 整体结构是**矩阵 / 状态机 / 管线**，需要图/表一次性展示
- 把骨架打散到"问题一/二/三/四"四个 H4 节里 = 读者拼不起整体

`quick-view` 卡的作用：**把骨架先摆出来作为锚点**，后面章节的决策推演就有了"它在改进哪个 cell / 哪个状态 / 哪个阶段"的引用对象。

## 输出骨架

放在 `## 目标` 之后、`## 前置假设` 或 `## 架构` 之前。命名按内容定（不一定叫"Quick View"）：

```markdown
## <topic> 骨架

> 一句话讲整个系统/管线/矩阵的核心结构。
> 后续章节展开决策推演和实施细节，这一节是**整体锚点**——读者先抓骨架再读细节。

<完整 ASCII 流程图 / 矩阵表 / 状态机图>

<分维度展开（每维度一句话 + 必要的子表）>
```

## 三种典型形态

按内容性质选其一：

### 形态 1：管线骨架（评测体系 / pipeline 类）

```markdown
## 评测体系骨架

整体三轴：意图识别（入口分流）+ 输出质量（任务类型 × 3 层打分）+ 过程合规（性能 / 缓存 / 工具调用）。

[输入] 数据集 + Case = {prompt, intent_label, task_type, rubric}
   │
   ▼
┌──────────────────────────┐
│ Step 1：分类调度          │ ──模糊──▶ [反问 judge → END]
└──────────────────────────┘
   │ 明确
   ▼
┌──────────────────────────┐
│ Step 2：跑 agent          │
└──────────────────────────┘
   │
   ▼
┌──────────────────────────┐
│ Step 3：3 层打分          │
│   L1 硬门槛 / L2 / L3     │
└──────────────────────────┘
   │
   ▼
┌──────────────────────────┐
│ Step 4：过程指标采集      │
└──────────────────────────┘

### 任务类型（4 类）

任务类型
├─ 客观维度（按规约执行）
│   ├─ 1. 简单产物    图表 / 表格
│   └─ 2. 复杂产物    仪表板 / 故事板
└─ 主观维度（自主规划）
    ├─ 3a. 自主产物   agent 自选形态
    └─ 3b. 思维输出   分析思路 / 答疑

### 3 层打分（rubric 共性）

| 任务类型     | L2 权重    | L3 权重 | Judge 敏感度 |
| 1. 简单产物  | 重         | 轻      | 不敏感       |
| 2. 复杂产物  | 重         | 轻      | 不敏感       |
| 3a. 自主产物 | 中（动态） | 重      | 敏感         |
| 3b. 思维输出 | 弱         | 重      | 极敏感       |
```

### 形态 2：矩阵骨架（rubric / 路由表类）

```markdown
## 路由骨架

backend 路由表（CompositeBackend）：

```
默认/任意                  → StateBackend (LangGraph runtime state)
/conversation_history/    → StoreBackend (5 层硬隔离 namespace)
/memories/                → MemoryPolicyBackend
/skills/                  → ❌ 不挂（D5）
```

按路径前缀分发到不同物理存储，LLM 不关心后端是什么。
```

### 形态 3：状态机骨架（lifecycle 类）

```markdown
## 状态机骨架

```
draft ─────▶ in-review ─────▶ approved ─────▶ implemented ─────▶ archived
              │                    │
              └─ rejected           └─ rolled-back ──▶ draft
```

approved 状态后仍是 living document（可 in-place 修订，与 ADR 不同）。
```

## 填充规则

1. **整体图必有**：ASCII 流程图 / 矩阵表 / 状态机图三选一
2. **维度展开**：每个维度一句话定义 + 必要时给子表
3. **不展开决策推演**：「为什么按这个维度切」留给后续「架构」/「方案选型」节
4. **不展开实施细节**：「具体代码怎么写」留给后续「实现」节的业务流（BF1/BF2/...）
5. **承上启下**：节首一句话承接「目标」节；节末一句话引出「架构」/「实现」

## 关键约束

- **长度**：1-2 屏，不能太长（超过 = 喧宾夺主，回归到决策驱动的"架构"节）
- **位置**：必须在「目标」之后、「架构」之前——这是"读者前 3 屏抓骨架"的核心
- **不引用未定义术语**：节内出现的术语必须在「背景」或「目标」已定义；否则在 quick-view 内 inline 解释一句

## 反例

❌ **整节都是文字**（没图）—— 退化为另一个"架构总结"节，失去意义
❌ **整节都是图，没有维度展开**——读者看图能猜个大概，但抓不住每个维度的精确含义
❌ **位置错放**（在「实现」节之后）——锚点失效，读者已经被前面章节拖走了
❌ **过度展开决策**（"我们为什么按 X/Y 切"）——这是「架构」/「方案选型」节的工作

## 与 design-doc 主轴章节的关系

- 上游：「背景」（提供问题语境）+「目标」（提供目标）
- 下游：「架构」（展开"为什么这么切 + 整体组件关系"）+「实现」的业务流 BF1/BF2/...（展开"怎么实施"）+「方案选型」（Q→选项→定）
- 后续章节**可以引用 quick-view 节的命名**作为锚点（eg.「BF1 覆盖骨架的 Step 1 + Step 2」「方案选型 Q1 改进骨架第二轴的打分权重」）

> 与 `references/doc-types/design-doc.md` 主骨架（背景 → 目标 → 架构 → 实现 → 方案选型 → 后果）的关系：quick-view 插在「目标」与「架构」之间作为**结构锚点节**，不替代「架构」节（后者展开组件依赖、依赖关系、关键决策），二者互补。
