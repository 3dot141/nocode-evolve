# PRD（Product Requirements Document）

产品需求文档——回答 **"what + why"**，给团队对齐用，是工程设计的起点。

## 何时用 PRD

- 新产品 / 新模块 / 新 feature 立项
- 产品负责人与工程团队对齐需求
- **不是** 工程实施细节（用 Design Doc）
- **不是** 单一架构决策（用 ADR）

## 骨架

```
## 背景         (用户痛点 + 主因/辅因 + 不做的代价)
## 目标         (本 feature 要达成什么，可量化)
## 用户场景
### 场景一 <名字>
角色 / 触发 / 当前流程 / 期望流程 / 痛点位置
### 场景二 ...
## 验收标准     (可验证 checklist + 边界情况 + 明确排除)
```

**关键约束**：

- 「背景」必显式标主因 vs 辅因——平铺 N 条 bullet 是反模式
- 「用户场景」每场景要具体到角色 / 触发 / 流程 / 痛点定位；不允许"用户可以查看订单"式抽象描述
- 「验收标准」可机器或人工逐条 check；包含**明确排除项**（防 scope creep，取代旧"Non-Goals"硬节）
- 不写工程实施细节（接口 schema / 数据库 / 算法）——那是 Design Doc 的事

## 各节写作要点

### 背景

- 列具体痛点，主因 vs 辅因划分清楚
- 量化代价（"每次浪费 8.4 分钟"、"60% 错误来自 X"），不要"用户体验差"敷衍
- 现状 vs 期望对照写——告诉读者"现在卡在哪、想到哪去"
- 不复述用户原 prompt；不堆功能清单

### 目标

- 可量化最好（DAU、转化率、错误率、时间节省）
- 不允许"灵活、可扩展、易维护"凑数
- 与背景的主因对得上——目标解决主因，辅因要么纳入要么明示不解

### 用户场景

每场景一节，结构：

```
#### 场景X：<场景名>
角色：<persona>
触发：<什么时候触发>
当前流程：<现在用户怎么做，卡在哪>
期望流程：<本 feature 后用户怎么做>
痛点位置：<具体卡在流程哪一步>
```

2-4 个场景够；超 5 个 scope 太大，拆 PRD。

### 验收标准

可验证的 checklist。最后必含**明确排除**节——同等具体，不允许"其他都不做"敷衍。

```
- [ ] <可验证条件 1>
- [ ] <可验证条件 2>
...
**明确排除**：
- 不做 X（因为 Y）
- 不做 Z（因为 W）
```

## 状态机

```
draft → in-review → approved → implemented → archived
```

## frontmatter

```yaml
---
type: prd
topic: <一句话讲这个产品 / feature 是什么>
date: YYMMDD
author: <username>
status: draft   # draft | in-review | approved | implemented | archived
---
```

## 长度参考

1-2 页正常；超过 3 页通常说明 scope 太大，考虑拆分多个 PRD。

## 写作纪律

- 「背景」主因/辅因划分清楚
- 「用户场景」具体到角色 / 触发 / 流程 / 痛点定位
- 「验收标准」可验证 + 明确排除
- 不写工程实施细节（接口 / 表 / 算法）
- 不写"灵活、可扩展、易维护"等空话
