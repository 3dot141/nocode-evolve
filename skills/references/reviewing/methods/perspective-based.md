# 方法卡：perspective-based（多视角分工，PBR）

> reviewing 框架方法库 · 评审方法之一。**适合**：方案 / 设计文档 / 需求——内容**面向多类利益相关者**、单一视角易漏的对象。Perspective-Based Reading（PBR）。**不适合**：纯机械逐项核查（用 checklist）、纯对抗判断（用 red-blue-adversarial）。
>
> ⚠️ 业界证据（设计 §2.3）：**视角分工 > 通用清单**——让每个 reviewer 戴一顶特定「帽子」深读，比所有人用一份大清单泛读检出力更高。检出集是各视角的**并集**。

## 一、维度 / 思路

PBR 的核心是**分视角、各深读、取并集**。不给所有 reviewer 同一份清单，而是每人扮一个角色，只从那个角色的关切点深挖：

| 视角（帽子） | 关切点 | 典型问题 |
|---|---|---|
| **用户 / 使用者** | 能不能用、好不好用、边界场景 | 异常输入怎么办？空状态？错误提示清楚吗？ |
| **维护者 / 后来人** | 可读性、可改性、隐含耦合 | 半年后改这块要读懂多少上下文？命名/边界清楚吗？ |
| **测试者** | 可测性、覆盖盲点 | 这条路径怎么测？有没有不可测的副作用？ |
| **攻击者 / 滥用者** | 信任边界、误用 | 外部输入校验了吗？能被构造恶意输入吗？（深入用 threat-modeling） |
| **运维 / SRE** | 可观测、故障域、回滚 | 挂了怎么知道？怎么回滚？新增几个故障点？ |
| **领域专家** | 业务正确性、规则一致 | 业务规则对吗？和已有约定冲突吗？ |

视角集**按对象裁剪**——不是每个对象都需要全部六顶帽子。引入细则据评审对象选 2-4 个最相关视角分工。

**纪律**：① 一个 reviewer（或一轮）只戴一顶帽子，戴齐再换，不要混着看（混着看 = 退化成泛读，失去 PBR 价值）；② 各视角发现**取并集**，不同视角命中同一问题 = 高置信；③ 落到 `file:line` / `[锚点]`。

## 二、输出契约

产出 `findings[]`，映射 `{NOCODE_SKILL_REF}/reviewing/findings-contract.md`：

- 每条 finding：`axis` = 视角名（`用户视角` / `维护者视角` / `攻击者视角`……）；`location` 必填；`severity` = C/W/S；`source` = `subagent`（分视角派 subagent 时）/ `主路`（主会话自演多视角时）。
- 各视角并集去重：`dedup(by=[location, axis])`——同位置不同视角各记一条（视角不同价值不同），同位置同视角才合并。
- 受 Evidence Gate 约束（事实类 critical 缺 location 降 open-question）。
- `verdict.counts` 汇总。

## 三、派发策略

| 模式 | 派 subagent | 调 codex | 说明 |
|---|---|---|---|
| **轻量多视角自审** | 否 | 否 | 主 agent 顺序戴每顶帽子各深读一遍（适合 2-3 视角、低风险） |
| **并行分工**（推荐重档） | **是**（每视角一个 general-purpose subagent）| 可选 | 视角间天然独立，并行派发避免主 agent 串行时「视角污染」（看完用户视角再看维护者会带前一顶帽子的锚定）|

档位：
- 轻档 → 主 agent 自审 2-3 视角
- 重档 / 多利益相关者对象 → 每视角派独立 subagent 并行，**CLAIM 剥离**（只传对象 + 该视角关切点，不传其他视角发现），最后主 agent 取并集合并

codex 在 PBR 中可选——若需异源独立性，让 codex 扮其中一个高价值视角（如攻击者）。codex 不可用 → 该视角降级由 subagent 扮 + 明说。
