## 背景

核心问题：批量同步资源到多个 Agent 时，前端需要实时看到每条资源的同步进度（成功 / 失败 / 重试）。当前没有实时通道，前端只能等整批结束才拿到结果，体验差。

触发：feat「资源批量导入」设计中，场景 3「同步进度」需要一条服务端→前端的实时通道。这个通道用什么技术，影响前后端架构，单独预研后再进 dev-design。

预研边界：只决定"用哪种通信方案"，不设计具体的消息格式 / 重连策略 / 错误处理——那些是选定方案后 dev-design 的事。

## 问题定义

**要研究什么**：服务端→前端实时推送同步进度，三种候选方案怎么选？
- WebSocket（双向长连接）
- SSE（Server-Sent Events，服务端单向推送）
- 轮询（前端定时拉取）

**约束**：
- 现有技术栈：React 前端 + Node.js/Express 后端，无消息中间件
- 进度推送是**单向**的（服务端→前端），前端不需要实时上行
- 单实例部署，无多实例广播需求（暂时）
- 不引入新的基础设施（Redis pub/sub、消息队列等）除非必要

**评估维度**（按重要性排序）：

| 维度 | 为什么重要 |
|---|---|
| 通信方向匹配度 | 进度是单向推送，双向能力是浪费 |
| 实现复杂度 | 影响开发成本和维护成本 |
| 实时性 | 进度延迟影响用户体验 |
| 基础设施依赖 | 引入新组件 = 新的运维负担 |
| 断连恢复 | 网络抖动时能否自动恢复 |
| 扩展性 | 未来多实例部署是否好扩展 |

## 调研

### 各方案技术原理

**WebSocket**：
- 基于 HTTP Upgrade 握手后建立的全双工 TCP 长连接，客户端服务端可随时互发消息 [SOURCE: developer.mozilla.org/WebSocket]
- 需要单独的 `ws://` / `wss://` 协议，服务端要维护连接生命周期
- Node.js 生态用 `ws` 或 `socket.io` 库

**SSE（Server-Sent Events）**：
- 基于普通 HTTP 长连接，服务端通过 `text/event-stream` 持续推送，**单向**（仅服务端→客户端）[SOURCE: developer.mozilla.org/Server-sent_events]
- 浏览器原生 `EventSource` API，**自带断线自动重连**（默认 3 秒）
- 服务端只需保持响应流打开，按 `data: {...}\n\n` 格式写

**轮询**：
- 前端定时（如每 2 秒）发 HTTP 请求拉最新状态，服务端无状态响应 [SOURCE: 长轮询 vs 短轮询对比]
- 短轮询：固定间隔拉，简单但有延迟和空请求浪费
- 长轮询：服务端 hold 住请求直到有数据或超时，实时性好但占连接

### 业界怎么选

| 场景 | 业界选择 | 来源 |
|---|---|---|
| 进度条 / 通知推送（单向） | SSE | [SOURCE: GitHub Actions 实时日志用 SSE] |
| 协作编辑 / 聊天（双向高频） | WebSocket | [SOURCE: Figma / Slack 用 WebSocket] |
| 低频状态查询 | 短轮询 | [SOURCE: CI 状态徽章多用轮询] |
| AI 流式输出（单向逐 token） | SSE | [SOURCE: OpenAI / Claude API streaming 用 SSE] |

启发：**单向推送场景，业界主流是 SSE**——OpenAI、Claude 的流式 API 都用 SSE 而非 WebSocket，因为单向场景下 WebSocket 的双向能力是浪费。

### 代码现状

- [Read src/services/sync.ts:88] 现有 `syncToAgent()` 是同步阻塞调用，无进度回调机制
- [Read src/routes/index.ts:34] 现有路由全是普通 REST，无长连接 endpoint
- [Read package.json:22] 依赖里无 `ws` / `socket.io`，引入 WebSocket 需加新依赖；SSE 用原生 HTTP 不用加依赖

## 选项对比

### 逐维度对比表

| 维度 | WebSocket | SSE | 轮询（长） |
|---|---|---|---|
| 通信方向匹配 | 双向（过剩） | **单向（精确匹配）** | 单向（拉取式） |
| 实现复杂度 | 高（连接管理 + 库） | **低（原生 HTTP）** | 中（hold 请求 + 超时） |
| 实时性 | 实时 | **实时** | 接近实时（有间隔） |
| 基础设施依赖 | 加 ws 库 + 可能需 sticky session | **无新依赖** | 无新依赖 |
| 断连恢复 | 需手写重连 | **原生自动重连** | 天然无状态（下次拉即恢复） |
| 多实例扩展 | 难（需共享连接状态 / Redis） | 中（需 sticky 或共享事件源） | **易（无状态）** |
| 浏览器支持 | 好 | 好（IE 不支持，已不考虑） | 最好 |

### 各方案架构（技术原理差异）

**WebSocket**：
```
前端                          后端
 │  HTTP Upgrade 握手          │
 │ ─────────────────────────→ │
 │  101 Switching Protocols    │
 │ ←───────────────────────── │
 │ ═══ 全双工长连接 ═══         │  ← 双向，但进度只用到服务端→前端
 │ ←─── progress event ─────── │
 │ ←─── progress event ─────── │
 │ ──── (上行通道闲置) ──────→  │  ← 浪费的能力
```

**SSE**：
```
前端                          后端
 │  GET /progress              │
 │  Accept: text/event-stream  │
 │ ─────────────────────────→ │
 │  200 + 流保持打开            │
 │ ←───────────────────────── │
 │ ←── data: {r1 synced} ───── │  ← 单向推送
 │ ←── data: {r2 synced} ───── │
 │ ←── data: {complete} ────── │
 │     (断线 → 浏览器自动重连)   │  ← 原生能力
```

**轮询（长轮询）**：
```
前端                          后端
 │  GET /progress?since=0      │
 │ ─────────────────────────→ │
 │     (hold 住直到有数据)      │
 │ ←── {r1 synced} ─────────── │
 │  GET /progress?since=1      │  ← 每次新请求
 │ ─────────────────────────→ │
 │ ←── {r2 synced} ─────────── │
 │  GET /progress?since=2      │
 │ ─────────────────────────→ │
```

### 各方案优劣 + 适用条件

**WebSocket**：
- 优：全双工，未来若需前端实时上行（如取消单条同步）天然支持
- 劣：单向场景能力过剩；连接管理复杂；多实例需 sticky session 或共享状态；要加依赖
- 适用：双向高频交互（聊天、协作编辑、实时游戏）

**SSE**：
- 优：精确匹配单向推送；原生 HTTP 无新依赖；浏览器自带重连；实现最简单
- 劣：单向（前端要上行得另开 REST 请求，本场景不需要）；多实例扩展需 sticky session
- 适用：单向推送（进度、通知、流式输出）—— **本场景**

**轮询**：
- 优：最简单的心智模型；无状态最好扩展；网络层最兼容
- 劣：短轮询有延迟和空请求浪费；长轮询占连接且实现要处理超时；实时性不如推送
- 适用：低频状态查询，或对实时性要求不高的场景

## 结论 + 建议

**推荐：SSE**

理由（对照评估维度）：
1. **方向精确匹配**——进度推送是纯单向，SSE 正好；WebSocket 的双向是浪费
2. **零新依赖**——SSE 用原生 HTTP，WebSocket 要加 `ws` 库
3. **原生断连恢复**——浏览器 `EventSource` 自带重连，省去手写重连逻辑
4. **实现最简单**——spike 已验证现有技术栈下可直接落地
5. **业界印证**——OpenAI / Claude 流式 API、GitHub Actions 日志都用 SSE 做单向推送

**不推荐 WebSocket 的原因**：本场景纯单向，WebSocket 的全双工能力用不上，反而带来连接管理、依赖、多实例 sticky session 的额外复杂度。除非未来明确需要前端实时上行（如实时取消单条同步），否则不值得。

**不推荐轮询的原因**：长轮询实时性可接受但实现要处理 hold/超时，比 SSE 复杂；短轮询有延迟和空请求浪费。SSE 在实时性和实现简单度上都更优。
