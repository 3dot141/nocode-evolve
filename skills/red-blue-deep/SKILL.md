# 红蓝军辩论

评估/拍板类提问的思考框架。**先判档位，再选输出形态**——不要默认上重档，也不要默认糊轻档。

## 档位判定（必先做这一步）

| 信号（任一命中） | 档位 |
|---|---|
| 不可逆 / 跨模块 / 涉及选型 / 架构 / 重构 / 多方案僵持 / 用户显式说「深度评估 / 红蓝军 / 第一性原理 / 仔细想」 | **重档** |
| 决策可逆 + 影响单文件 + 易回滚（命名、文案、单点小改、风格偏好） | **轻档** |

模糊时按「能否 5 分钟内回滚」判：能 → 轻档，不能 → 重档。

## 轻档输出

**一句表态 + 一句关键理由**，不展开蓝/红/结论。

✅ 正例：
> 「这个变量名 `user_id` 怎么样」
> → 「比 `uid` 好——后者太泛，全局搜会撞到一堆无关引用。」

❌ 反例：为命名问题走完整三段红蓝军——折磨用户。

## 重档输出（完整四步）

### Step 1: 第一性原理拆解

剥到最基础的假设：这个决定要满足的**根本需求**是什么？哪些是真约束，哪些是历史包袱 / 沿用习惯？把伪需求剔掉。

**示例**：用户问「会话存储要不要上 Redis」

❌ 不拆解直接进蓝/红军：
> 蓝军：Redis 性能好、有持久化、生态成熟
> 红军：多一个运维负担、多一个故障点

→ 这场争论是在「Redis 这个具体技术」上打转。如果根本需求是别的，整场辩论方向就错了。

✅ 第一性原理拆解：
> **根本需求**：会话需要在多个服务进程间共享，且单进程崩溃时不丢用户登录态。
> **真约束**：(a) 多进程共享 (b) 不丢登录态
> **历史包袱**：「大家都用 Redis 做会话」是惯例不是约束；「我们之前用过 Redis」是沿用不是需求。
> **伪需求剔掉**：高性能（会话读写 QPS 实际很低）、持久化（登录态丢了用户重登即可，不是必须 durable）
> **拆解结论**：真问题是「跨进程共享 + 短期可靠的 KV」。可选项不止 Redis——sticky session + 内存、共享文件、Memcached、数据库表都能选。Redis 只是其中一种，不是默认答案。

→ 拆完才进蓝/红军，否则在错误命题上辩论。

### Step 2: 蓝军（防守方）

列**提议方案**的优势 / 适用场景 / 隐含好处。必须落到具体场景（「X 时候有用」），不能空对空（「灵活性更好」）。

### Step 3: 红军（攻击方）

列弱点 / 边界 / 隐藏代价 / 维护负担。必须落到具体场景（「实现时会遇到 X」/「N 个月后会出现 Y」），「理论上可能」不算。

### Step 4: 结论

格式：「**倾向 A —— 因为 [关键蓝军论点]；但承认 [关键红军论点] 是真问题，[如何缓解]**」

不要「看情况」「都有道理」「你怎么想」——这是逃避。

## Sequential-Thinking（重档默认开）

重档**默认调用** `sequential-thinking` skill 或 `mcp__sequential-thinking__sequentialthinking`：

- 重档天然有多分支（每个红军论点都可能引出新方案）
- 允许 **revise**：红军环节发现 step 1 拆错了基础假设，回去重拆，不要硬撑
- 允许 **branch**：蓝军强支撑某方案、红军强反驳后想试一个折中，不要丢主线

仅当问题分支 ≤ 2 个**且**推理链 ≤ 3 步时可跳过。

## 反例

- 轻档问题强走重档 → 噪音
- 重档问题降级走轻档 → 草率，架构决策一句话表态等于失职
- 跳过第一性原理直接进蓝/红军 → 在错误假设上反复辩论
- 只蓝军独白 → 销售
- 只红军独白 → 抬杠
- 双方都列了结论说「都可以」→ 失职
- 红军论点全是「理论上可能」→ 没暴露真问题
- 全段中立陈述无对抗 → 退化成 pros/cons 列表
