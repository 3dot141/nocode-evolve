# 红蓝军辩论

评估/拍板类提问的思考框架。**先判档位，再选输出形态**——不要默认上重档，也不要默认糊轻档。

## 档位判定（必先做这一步）

| 信号（任一命中） | 档位 |
|---|---|
| 不可逆 / 跨模块 / 涉及选型 / 架构 / 重构 / 多方案僵持 / 用户显式说「深度评估 / 红蓝军 / 第一性原理 / 仔细想」 | **重档** |
| 决策可逆 + 影响单文件 + 易回滚（命名、文案、单点小改、风格偏好） | **轻档** |

模糊时按「能否 5 分钟内回滚」判：能 → 轻档，不能 → 重档。

**「多方案僵持」定义**：两个或以上互斥方案各有强支撑、你无法判断哪个更好。比如「前后端分离 vs 全栈 SSR」「PostgreSQL vs MongoDB 当主存储」。

**边界示例**：

- 改对外 API 字段名：代码层可逆但已发布 client 会破 → **重档**
- 升主依赖大版本（框架 / 语言运行时）→ **重档**（影响生态而非自身代码）
- 升工具依赖（lint / formatter / 单测库）→ **轻档**
- 改 commit message / PR 标题文案 → **轻档**
- 调一个内部函数命名 → **轻档**

## 轻档输出

**一句表态 + 一句关键理由**，不展开蓝/红/结论。

✅ 正例：
> 「这个变量名 `user_id` 怎么样」
> → 「比 `uid` 好——后者太泛，全局搜会撞到一堆无关引用。」

❌ 反例：为命名问题走完整三段红蓝军——折磨用户。

## 重档输出（完整四步）

**前置 Gate — 开 sequential-thinking**：进 Step 1 前**必须**先调用 `Skill(sequential-thinking)` 或 `mcp__sequential-thinking__sequentialthinking` 开启结构化思考 session。**不开不能往下走**——这是硬 gate，不是建议。

sequential-thinking 在重档中的作用：
- 多分支推演（每个独立审查发现都可能引出新方案）
- 中途回退重拆（独立审查发现 Step 1 拆错了基础假设，回去重拆，不硬撑）
- 试折中分支不丢主线（蓝军强支撑、独立审查强反驳后想试折中，可开新分支推演）

```
sequential-thinking 可用？
     │
     ├─ 可用 ──→ 开启 session → 进 Step 1
     │
     └─ 不可用 ──→ 明说「sequential-thinking 不可用，
                    重档辩论在无结构化思考辅助下进行」
                    → 仍进 Step 1（降级不阻断）
```

下面用同一个例子串完 4 步——用户问「会话存储要不要上 Redis」。

### Step 1: 第一性原理拆解

剥到最基础的假设：这个决定要满足的**根本需求**是什么？哪些是真约束，哪些是历史包袱 / 沿用习惯？把伪需求剔掉。

❌ 不拆解直接进蓝/红军：
> 蓝军：Redis 性能好、有持久化、生态成熟
> 红军：多一个运维负担、多一个故障点

→ 这场争论是在「Redis 这个具体技术」上打转。如果根本需求是别的，整场辩论方向就错了。

✅ 第一性原理拆解：
> **根本需求**：会话需要在多个服务进程间共享，且单进程崩溃时不丢用户登录态。
> **真约束**：(a) 多进程共享 (b) 不丢登录态
> **历史包袱**：「大家都用 Redis 做会话」是惯例不是约束；「我们之前用过 Redis」是沿用不是需求。
> **伪需求剔掉**：高性能（会话读写 QPS 实际很低）、持久化（登录态丢了用户重登即可，不是必须 durable）
> **拆解结论**：真问题是「跨进程共享 + 短期可靠的 KV」。候选项 = Redis / sticky session + 内存 / Memcached / 数据库表。Redis 只是其中一种，不是默认答案。

→ 拆完才进蓝/红军，否则在错误命题上辩论。

### Step 2: 蓝军（防守 Redis 提议）

列**提议方案**的优势 / 适用场景 / 隐含好处。必须落到具体场景（「X 时候有用」），不能空对空（「灵活性更好」）。

✅ 示例：
> - 团队已有 Redis 运维经验 → 不增加新组件学习成本
> - 原生 TTL/expire 策略 → 会话过期处理省心，不用自己写过期 job
> - 后续如果加「按用户 ID 强制下线」这类操作 → Redis 的命令集天然支持，比 sticky session 改起来简单

### Step 3: 独立审查

蓝军由主 agent 做（Step 2），红军和全面审查交给**隔离上下文的独立 reviewer**——主 agent 自己攻击自己的方案难免手下留情，而且只从攻击角度看容易遗漏盲区。

**并行双跑**（参照 `rule-codex-review` 场景四）：

1. **Subagent**（`Agent` general-purpose）：传入被评估方案 + 约束条件 + Step 1 拆出的真约束，做完整独立 review
2. **Codex**：同样传入方案 + 约束 + 真约束，独立 review

每路 reviewer 输出四个维度：
- **优势**（落到具体场景，可能发现蓝军遗漏的好处）
- **弱点和隐藏代价**（落到「实现时会遇到 X」/「N 个月后会出现 Y」，不要「理论上可能」）
- **盲区**（提议者可能没想到的维度）
- **替代方案**

```bash
node "${CLAUDE_PLUGIN_ROOT}/vendor/codex/scripts/codex-companion.mjs" task \
  "只读。独立审查以下方案，列出：
   1. 优势（落到具体场景）
   2. 弱点和隐藏代价（「实现时会遇到 X」/「N 个月后 Y」，不要「理论上可能」）
   3. 盲区（提议者可能没想到的维度）
   4. 替代方案
   <方案描述 + 约束条件 + 真约束>"
```

**CLAIM 剥离**：只传方案 + 约束 + Step 1 真约束。**不传蓝军分析和你的倾向**。传了倾向，reviewer 会锚定你的分析而不是自己想——就像给 reviewer 看了作者的自评，独立性直接打折。

**合并三路发现**（主 agent 蓝军 + subagent + codex）：
- 三路交集 = 高置信
- 对称差（只有一路提到）= 盲区，逐条判断是否成立
- 盲区中成立的纳入 Step 4 结论

```
codex 可用？
     │
     ├─ 可用 ──→ subagent + codex 并行双跑 → 合并三路
     │
     └─ 不可用 ──→ 仅 subagent 单跑 + 明说「codex 不可用，
                    仅 subagent 独立审查」→ 合并两路
```

✅ 示例（续 Redis 案例）：
> **subagent 独立发现**：
> - 优势：Redis Sentinel 自带高可用，sticky session 实例挂了没有自动恢复
> - 弱点：5 人小组无专职 SRE，Redis 挂了登录全断 → 多 1 个 P0 故障源
> - 盲区：sticky session 在 WebSocket 长连接场景下不生效（负载均衡无法粘连）
>
> **codex 独立发现**：
> - 弱点：Memcached 能力等价但维护更简单 → Redis 在本场景是 over-engineering
> - 盲区：跨数据中心部署时所有内存方案都要重来
> - 替代方案：数据库 session 表 + 短 TTL，QPS 低时性能够用
>
> **合并判断**：WebSocket 盲区成立（当前系统有长连接）→ 纳入结论；跨 DC 不成立（3 年内单 DC）→ 记录但不影响结论；数据库替代方案成立 → 作为候选纳入结论。

### Step 4: 结论

格式：「**倾向 A —— 因为 [关键蓝军论点]；但承认 [独立审查关键发现] 是真问题，[如何缓解]**」

纳入 Step 3 独立审查的发现——特别是盲区中成立的部分，必须在结论中有体现，不能合并完又丢掉。

✅ 示例：
> **倾向 sticky session + 内存** —— 因为 QPS 实际很低、登录态丢了用户重登可接受，少一个组件就少一个故障源；但承认独立审查的两个真问题：(1) 负载均衡器更换/单实例宕机时会话集体失效，(2) WebSocket 长连接场景 sticky session 不生效——缓解：先用 sticky 跑 3 个月，QPS 或宕机频率突破阈值再迁；WebSocket 模块如需会话共享，单独走数据库 session 表（独立审查提出的替代方案，QPS 低时性能够用）。

不要「看情况」「都有道理」「你怎么想」——这是逃避。

## Doubt Theater 检测

独立审查（subagent + codex）返回的弱点和盲区全是"理论上可能"但无具体场景 = 走过场。检测到后两个选择：
- 换审查角度重跑（从技术换到运维/从性能换到安全/从短期换到长期，给 reviewer 新的提示）
- 承认无有效反驳，结论直接采纳蓝军方案

不要为了"独立审查也得说点什么"而把站不住的发现当真。

## 三轮收敛上限

sequential-thinking 允许回退重拆，但最多 3 轮。第 3 轮仍无法收敛 = 问题不在信息不够，在于缺用户输入——停下问用户补约束（"你更在意 X 还是 Y？"），而不是继续空转。

## 反例

- 轻档问题强走重档 → 噪音
- 重档问题降级走轻档 → 草率，架构决策一句话表态等于失职
- 跳过第一性原理直接进蓝军/独立审查 → 在错误假设上辩论
- 只蓝军独白、跳过独立审查 → 销售（自己说好没人查）
- 主 agent 自己演红军而不交给独立 reviewer → 手下留情，失去隔离价值
- 蓝军 + 独立审查都列了结论说「都可以」→ 失职
- 独立审查发现全是「理论上可能」→ Doubt Theater，没暴露真问题
- 全段中立陈述无对抗 → 退化成 pros/cons 列表
- 重档跳过 sequential-thinking gate → 失去多分支推演和回退能力，硬撑做决定
- 独立审查传了蓝军分析和倾向 → reviewer 被锚定，失去独立性
- 独立审查发现了盲区但结论没体现 → 做了审核等于没做
