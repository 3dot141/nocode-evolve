# Devflow Redesign — Design Log

> 状态：已实现并验证，待提交
> 创建日期：2026-08-03
> 主题：简化 devflow，并重构 Define / Design 的澄清与设计流程
> 定位：本文件是本轮设计沟通的过程事实源。每轮沟通先入库，再进入下一轮。

## 记录协议

1. 记录用户原意、形成的决定、采用的术语、影响的流程和未决分支。
2. 代码或环境能够确认的事实由 agent 调查，并记录证据；需要用户判断的决策逐项追问。
3. 新结论与旧结论冲突时，保留旧结论并标记「已替代」，不得静默覆盖。
4. 使用可能产生歧义的名词时，在当轮记录其含义或标记为未定义。
5. 一轮沟通只有在本文件更新完成后才算结束；下一轮必须基于本文件的最新状态继续。
6. 最终全景从本文件收敛生成，不另造 `shapeReceipt` 等中间协议对象。

## 当前已确认

### D-001：devflow 只判断任务类型

devflow 进入后只判断三种任务类型：

- `bug`
- `feat`
- `refactor`

不再使用 `Mini / Standard / Full / Fix` 作为 devflow 内部的四场景分类。简单单步任务是否进入 devflow，属于外层触发问题，不作为第四种任务类型。

### D-002：Define 与 Design 朝合并方向重构

当前方向是把 Define 与 Design 合并为同一个连续沟通过程：保留「先定义问题，再选择方案」的认知顺序，但不再维护两个 Skill 的重复计划、文档所有权、确认点和交接协议。

合并后阶段的正式名称尚未确认；`Shape` 只是讨论中的建议名，不是已确认术语。

### D-003：第一步不是给全景，而是追问

任务类型确定后，不能立即由 agent 生成全景。必须从第一性原理开始追问，把用户意图、约束、流程和验收逐项澄清。

全景是追问和对齐完成后的确认产物，不是沟通起点。

### D-004：追问必须闭合全部相关流程

追问不能只收集目标、范围等字段。必须把相关流程逐条展开并对齐，包括：

- 触发者与前置条件
- 主流程与分支条件
- 状态变化与最终结果
- 失败、恢复、重试和回滚
- 角色、权限和数据边界
- 外部依赖与不可用场景
- 验收标准与验证证据

追问结束不能依赖主观的「95% 置信度」。是否完成应由结构性闭合判断：流程无未定义分支、流程与验收双向对应、状态变化闭合、事实冲突已解释、没有会改变方向的未决问题。

### D-005：沟通过程每一步都要入库

为防止长会话、compact、换会话或换 agent 导致漂移，每轮问答完成后必须先更新本文件，再提出下一题。

每轮至少记录：

- 问题及其上下文
- agent 的推荐答案和理由
- 用户回答
- 使用或新形成的术语
- 已确认事实、假设和决定
- 受影响的流程
- 尚未解决的决策树分支

「用户已经回答」不等于本轮完成；记录已落盘并完成一致性检查，才算本轮完成。

### D-006：术语记录在沟通 Log 中

沟通过程使用领域名词或可能歧义的术语时，必须在当轮 Log 中记录其含义、边界和确认状态。术语尚未确认时也要记录为未决；后续定义改变时追加修正记录，不静默覆盖历史。

当前没有确认要在沟通过程中同步维护独立的 `CONTEXT.md` 或 ADR 文件。已经确认的是：术语、重要决定及其理由必须进入本沟通 Log。是否在收敛后进一步提炼为 `CONTEXT.md` / ADR，留待后续讨论。

### D-007：过程文件命名为 `design.log.md`

本文件名已确认使用 `design.log.md`，并落在用户的工程设计文档目录中。

### D-008：三种任务共用统一入口，退出深度不同

合并后的 Define / Design 作为 `bug / feat / refactor` 的统一入口，但按任务类型采用不同的退出深度：

- `bug`：闭合预期行为、实际行为、复现路径、影响范围和修复验收；根因与修复方案暂缓，进入 Debug。
- `feat`：闭合问题、全部相关流程和解决方案，进入 Plan。
- `refactor`：闭合当前结构问题、行为不变量和目标结构，进入 Plan。

统一入口不等于三种类型使用完全相同的追问树。

### D-009：主 `SKILL.md` 只保留流程主干

合并后的 Skill 必须保持精简：主 `SKILL.md` 只承载稳定主干、硬约束、类型路由和总 Gate；不同类型的追问细节、Log 写入细节、流程闭合检查等放在 Skill 自己的子文件中，并由主干按当前类型和步骤按需读取。

子文件必须留在该 Skill 自己的目录边界内，不能把执行细节重新指向 rule、model、hook 或其它插件内部实现文件。具体目录和拆分粒度尚待设计。

### D-010：唯一对外入口沿用 `dev-design`

合并后的唯一对外 Skill 沿用 `dev-design`。现有 `dev-define` 退出 devflow 主流程，不再与 `dev-design` 形成两个连续阶段或两个公开职责入口。

`dev-design` 内部仍严格保持「先 grilling 闭合问题，再选择和对齐方案」的顺序；沿用名称不代表可以跳过问题定义。

### D-011：私有细节按任务类型分目录

`dev-design` 采用类型专属的私有子目录，`bug / feat / refactor` 分别维护自己的追问、闭合和全景协议：

```text
skills/dev-design/
├── SKILL.md
└── references/
    ├── grilling.md
    ├── bug/
    │   ├── questions.md
    │   ├── closure.md
    │   └── panorama.md
    ├── feat/
    │   ├── questions.md
    │   ├── closure.md
    │   └── panorama.md
    └── refactor/
        ├── questions.md
        ├── closure.md
        └── panorama.md
```

单一共享 `panorama.md` 的方案已否决。三类全景采用不同的信息结构：Bug 面向可复现问题与 Debug handoff；Feat 面向完整用户/系统流程与方案承接；Refactor 面向 Before / After、行为不变量和迁移验证。

### D-012：`questions.md` 使用动态覆盖决策树

三种类型的 `questions.md` 不采用固定问卷，而是定义动态覆盖决策树：稳定的是必须闭合的决策域、节点依赖、分支触发条件和完成证据；实际提问路径根据环境事实与用户回答动态展开。

每轮只处理一个依赖已满足的未闭合节点。节点只能以「已确认」「有证据地不适用」或「被后续决定替代」闭合。环境能够回答的事实由 agent 调查并入库，不向用户重复提问。

### D-013：Bug 进入 Debug 前必须形成复现契约

Bug 进入 Debug 前不强制已经稳定复现成功，但必须形成复现契约，并满足以下二选一：

1. 已复现：存在可重复执行的最小复现步骤和明确失败证据。
2. 暂不可复现：记录已尝试的环境、输入和结果，保留可靠现象或生产证据，并定义 Debug 下一步要补充的观测或实验。

两条路径都必须先闭合预期行为、实际行为、影响范围和修复验收。模糊现象且没有证据边界或下一步观测方案，不能通过该 Gate。

### D-014：Bug 必须违反既有权威预期

任务只有在当前行为违反本次请求之前已经成立的权威预期时，才能分类为 `bug`。权威预期可以来自已批准需求或设计、接口契约、自动化测试、明确验收标准、可证明的历史正常行为，或已存在且经用户确认的业务规则。

若用户在本次沟通中首次要求一种系统从未承诺过的新行为，则分类为 `feat`。多个预期来源互相冲突时，必须把冲突与证据写入 `design.log.md`，由用户确认有效基线，不自动选边。

### D-015：Bug 采用 Debug 前后双段设计

Bug 使用同一份 `design.log.md` 完成两段 `dev-design`：

```text
dev-design 问题段
→ Bug 问题全景
→ Debug
→ dev-design 修复段
→ Bug 修复全景
→ Plan 或 Build（条件待确认）
```

问题段闭合既有预期、实际行为、复现契约、影响和验收；Debug 负责证明根因；修复段消费根因证据，确定修复方案并重新对齐受影响流程、契约、数据边界和回归验证。两段不创建第二份事实源。

### D-016：Bug 修复后按实施结构条件路由

Bug 修复全景确认后不一律进入 Plan，也不重新引入 Mini / Standard 等复杂度分类：

- 单一闭环修复可直接进入 Build。
- 多切片、存在依赖顺序、迁移、兼容、公开契约变化、rollout 或多个检查点的修复必须进入 Plan。

路由结论及证据写入 Bug 修复全景，devflow 只消费结果并执行 handoff，不自行重新评估复杂度。

### D-017：Bug 使用双段动态覆盖决策树（经 D-018 修订）

`bug/questions.md` 采用 B0–B13 的双段动态覆盖决策树：问题段从权威预期、expected / actual、复现契约、流程差异、影响证据和外部对标闭合到验收与 Debug 调查契约；修复段从根因证据、候选修复、影响传播和回归设计闭合到 Build / Plan 路由。

决策树按条件展开暂不可复现、预期冲突、敏感风险、外部依赖、时序并发、幂等、迁移和兼容分支。各节点必须满足 D-012 的闭合状态要求。

当前编号为：

```text
问题段：B0 权威预期 → B1 expected/actual → B2 复现契约
→ B3 流程差异 → B4 影响风险 → B5 内部证据
→ B6 外部对标 → B7 修复验收 → B8 Debug 调查契约

修复段：B9 根因证据 → B10 候选修复 → B11 影响传播
→ B12 回归/观测/兼容/回滚 → B13 Build/Plan 路由
```

### D-018：三类决策树都包含类型专属竞品对标（经 D-020 修订）

`bug / feat / refactor` 都必须包含外部对标覆盖节点，但研究对象和目的按类型区分：

- Bug：同类产品正确行为、upstream issue、known issue、release note、安全公告和修复先例。
- Feat：可比竞品、开源产品和行业方案的用户流程、权限、状态、失败恢复、产品取舍和未解决痛点。
- Refactor：成熟开源实现、官方架构指南、模块 seam、依赖方向、数据所有权、测试方式和迁移案例。

竞品对标是必经覆盖节点，可以用「有证据地不适用」闭合。默认信息来源和联网边界由 D-020 规定；竞品相似方案不能代替本仓事实或根因证据。

### D-019：Feat 使用 F0–F14 动态覆盖决策树

`feat/questions.md` 采用 F0–F14 动态覆盖决策树，从真实结果、角色、当前流程和竞品方案开始，依次闭合范围、领域模型、用户流程、业务规则、系统流程、风险约束、现有承接点、候选方案、边界契约、发布迁移，最终完成流程 → 规则 → 方案 → 验收 → 证据的双向闭合并进入 Plan。

### D-020：竞品节点默认直接给方案，不自动联网

三类决策树进入竞品 / 外部对标节点时，默认由 agent 基于当前上下文、仓库事实和已有知识直接给出竞品方案，不自动发起网络查询。只有用户明确要求联网查询时，才进行网络检索。

默认模式下必须遵守 D-021 的内部知识库来源规则，不得把模型已有知识包装成当前、精确或已在线核验的竞品事实。竞品方案用于打开设计空间和帮助用户决策；影响范围或产品取舍的内容仍需用户确认。

### D-021：联网来源与内部知识库采用两套标注规则

竞品对标保留两种来源模式，不要求默认联网：

1. **联网对标**：用户明确要求网络查询时执行；结论必须附实际访问的在线来源，并记录 URL、页面可得的发布 / 更新时间、本轮访问时间和来源支持的具体结论。
2. **内部知识库**：默认直接给竞品方案时使用；必须明确标注「内部数据源」，并给出能够确认的内部数据源时间，同时标记未在本轮联网核验。

两种模式不能混写成同一种证据。内部知识库结论不能伪装成在线来源，联网结论也不能省略 URL 和访问时间。

### D-022：内部知识库时间不可得时不得猜测

运行时未提供可确认的模型知识截至时间或内部知识库快照时间时：

- 明确标注「内部数据源时间：运行时未提供」。
- 不得使用当前日期冒充知识截至时间。
- 相关竞品方案只能作为待验证候选，不得表述为当前竞品事实。
- 设计拍板必须依赖该事实时，停下请求用户授权联网；仅用于打开方案空间时可以继续比较，但必须保留未验证标记。

### D-023：Refactor 使用修订后的 R0–R13 动态覆盖决策树

`refactor/questions.md` 采用 R0–R13 动态覆盖决策树：从类型 Gate、重构动机、Before、行为不变量和竞品 / 参考架构对标，进入目标质量、候选结构、After、迁移、兼容回滚、验证、清理和最终闭合，然后进入 Plan。

R1 允许结构 / 工程问题与设计质量 / 优雅性改进两类合法动机。优雅性改进不要求先证明量化损失，但必须点名具体代码或结构、说明改善性质、锁定行为不变量，并明确范围和停止条件。R6 允许使用经用户确认的专业设计质量判据，不强制全部数字化。

### D-024：devflow 采用四项最小职责和薄路由循环

devflow 只保留：

1. 判断 `bug / feat / refactor`。
2. 根据类型和当前阶段结果选择下一 Skill。
3. 原样传递 `design.log.md`、阶段产物和用户决定。
4. 处理明确回流，例如 Bug `dev-design → Debug → dev-design`、Verify 失败回 Build。

devflow 删除重复阶段 sub-steps、完整 Gate 细节、全阶段预创建 plan / task、下一阶段内部步骤展开及 Mini / Standard / Full / Fix 场景矩阵。每个阶段 Skill 自己负责内部流程、确认和证据。

devflow 每次 handoff 只向 `design.log.md` 追加 from / to、原因和产物引用的阶段流转记录，不复制阶段内容。

### D-025：design.log.md 同时维护四个同步视图

`design.log.md` 固定维护当前决定索引、当前术语表、当前决策树位置和追加式 Round Log。每轮用户回答后，必须依次追加 Round、更新 D-xxx、更新术语、更新决策树位置并检查四视图一致，完成后才能提出下一题。

Round 使用固定 Markdown 模板记录节点状态、背景事实、唯一问题、agent 推荐、用户回答、术语、形成决定、流程影响和下一可提问节点。没有内容的字段写「无」，不能删除字段。

### D-026：事实证据按来源类型记录并绑定结论

`design.log.md` 对仓库代码、命令结果、内部文档、用户决定、联网来源、内部知识库及截图 / 日志 / 附件采用不同的最小证据格式。

仓库代码使用 `scanBase commit + path + symbol / 配置键 / section + 读取时行号`；行号不是唯一锚点。所有来源必须点名它支持的具体结论。证据被后续事实推翻时保留旧记录并标记 superseded。

### D-027：术语采用可回查的确认与变更生命周期

术语使用 `observed / proposed / confirmed / rejected / superseded` 状态。每个术语记录定义、包含与不包含的边界、别名 / 禁用说法、来源、影响和修订关系。

新业务术语、歧义术语和影响方案边界的术语必须由用户确认；项目已有权威词汇且无冲突时可记录为 `confirmed by source`。定义变化时保留旧定义并标记 superseded，创建新的当前定义，回查受影响流程、数据、契约和决定，并重新打开被推翻的决策树节点。

### D-028：默认不维护 ADR，design.log.md 是唯一设计事实源

dev-design 默认不创建或同步 ADR，也不把 ADR 作为 grilling、closure 或 panorama Gate。决定、理由、证据、替代关系和历史统一保存在 `design.log.md`。

只有用户明确要求，或仓库存在强制 ADR 的显式约定时，才从已确认 D-xxx 派生 ADR。派生 ADR 引用原 Round / D-xxx，Log 反向记录路径；跨任务可发现性优先通过文档索引解决。

### D-029：最终全景一次确认并使用 Log 内 Handoff

用户确认最终 panorama 时，同时授权 panorama 中点名的下一阶段，不再增加第二个 handoff Gate。确认结果必须先写入 `design.log.md`，再由 devflow 调用 Debug、Plan 或 Build。

Handoff 作为同一 Log 内的导航区块，只记录 From、To、Reason、Read、Preserve 和 Open，不承载新的设计事实。用户在确认时修改全景内容，必须先作为新 Round 入库并重新执行当前类型 closure，不能直接 handoff。

### D-030：design.log.md 采用单写者边界

`dev-design` 主协调会话是设计事实的唯一写入者，负责 Round、D-xxx、术语、决策树位置、panorama 和 Handoff。私有 playbook、仓库调查、竞品研究、Debug 及其它 agent / Skill 只返回结构化材料和证据，不直接修改设计事实。

devflow 只按 D-024 追加最小阶段流转记录；Plan、Build、Verify、Review 维护各自产物。任何会改变设计基线的发现都必须回流 `dev-design`，由其记录冲突、取得确认并更新 Log。

每次写入固定执行：读取最新文件 → 验证预期节点 / revision → 应用更新 → 重新读取验证 → 才能提出下一题或 handoff。禁止多个执行单元并行修改同一 Log。

### D-031：一项工程任务只绑定一份 design.log.md

首次进入 dev-design 时为工程任务确定唯一 `design.log.md` 精确路径；后续 compact 恢复、阶段 handoff 和流程回流都必须原样携带该路径。同一任务不得因会话或阶段变化自动创建第二份 Log，也不得按文件名、最近修改时间等模糊规则猜测当前 Log。

恢复路径的优先级是用户明确给出的路径，其次是当前 devflow / handoff 原样传入的活动路径。没有活动 Log 的新任务只创建一次；出现多个候选时必须让用户选择。任务确需拆分时，先在原 Log 记录拆分决定，再为子任务创建独立 Log 并记录双向关系。

### D-032：中断恢复只使用最新 Round 状态，不增加 revision

`design.log.md` 不增加数字 revision 或额外状态机。每道问题先完整写入 Round，再展示给用户；回答尚未完成一致性入库时保持「等待用户回答」，回答及其决定、术语和决策树影响写完后改为「已确认」或其它明确结果。

compact、换会话或中断后，通过 D-031 的精确路径读取 Log：最新 Round 仍在等待且能取得可靠回答时补记，无法取得回答时原样重问同一题；最新 Round 已确认时先检查四视图一致性。补记、重问或修复完成前不得进入下一节点。该规则属于 `grilling.md` 内部恢复细节，不增加 devflow 职责。

### D-033：改变 panorama 或 Preserve 的下游发现必须回流 dev-design

Plan、Build、Verify、Review 的新发现只要会改变已确认 panorama 或 Handoff Preserve，就必须携带同一 Log 精确路径回流 dev-design；不改变设计基线的局部实现选择由当前阶段自行处理。

回流方只提交发现、证据、与基线的冲突和可能影响，不直接写设计结论。dev-design 追加 Round，重新打开受影响节点及其依赖，重新执行 grilling、closure 和 panorama；旧结论保留并标记 superseded。用户重新确认后生成新 Handoff，并根据新结果选择目标阶段，不默认回到原阶段。

### D-034：同一任务执行期间沿用原 Log，任务结束后关闭

panorama 确认和 Handoff 不关闭 Log；同一任务执行期间发生设计变化时，按 D-033 回流原 Log 并追加历史，不改写旧 panorama。Land 成功、用户取消或任务明确终止后，记录结束原因与结果引用，Log 转为「已结束」。

已结束 Log 不再承载新的 bug、feat 或 refactor；后续工程任务创建新 `design.log.md` 并记录与旧 Log 的关系。已结束 Log 只允许不改变原设计结论的历史勘误。

### D-035：采用过程 Log、派生设计文档和完整下游追踪链

`design.log.md` 保存逐轮沟通、证据、术语、D-xxx、替代历史和确认记录，是设计决定的过程事实源。dev-design 在 closure 与 panorama 确认后，从同一 Log 生成类型专属设计文档，作为下游实施读取的当前设计基线；设计文档不能脱离 Log 独立修改。

完整追踪链为：

```text
design.log.md
→ dev-design 类型专属设计文档
→ Plan 任务映射
→ Build 实施回报
→ Verify 验证证据
```

稳定的设计义务 ID 产生在设计文档中，由 Plan、Build、Verify 共同引用；具体 ID 类型和状态仍待确认。设计变化必须先回流 dev-design 更新 Log、重新 closure / panorama，再更新设计文档和受影响的下游映射。

### D-036：追踪采用 Log ID → Design ID → 全部下游的两层契约

`design.log.md` 中形成稳定 Log ID，dev-design 消费 Log ID 生成设计文档；设计文档形成稳定 Design ID，Debug、Plan、Build、Verify、Review、Land 等所有后续阶段统一消费 Design ID，不让各下游阶段直接重新解释原始沟通记录。

Log ID 保存「为什么有这项设计输入」及其沟通、证据和决定来源；Design ID 保存「最终需要实现、调查、保持或验证什么」。Design ID 必须能够回查来源 Log ID，下游产物必须能够回查对应 Design ID。具体双向覆盖 Gate、ID 命名和状态仍待确认。

### D-037：Log ID 与 Design ID 必须双向覆盖

每个需要进入设计的 Log ID 必须被至少一个 Design ID 消费；确实不产生设计义务时必须记录不适用及理由，不能静默遗漏。每个 Design ID 必须引用至少一个来源 Log ID；无来源的设计内容必须退回 grilling，不能由 dev-design 擅自新增。

一个 Log ID 可以产生多个 Design ID，多个 Log ID 也可以共同收敛成一个 Design ID。dev-design 在设计文档末尾生成轻量 `Log ID ↔ Design ID` 覆盖视图作为正文引用汇总，不创建独立 Registry。所有下游只携带 Design ID，需要追溯时沿其来源回查 Log ID。

### D-038：ID 只使用 LOG-### 与 DES-### 两个任务内命名空间

新 `design.log.md` 模板中，所有需要由 dev-design 消费的当前 Log 项统一使用 `LOG-###`；类型通过 `kind` 字段表达。设计文档中供所有后续阶段消费的设计义务统一使用 `DES-###`，同样以 `kind` 表达调查、行为、结构、契约、数据、迁移、可观测或验证等语义，不再按语义创建大量 ID 前缀。

ID 只需在当前任务文档内唯一；跨任务引用使用文档路径加 ID。ID 一经发布不得重排、复用或改变原义；语义变化创建新 ID，并通过 `supersedes / supersededBy` 连接。Round 继续记录过程顺序，B/F/R 继续作为 playbook 节点键，不进入跨层 ID 契约。

D-025 的未来模板表达修订为「Log Item 当前视图」而非独立 `D-xxx` 决定索引；决定使用 `LOG-### kind: decision`。本设计 Log 已存在的 D-xxx 作为历史原样保留，不在讨论中途重编号。

### D-039：Bug 使用一份包含问题基线与修复基线的设计文档

Bug 问题 panorama 确认后，在同一份类型专属设计文档形成「问题基线」和第一组调查 / 保持 / 验证类 DES ID，供 Debug 消费。Debug 回报绑定 DES ID 的调查结果，由 dev-design 写成新 LOG ID；修复 panorama 确认后，在同一文档形成「修复基线」和新的修复类 DES ID，供 Plan 或 Build 及后续阶段消费。

两段 DES ID 在同一文档内连续且不可重编号。调查 DES ID 不因 Debug 完成而删除；Debug 产物记录完成结果。根因推翻旧义务时，旧 DES ID 标记 superseded 并指向新 ID。文档仅显示自然语言阶段，不引入 revision / digest 状态机，也不另建第二份 Bug 设计文档。

### D-040：Feat 设计文档覆盖完整设计，但只给独立设计义务分配 DES ID（经 D-041 术语修订）

Feat 设计文档固定覆盖来源与目标、现状与方案选择、端到端用户流程、业务规则与状态模型、系统边界与数据 / 契约、多领域时的跨域协作、适用的横切关注点、发布演进、验收验证和 LOG ↔ DES 追踪覆盖。

只有可以被 Plan 单独映射、由 Build 单独回报、并由 Verify 单独判断结果的行为、规则、契约、数据、迁移、可观测或验证义务才分配 DES ID。背景、设计理由、竞品资料和被否决方案只作为来源上下文；除非形成必须保持或验证的约束，否则不分配 DES ID。粒度按独立结果和失败语义拆分，不细到每个函数、字段或文件。

### D-041：dev-design-writing 仅作内容迁移源，并区分跨域协作与横切关注点

现有 dev-design-writing 不作为新流程的运行时嵌套 Skill。只迁移 LOG → 类型文档 → DES 的生成规则、基本写作原则、类型骨架、来源忠实性和覆盖自检；删除旧 Decision Packet、通用 Registry、revision / digest、DesignReviewVerdict、render 和重复确认状态机。详细方法移入 dev-design 自己的私有 references，主 `SKILL.md` 不固定加载。

多领域任务的「跨域协作」是核心设计：必须逐条闭合领域 / 数据所有者之间的触发与责任、交互方向、输入输出契约、数据所有权、状态一致性、权限边界、失败 / 重试 / 补偿、可观测和验证；单领域任务才能有证据地 N/A。

安全、隐私、可靠性、性能、可观测等另称「横切关注点」，先轻量覆盖，只有实际跨多个领域 / 技术层或形成共同策略时才详细展开。架构与 DDD 是由 LOG 内容和系统形态触发的可选 lens，只帮助解释边界，不替代跨域流程。现有 `cross-cutting-design.md` 只作为可抽取材料，不直接沿用其统一 placement 状态机。

### D-042：Refactor 设计文档以 Before / After / Invariants / Migration 为核心

Refactor 设计文档固定覆盖来源与边界、Before、必须保持、方案与质量判断、After、受影响的跨域协作、Before → After 迁移、清理退出、验证以及 LOG ↔ DES 覆盖。

每条必须保持的不变量，以及具有独立完成条件的结构变化、依赖反转、所有权迁移、兼容步骤、清理 Gate 或验证义务可以形成 DES ID。「代码更优雅」只有在已点名具体结构、期望质量和停止条件时才形成结构 DES ID；单纯文件移动、重命名或抽方法不是天然 DES ID。单域内部重排不强制加载 DDD 或架构 lens。

### D-043：三类设计文档统一采用图优先、关系驱动选图

设计文档先用一屏总图和关键子图表达全局关系、路径与变化，再用文字补充图无法表达的决定、契约和理由。流程 / 结构类 DES ID 必须能在图中定位，或明确说明不适合可视化的理由；图必须覆盖相关失败与恢复，不能只画 happy path。

流程与分支使用流程图，领域 / 组件边界、职责、依赖和数据所有权使用架构图，跨参与者调用顺序、返回、超时、重试或并发使用时序图。Bug 重点展示故障与修复前后流程；Feat 重点展示端到端流程、跨域关系和关键时序；Refactor 重点展示 Before / After 架构与迁移流程。状态图、数据流图或 ER 图只在对应关系承重时按需增加。

### D-044：设计文档默认以 ASCII 保存规范图，渲染产物不得成为第二事实源

类型专属设计文档中的规范性图默认使用 ASCII，与正文、LOG ID 和 DES ID 一同进入 Git。ASCII 图必须直接可读、可 diff、可由下游消费，不依赖特定 Markdown 渲染器；图过大时拆成一屏总图与场景子图。

Mermaid 不作为默认规范图源，只能在渲染阶段按需选用。HTML、SVG、PNG、Mermaid、D2 或其它渲染中间产物均属于派生展示，不得与 ASCII 并列维护为另一份设计事实；渲染结果若暴露出关系缺失，必须回到 ASCII 规范图和对应 DES ID 修正。

### D-045：渲染优先 HTML，Mermaid 仅作回退

设计文档需要视觉渲染时，首选产物是 HTML；只有 HTML 无法生成、交付环境无法承载或用户明确要求兼容 Markdown 图时，才回退为 Mermaid。Mermaid 不与 HTML 同时维护，也不因回退获得设计事实地位。

HTML 和 Mermaid 都必须从同一份 ASCII 规范图及其 DES ID 派生，保留相同节点、边界、顺序、失败路径和追踪关系。回退只允许降低视觉表现或交互能力，不得减少设计语义。

### D-046：HTML 渲染产物使用单文件交付

HTML 主渲染产物固定为一个 `.html` 文件，不拆分配套 CSS、SVG、图片或脚本文件，避免设计展示在归档、评审和传递时丢失附件。是否允许该单文件引用 CDN 或其它外部运行时依赖，尚未由本决定确认。

### D-047：HTML 单文件允许引用在线资源

HTML 主渲染不要求完全自包含或离线可用，可以引用在线 CSS、字体、脚本和其它展示资源。这里的「单文件」只约束本地交付物数量，不约束网络依赖数量。

在线资源只服务派生展示；其不可用、变更或失效不得改变 ASCII 规范图、DES ID 或设计语义。在线依赖是否必须锁定精确版本、记录来源和定义失败回退，留待后续决定。

### D-048：在线展示依赖不强制锁定或设置运行时回退提示

HTML 引用的在线 CSS、字体、脚本和其它展示资源不要求锁定精确版本、记录依赖清单或禁止浮动 URL；资源加载失败时，也不要求 HTML 自动切换或明确提示 Mermaid。

由此产生的视觉变化、暂时不可用或不可复现只影响派生展示，不进入设计事实契约。Mermaid 回退仅指生成 HTML 不合适或目标环境不承载 HTML 时，选择生成 Mermaid 的格式回退，不是 HTML 运行时的容灾机制。

### D-049：设计文档必须通过四项最小自检 Gate 才能请求确认

dev-design 将类型专属设计文档交给用户确认前，必须同时证明：相关类型决策树已闭合；所有应由设计消费的 LOG ID 均已映射；所有 DES ID 均能追溯到 LOG ID；关键图与正文表达的边界、流程、顺序和失败语义不存在冲突。

任一项失败都不得进入 Handoff 或请求用户用确认掩盖缺口，必须回到对应 grilling 节点补充设计事实并重新自检。自检只做一致性和覆盖检查，不另设评分、审美 Gate 或重型 Review 状态机。

### D-050：panorama 是设计文档的一屏总览，不生成独立 panorama.md

Bug、Feat、Refactor 的类型专属设计文档都在开头提供一屏 panorama，集中呈现目标、范围、关键图、主要 DES ID、风险和 Handoff 路线；正文随后展开类型专属细节。

不再生成或维护独立 `panorama.md`。HTML 只作为整份设计文档的派生渲染，panorama 是其中的首页 / 首屏。用户对 panorama 与正文组成的完整设计基线只做一次明确确认，避免摘要与正文分别确认后发生漂移。

### D-051：三种类型统一使用 design.md 与 design.html

Bug、Feat、Refactor 均使用 `design.md` 作为规范设计文档，使用 `design.html` 作为 HTML 主渲染；类型通过 `design.md` 元数据中的 `type: bug | feat | refactor` 表达，不进入文件名。

同一任务目录内只有一份当前规范设计文档和一份可重新生成的主渲染。类型差异由文档模板、决策树和 DES ID 内容表达，不通过不同文件名或额外目录制造分支。

### D-052：用户确认通过单条 Log Item 入库并在同一 Log 形成 Handoff

用户确认完整设计基线后，dev-design 只在 `design.log.md` 追加一条 `LOG-### kind: design-confirmation`，记录规范 `design.md` 路径、确认时所有当前有效 DES ID 和获授权的下一 Skill；随后在同一 Log 形成最小 Handoff 导航。

不创建 receipt、manifest 或独立确认文件，也不为确认逐条修改 DES ID 状态。Handoff 继续只承载 From、To、Reason、Read、Preserve 和 Open 等导航信息，不新增设计事实；下游以 `design.md` 路径和有效 DES ID 为消费入口。

### D-053：design.html 仅在用户明确要求时生成

dev-design 通过最小自检 Gate 后，默认直接用包含 ASCII 图的 `design.md` 请求用户确认，不自动生成 `design.html`，也不设置 render-choice 暂停。`design.html` 不是设计确认或 Handoff 的前置条件。

只有用户明确要求渲染时才生成或刷新 `design.html`；此时 HTML 是首选格式，无法交付 HTML 才回退 Mermaid。没有渲染请求时不创建占位 HTML，也不把“未渲染”视为缺口。

### D-054：暂不处理设计变化后的旧 HTML

当前版本不加入「`design.md` 变化即删除、标记或自动刷新 `design.html`」的规则。旧 HTML 可以继续存在，但不参与设计确认、最小自检 Gate 或下游 Handoff；任何阶段都只能以 `design.md` 和当前有效 DES ID 判断设计基线。

该问题保留为未来可重开项，不在本轮引入 stale 标记、source digest、render receipt 或历史 HTML 管理。

### D-055：按需 HTML 由 nocode:open-design 独立渲染

用户明确要求 HTML 时，dev-design 调用 `nocode:open-design`，以当前规范 `design.md` 作为唯一内容输入，并将结果导出 / 落位为同目录 `design.html`。dev-design 主干只保留这一条件 handoff，不复制 HTML、CSS、SVG、布局或 Open Design 工具细节。

Open Design 可以重新组织视觉层级和交互，但不得新增、删除或改写设计事实，且必须保留关键 DES ID 与设计关系。Open Design 不可用或无法交付 HTML 时，才按 D-045 / D-048 生成 Mermaid 格式回退。

### D-056：dev-design 不约束 HTML 的具体渲染技术

dev-design 协议不指定 inline SVG / CSS、D2、Graphviz、PlantUML、布局引擎、主题实现或其它前端技术；这些都由 `nocode:open-design` 在其职责内自主选择和演进。

dev-design 对渲染只保留四项边界：输入必须是当前 `design.md`；主输出落为同目录 `design.html`；关键 DES ID 和设计关系必须保留；渲染不得新增或改写设计事实。由此删除未确认的「绘图表示」和「布局后端」候选术语。

### D-057：dev-design 使用共享阶段协议与类型阶段协议的私有 references 结构

`skills/dev-design/SKILL.md` 只保留入口、按需读取顺序、硬约束和阶段路由。共享细节固定为 `references/grilling.md`、`writing.md`、`handoff.md`、`render.md`；Bug、Feat、Refactor 各自在类型目录维护 `questions.md`、`closure.md`、`document.md`。

执行时只读取当前阶段和当前类型需要的 reference。现有 `decision/SKILL.md`、`writing/SKILL.md` 不继续作为嵌套 Skill 或私有状态机；其中符合已确认决定的内容迁入上述 references，其余 Packet、revision、digest、verdict、receipt 和 render-choice 等旧协议删除。

### D-058：删除 dev-define，不保留兼容 Skill

实现合并时直接删除 `skills/dev-define/`，把插件内所有运行时路由、Skill handoff、说明和有效引用迁移到唯一公开入口 `dev-design`。不保留 deprecated redirect、别名 Skill 或只做转发的兼容目录。

旧 `dev-define` 中符合本设计的内容只迁移到 dev-design 私有 references；旧 Define 状态机、场景分级、独立产物和退出 Gate 不保留。历史文档中的事实引用可以作为历史存在，但不得继续指导运行时。

### D-059：devflow 使用无 references 的单文件五步骨架

`skills/devflow/` 只保留一个精简 `SKILL.md`，按固定五步运行：解析或创建活动 `design.log.md`；判断 `bug / feat / refactor`；调用 `dev-design`；读取同一 Log 的 Handoff 调用下一 Skill；接收明确回流，或在 Land / 取消 / 终止时结束活动 Log。

删除 8 阶段看板、Full / Standard / Fix / Mini 场景、devflow 自己的 task plan、阶段子流程、全局完成清单和 references。各阶段是否完成由对应 Skill 的自闭环 Gate 判断，devflow 不复制其方法或检查表。

### D-060：混合请求按单一主要结果定型，独立目标才拆 Log

一个用户请求只有一个主要可验收结果时，devflow 只确定一个主类型；为实现该结果所需的修补、兼容或结构调整属于设计方案内容，不另起类型。请求包含两个及以上可独立验收、可独立 Handoff 的目标时，才拆成多个任务 Log，并在原 Log 记录拆分关系。

类型继续按结果语义判定：违反请求前已成立的权威预期是 `bug`；新增对外可观察行为是 `feat`；只改变内部结构并保持约定行为是 `refactor`。不按提交文件、实现动作数量或用户文本中的类型关键词机械分类。

### D-061：类型判断证据优先，用户标签只作线索

devflow 最终按目标、既有权威预期和可观察行为证据判定 `bug / feat / refactor`。用户自称的类型是重要线索，但不单独构成分类证据；当事实已经足够时，devflow 直接给出类型和简短理由并入库。

证据不足以区分类型时，devflow 只追问一个当前最有区分力的问题，不加载 dev-design 的完整追问树。用户若不同意分类，应补充或修正目标、权威预期或行为证据；不能在三类语义不成立时仅用标签强行覆盖。

### D-062：类型结论使用 classification Log Item 并可在同 Log 追溯替代

首次判型写入 `LOG-### kind: classification`，至少记录 `type`、判型证据和被排除类型的理由。后续证据推翻分类时不覆盖或改写旧项，而是追加新的 classification Log Item，并通过 `supersedes` 指向旧项。

只要主要可验收目标没有改变，重新分类继续沿用原 `design.log.md`，重新打开新类型的相关决策树，并按 ID 不变性替代受影响的 DES ID。主要目标改变或出现可独立验收 / Handoff 的新目标时，才新建或拆分任务 Log。

### D-063：新任务使用统一工程设计目录和固定产物名

新任务默认创建 `docs/dev/{username}/{yymmdd}-{serial}-{topic}/`，其中规范过程文件是 `design.log.md`，规范设计文件是 `design.md`，用户明确要求渲染时才生成 `design.html`。

用户提供已有设计目录或精确 `design.log.md` 路径时优先沿用，不另建默认目录。路径约定写入 dev-design 自己的 `references/grilling.md`，Skill 运行时不跨层读取 model、rule 或 hook 文件。

### D-064：目录动态段确定后保持任务路径不变

`username` 优先使用用户或项目明确配置，无法唯一确定时才向用户追问一次；`yymmdd` 使用任务目录创建日；`serial` 扫描同一 username 当日已有目录并取下一个两位序号；`topic` 从主要可验收目标生成简短 kebab-case。

目录创建后即绑定该任务，同一任务重新分类、跨日恢复、设计回流或下游返工都不得重命名或迁移目录。只有拆分出的独立任务创建自己的新目录，并从新 Log 引用原任务 Log。

### D-065：design.log.md 使用六段固定结构

新任务的 `design.log.md` 固定按 Header、Current Log Items、Decision Tree、Terms、Handoff、Round Log 六段组织。前五段是从追加式 Round Log 同步维护的当前视图；Round Log 保存逐轮问题、回答、证据、决定和未决节点历史。

证据直接绑定对应 Log Item 或 Round，不建立独立 Evidence Registry。新任务不建立 D-xxx 决定索引；需要由设计消费的事实、决定、约束和分类全部进入 LOG-### 体系。本设计 Log 已有 D-xxx 仅作为历史保留。

### D-066：Header 与 Log Item 只保留最小字段且 LOG ID 永不删除

Header 只包含 `task / status / type / currentNode / createdAt / artifacts`。每个 Log Item 只包含 `kind / status / statement / sourceRounds / evidence / designDisposition / relations`；没有值的按需字段可写 `n/a`，不扩展 owner、priority、revision、digest 或 approval。

`designDisposition` 只能是 `required` 或 `n/a`，其中 `n/a` 必须说明理由。`relations` 按需记录 `supersedes / supersededBy / splitFrom / splitTo`。LOG ID 一经分配永不删除，即使条目 rejected 或 superseded 也保留，使 design.md 中的 sourceLogIds 始终可解析。

### D-067：Round 使用八段固定模板且每轮只有一个决策问题

每个 Round 固定包含 Background / Evidence、Question、Agent Recommendation + Reason、User Answer、Log Item Changes、Term Changes、Flow Impact、Next Node 八段；没有内容的段落写「无」，不能省略。

用户回答前，Round 先以 waiting 状态落盘问题、背景和推荐；回答后先补齐回答与变化，同步 Header、Log Items、Decision Tree、Terms 和 Handoff，再把 Round 关闭，最后才能提出下一题。每轮只向用户提出一个决策问题，事实调查和证据可以包含多条。

### D-068：Decision Tree 使用最小字段、六种状态和单 active 约束

Decision Tree 当前视图中每个适用节点只记录 `node / status / sourceLogIds / dependsOn / note`。状态限定为 `open / active / blocked / confirmed / n/a / superseded`，任一时刻最多一个 active，且 Header.currentNode 必须与 active 节点一致。

只有 `confirmed / n/a / superseded` 视为闭合；`n/a` 必须绑定不适用证据，`blocked` 必须点名未闭合依赖。动态分支只在触发后加入当前视图，不复制类型 questions.md 中尚未触发的整棵决策树。

### D-069：停止继续 grilling，进入实现

用户判断当前设计已经足够完整并授权开始实现。Round 76 提出的 Handoff 精确字段集不再继续单独追问；实现沿用已确认 D-029 的 `From / To / Reason / Read / Preserve / Open`，并按 D-052 通过 design-confirmation Log Item 关联 `design.md`、有效 DES ID 与下一 Skill，不增加未确认的新字段或状态机。

实现范围包括 devflow 薄编排、dev-define 删除、dev-design 主干与私有 references 重构、LOG → DES 契约、三类动态决策树 / 文档、按需 Open Design 渲染，以及受旧 revision / digest / Registry 契约影响的下游衔接更新。实现前先从本 Log 生成 `design.md`，随后按仓库要求验证并打包平台发布物。

## 当前工作模型

以下是根据已确认决定形成的当前模型，仍可在后续 grilling 中修订：

```text
devflow 判断 bug / feat / refactor
        ↓
创建或读取 design.log.md
        ↓
追问循环
  读取最新 Log
  → 调查环境可确认的事实
  → 找到决策树中的下一个未决节点
  → 提出一个问题，并给出推荐答案与理由
  → 等待用户回答
  → 记录问答、术语、决定和流程影响
  → 检查全部相关流程是否仍然一致
  → 入库完成后进入下一题
        ↓
决策树分支闭合 + 全部流程对齐
        ↓
从 design.log.md 生成最终全景
        ↓
用户确认
        ↓
进入 Debug 或 Plan / Build 等下游执行阶段
```

## 讨论记录

### Round 1：审视当前 devflow

**讨论**

当前 devflow 是强 Gate 的八阶段驾驶舱，包含 Define、Env、Design、Plan、Build、Verify、Review、Land，并按 Full / Standard / Fix / Mini 路由。

**用户判断**

**形成方向**

### Round 11：三种类型是否共用合并阶段（已确认）

**问题背景**

devflow 已确认只判断 `bug / feat / refactor`。Define 与 Design 当前朝合并方向重构，但三种任务是否都进入同一个合并阶段尚未确认。尤其 `bug` 在根因查明前不能可靠选择修复方案。

**本轮问题**

合并后的 Define / Design 是否应作为 `bug / feat / refactor` 的统一入口？如果统一，`bug` 是否只在这里把问题和流程问清楚，然后进入 Debug，待根因明确后再确定修复方案？

**agent 推荐**

三种类型共用同一个入口，但按类型采用不同的退出深度：

- `bug`：闭合预期行为、实际行为、复现路径、影响范围和修复验收；方案暂缓，进入 Debug。
- `feat`：闭合问题与全部流程，并确认解决方案后进入 Plan。
- `refactor`：闭合当前结构问题、行为不变量和目标结构后进入 Plan。

理由：统一入口能避免重新制造三套沟通协议；`bug` 延后方案选择则避免在没有根因证据时猜修复方式。

**本轮术语**

- **统一入口**：三种任务类型都先进入同一个合并后的 Define / Design 沟通过程；不代表三种类型执行完全相同的追问树。
- **退出深度**：某一任务类型离开该沟通过程前必须闭合到什么程度。

**状态**

用户接受 agent 推荐。已形成 D-008，并完成当前路线一致性更新。

### Round 12：Skill 保持薄主干

**用户决定**

合并后的 `SKILL.md` 只有主干，细节都放在子文件中，保证 Skill 精简。

**形成决定**

已形成 D-009。主文件不复制三种类型的完整追问树，也不堆叠 Log 模板和全部流程检查细节；它只负责把当前会话路由到正确的私有子文件，并验证子文件返回的阶段结果。

**流程影响**

- `bug / feat / refactor` 各自的追问树可独立演进，不膨胀主文件。
- Log 持久化协议与流程闭合协议可作为共享子文件，供三种类型复用。
- 子文件必须按需读取；如果每次无条件读取全部子文件，只是把行数移走，不能真正降低上下文负担。

**本轮术语**

- **主干**：所有任务类型都必须执行的稳定流程，包括类型入口、逐轮入库、子文件路由、最终全景和 Exit Gate。
- **子文件**：位于当前 Skill 私有目录内、由主 `SKILL.md` 按任务类型或当前步骤读取的细节协议。
- **按需读取**：只加载当前类型和当前步骤实际需要的子文件，不在入口一次性加载全部细节。

**状态**

已入库。下一项依赖最靠前的决定是合并后 Skill 的正式名称与对外入口。

### Round 13：合并后 Skill 的正式名称（已确认）

**问题背景**

Define 与 Design 已确定合并，但正式对外入口尚未命名。名称会影响 devflow handoff、模型触发语义、目录结构和后续兼容处理。

**本轮问题**

合并后的唯一对外 Skill 是否沿用 `dev-design`，并让现有 `dev-define` 退出主流程？

**agent 推荐**

沿用 `dev-design`：

- 最终产物是经过追问和方案对齐形成的设计全景，与 `design.log.md` 命名一致。
- `design` 是工程人员熟悉的公开概念；`Shape` 会引入新的领域术语。
- “先 grilling、再设计”应作为 `dev-design` 内部主干，而不必体现在 Skill 名称中。
- `dev-define` 不再作为独立阶段，避免重新形成双入口和职责重叠。

**本轮术语**

- **对外 Skill**：可由用户、devflow 或模型直接调用的注册 Skill。
- **私有子文件**：只由对外 Skill 在执行中读取，不独立注册或直接调用。

**状态**

用户接受 agent 推荐。已形成 D-010。

### Round 14：私有子文件的拆分方式（等待用户回答）

**问题背景**

已确认主 `SKILL.md` 只保留稳定主干。下一步需要决定私有子文件按什么边界拆分，确保每次只加载当前类型、当前步骤需要的内容。

**本轮问题**

是否按「共享循环 + 类型追问树 + 收敛 Gate」拆成以下私有子文件？

```text
skills/dev-design/
├── SKILL.md
└── references/
    ├── grilling.md
    ├── bug.md
    ├── feat.md
    ├── refactor.md
    ├── flow-closure.md
    └── panorama.md
```

**agent 推荐**

采用这套拆分：

- `grilling.md`：一次一问、事实自查、推荐答案、每轮写入 `design.log.md` 的共享循环。
- `bug.md` / `feat.md` / `refactor.md`：只保存各类型的决策树和类型专属完成条件；一次只读取当前类型。
- `flow-closure.md`：问题和方案接近收敛时才读取，检查流程、状态、验收和方案是否双向无孤儿。
- `panorama.md`：闭合检查通过后才读取，生成最终全景并取得一次确认。

主 `SKILL.md` 只保存类型入口、读取顺序、硬 Gate 和 handoff。这样既减少主文件内容，也减少单次实际加载的上下文。

**本轮术语**

- **共享循环**：三种任务都遵守的单轮 grilling 与入库顺序。
- **类型追问树**：只服务某一种任务类型的依赖问题树。
- **收敛 Gate**：追问临近结束时执行的流程闭合检查和最终全景确认。

**用户澄清问题**

`panorama.md` 里面具体展示什么？

**候选职责说明**

`panorama.md` 不是新的设计产物，也不保存本任务的内容。它是私有展示协议：只在 `flow-closure` 通过后读取，指导 agent 从 `design.log.md` 的已确认事实生成最终全景。

全景的共享骨架候选为：

1. 任务类型、目标、范围与非范围。
2. 已确认的角色、术语和关键决定。
3. 完整流程：触发、主路径、分支、状态变化、失败与恢复。
4. 解决方案：`feat / refactor` 展示选定方案、关键取舍、边界和契约；`bug` 在 Debug 前不猜修复方案。
5. 风险、约束和明确接受的剩余问题。
6. 流程 → 方案 → 验收 / 验证的对应关系。
7. 下一阶段及其输入：`bug → Debug`，`feat / refactor → Plan`。

展示协议必须遵守：不新增事实、不重做追问、不复制完整 Grill Log；发现缺口就退回 `grilling` / `flow-closure`，不能在全景中自行补齐。全景直接追加到同一份 `design.log.md`，用户确认后成为下游阶段读取的当前基线。

**状态**

用户认为共享 `panorama.md` 不够细致，且 `bug` 与 `feat` 的展示内容不同。Round 14 中「单一共享 panorama」的建议已否决；其余薄主干和按需读取原则保留。

### Round 15：按任务类型拆分追问、闭合与全景（已确认）

**用户判断**

最终全景需要细致，并且必须分类；`bug`、`feat`、`refactor` 不能共用同一套展示结构。

**修订后的候选结构**

```text
skills/dev-design/
├── SKILL.md
└── references/
    ├── grilling.md
    ├── bug/
    │   ├── questions.md
    │   ├── closure.md
    │   └── panorama.md
    ├── feat/
    │   ├── questions.md
    │   ├── closure.md
    │   └── panorama.md
    └── refactor/
        ├── questions.md
        ├── closure.md
        └── panorama.md
```

**按需读取顺序**

1. 所有类型先读取共享 `grilling.md`。
2. 只读取当前类型的 `questions.md` 进行追问。
3. 问题树看似完成时，只读取当前类型的 `closure.md` 做结构性闭合检查。
4. 闭合通过后，只读取当前类型的 `panorama.md` 生成最终全景。

**类型全景候选边界**

- `bug/panorama.md`：证明问题是什么、怎样稳定复现、影响在哪里、Debug 必须回答什么；根因未查明前不展示猜测性修复方案。

- `refactor/panorama.md`：展示当前结构证据、行为不变量、Before / After、迁移路径、兼容与回滚、结构改善的验证方法。

**流程影响**

- 共享 `flow-closure.md` 和共享 `panorama.md` 被类型目录内的专属文件替代。
- 主 `SKILL.md` 仍只负责路由，不包含三种类型的详细展示字段。
- 单次执行只加载一个类型的三个细节文件，不加载其它类型。

**状态**

用户接受类型目录结构，以及 `bug / feat / refactor` 三类全景的详细边界。已形成 D-011。

### Round 16：`questions.md` 是固定问卷还是动态决策树（已确认）

**问题背景**

三种类型已经分别拥有 `questions.md`。需要确认这些文件是按固定顺序逐题执行，还是只定义必须覆盖的决策节点和依赖，由回答动态展开后续分支。

**本轮问题**

`questions.md` 是否应设计为动态覆盖决策树，而不是固定问题清单？

**agent 推荐**

采用动态覆盖决策树：

- 文件定义必须闭合的决策域、节点依赖、分支触发条件和完成证据。
- 每轮只选择一个「依赖已满足且尚未闭合」的节点追问。
- 用户回答可能新增、删除或重排后续分支。
- 环境可确认的节点由 agent 调查并直接入库，不向用户提问。
- 节点只能以「已确认 / 有证据地不适用 / 被后续决定替代」闭合，不能因为 agent 认为不重要而跳过。

固定问卷无法根据回答深入新分支，也容易问已经能从代码查到的问题；动态树更符合 grilling 的逐分支追问方式。

**本轮术语**

- **覆盖节点**：必须被确认、用证据判定不适用或明确替代的一个问题域。
- **可提问节点**：前置依赖已经闭合、当前可以进入的下一个覆盖节点。
- **动态决策树**：节点和依赖稳定，但实际提问路径会根据事实和用户回答展开或收缩。

**状态**

用户选择动态覆盖决策树。已形成 D-012。

### Round 17：Bug 进入 Debug 前是否必须稳定复现（已确认）

**问题背景**

D-008 要求 Bug 在统一入口中闭合复现路径后进入 Debug。但生产环境间歇性故障、时序问题、第三方依赖异常等问题可能无法在本地稳定复现。如果把“稳定复现成功”设为硬 Gate，这类 Bug 会永远卡在设计沟通阶段。

**本轮问题**

Bug 进入 Debug 前，是否必须已经稳定复现成功？

**agent 推荐**

不强制“复现成功”，改为必须形成 **复现契约**，满足以下二选一：

1. **已复现**：有可重复执行的最小复现步骤，以及明确的失败证据。
2. **暂不可复现**：明确记录尝试过的环境、输入和结果，拥有生产证据或可靠现象描述，并定义 Debug 下一步需要补充的日志、指标、trace 或实验。

两条路径都必须先闭合预期行为、实际行为、影响范围和修复验收。不能仅凭“偶尔有问题”进入 Debug，也不能因为本地复现失败就拒绝真实生产故障。

**本轮术语**

- **稳定复现**：相同前置条件和操作可以重复触发同一可观察失败。
- **复现契约**：Bug 进入 Debug 前必须具备的证据基线；可以是已复现的失败用例，也可以是有边界、有证据、有下一步观测方案的暂不可复现记录。

**状态**

用户最终明确回答「接受」。已形成 D-013。

**中间输入及修正记录**

用户曾先发送「不推荐」，随后明确补充「是否接受？接受」。按最后的明确答复记录为接受；前一条输入保留在 Log 中并标记为被后续答复修正，不作为当前决定。

### Round 18：什么条件下才能把任务定义为 Bug（已确认）

**问题背景**

devflow 只判断 `bug / feat / refactor`。如果“实际行为不符合用户刚提出的新期望”也一律算 Bug，新增需求可能被误送进 Debug；反过来，如果只认代码当前行为，真实的契约回归又可能被误判为 Feat。

**本轮问题**

任务被定义为 `bug`，是否必须存在一个在本次请求之前已经成立的权威预期？

**agent 推荐**

必须有既有预期，来源可以是：

- 已批准的需求、设计或接口契约
- 自动化测试或明确验收标准
- 可证明的历史正常行为
- 已存在且经用户确认的业务规则

当前行为违反既有预期才是 Bug。若用户是在本次沟通中首次提出一种新的行为，而系统从未承诺过，则应分类为 `feat`，不能以 Bug 路径绕过方案设计。

当多个预期来源互相冲突时，不自动选择：把冲突和证据写入 `design.log.md`，由用户决定哪个预期有效，再继续分类。

**本轮术语**

- **既有预期**：在本次请求发生前已经成立、能够作为正确行为判据的要求或契约。
- **权威预期**：有来源证据且经当前沟通确认可作为验收基线的既有预期。
- **行为变更**：系统并未违反既有预期，但用户希望它以后采用新的行为；默认属于 `feat`。

**状态**

用户接受「既有权威预期」判据。已形成 D-014。

### Round 19：Debug 后是否回到 dev-design 完成修复设计（已确认）

**问题背景**

Bug 在第一次进入 `dev-design` 时只能闭合问题、复现契约、影响范围和修复验收，不能在根因未知时猜修复方案。Debug 找到根因后，仍需决定由谁把根因转化为修复方案，并检查修复对其它流程、契约和回归面的影响。

**本轮问题**

Debug 找到根因后，是否必须回到同一份 `dev-design` / `design.log.md`，完成修复方案与流程对齐，再进入 Plan 或 Build？

**agent 推荐**

采用 Bug 双段设计：

```text
dev-design（问题段）
→ Bug 问题全景
→ Debug
→ dev-design（修复段，续写同一 design.log.md）
→ Bug 修复全景
→ Plan
→ Build
```

理由：

- 问题段不在缺少根因证据时猜方案。
- Debug 只负责证明根因，不独自决定跨流程、契约或数据边界的产品与架构取舍。
- 修复段基于根因证据，只追问由根因新暴露的决策，并重新检查修复方案是否覆盖原复现路径、失败路径和回归路径。
- 两段使用同一份 `design.log.md`，不创建第二份事实源。

简单到无需独立 Plan 的修复是否允许从修复全景直接进入 Build，可在后续单独决定；本轮只决定是否回到 `dev-design` 完成修复设计。

**本轮术语**

- **问题段**：Debug 前的 Bug grilling，产出问题、复现契约、影响和验收基线。
- **修复段**：Debug 证明根因后恢复的 Bug grilling，产出修复方案、影响对齐和回归验证设计。
- **Bug 双段设计**：问题定义与修复设计被 Debug 证据隔开的两段 `dev-design`，共用同一份 Log。

**状态**

用户接受 Bug 双段设计。已形成 D-015。

### Round 20：Bug 修复段后是否必须进入 Plan（已确认）

**问题背景**

Bug 修复段已经拥有根因证据、修复方案和回归验证设计。需要决定所有 Bug 是否一律再进入 Plan，还是由修复方案的实际结构决定直接 Build 或先 Plan。devflow 本身已确认只判断任务类型，不承担复杂度分类。

**本轮问题**

Bug 修复全景确认后，是否允许单一闭环修复直接进入 Build，而多切片修复才进入 Plan？

**agent 推荐**

条件路由，不使用 Mini / Standard 等复杂度标签：

**直接 Build** 必须同时满足：

- 只有一个可独立验证的修复切片。
- 不需要安排多个实现步骤的依赖顺序。
- 不涉及数据迁移、公开契约变化或新旧方案共存。
- 一个 red-green 回路可以证明修复并覆盖回归。

**必须 Plan** 命中任一即可：

- 存在两个及以上需要分别验证的实施切片。
- 切片之间有依赖、迁移或 rollout 顺序。
- 涉及跨模块契约、数据迁移、兼容期或回滚检查点。
- 修复需要多个测试层或人工检查点协同。

路由判断及证据写入 Bug 修复全景，由 devflow 按结果 handoff；devflow 不重新判断复杂度。

**本轮术语**

- **单一闭环修复**：能在一个独立 red-green 切片内完成、验证并交付的修复。
- **多切片修复**：需要两个及以上独立验证单元，或存在依赖、迁移、兼容、rollout 顺序的修复。
- **条件路由**：不增加新的任务类型，由当前阶段依据产物结构决定下一阶段。

**状态**

用户接受单一闭环直达 Build、多切片进入 Plan 的条件路由。已形成 D-016。

### Round 21：Bug 动态覆盖决策树（已确认）

**问题背景**

Bug 已确认使用问题段 → Debug → 修复段的双段设计。现在需要确定 `bug/questions.md` 必须覆盖的节点、依赖和条件分支。

**本轮问题**

`bug/questions.md` 是否采用下面的双段动态覆盖决策树？

**agent 推荐**

```text
问题段
B0 权威预期与类型 Gate
 ↓
B1 预期行为 vs 实际行为
 ↓
B2 发生上下文与复现契约
 ├─ 已复现 → 最小失败证据
 └─ 暂不可复现 → 证据边界 + 观测计划
 ↓
B3 实际流程 vs 预期流程
 ↓
B4 影响面与风险分支
 ↓
B5 证据、矛盾与已排除项
 ↓
B6 修复验收与回归边界
 ↓
B7 Debug 调查契约
 ↓
Bug 问题全景 → Debug

修复段
B8 根因主张与证据校验
 ↓
B9 修复约束与真实候选方案
 ↓
B10 选定修复及流程影响传播
 ↓
B11 回归、观测、兼容与回滚设计
 ↓
B12 单一闭环 / 多切片路由判定
 ↓
Bug 修复全景 → Build 或 Plan
```

节点要求：

- **B0**：找到既有权威预期；不存在则转为 `feat`，来源冲突则用户拍板。
- **B1**：用同一前置条件描述 expected / actual，差异必须可观察。
- **B2**：形成 D-013 的复现契约；记录环境、输入、角色、状态、频率和对照场景。
- **B3**：逐步重建实际流程和预期流程，标出已知分歧点或尚未定位的分歧区间。
- **B4**：覆盖用户、业务、数据、安全、资金、运维和外部依赖；命中高风险时展开隔离、止损或数据保护分支。
- **B5**：事实附证据，假设明确标注；代码、日志、测试、用户描述冲突时不能静默选边。
- **B6**：原复现路径、边界场景、失败恢复和明确不受影响路径都要进入验收。
- **B7**：只定义 Debug 要证明的问题、调查起点、必须保留的证据和完成条件，不猜根因。
- **B8**：Debug 返回的根因必须同时解释现象、复现条件和证据；只能解释部分现象时继续 Debug。
- **B9**：候选修复必须在机制上真实不同；无真实替代时记录为什么只有一个可行方案，不制造伪选项。
- **B10**：把修复传播到调用方、数据、状态、错误语义和相关流程，检查是否引入新的行为变更。
- **B11**：定义回归测试、生产观测、兼容策略、失败回滚和旧补丁清理条件。
- **B12**：按 D-016 的证据判定直达 Build 或进入 Plan。

条件分支至少包括：

- 暂不可复现 → 观测 / instrumentation 分支。
- 预期来源冲突 → 权威预期决策分支。
- 安全、资金、数据损坏 → 止损与敏感风险分支。
- 外部依赖 → 外部契约与降级分支。
- 时序、并发、幂等 → 状态与重放分支。
- 数据或公开契约变化 → 迁移、兼容与 Plan 分支。

**本轮术语**

- **Debug 调查契约**：问题段交给 Debug 的明确调查问题、证据基线和完成条件。
- **根因主张**：Debug 对导致现象的机制性解释；必须有证据且能解释全部已知现象。
- **影响传播**：把候选修复对调用方、数据、状态、失败语义和其它流程的影响逐项展开。

**状态**

用户接受 Bug 双段动态覆盖决策树。已形成 D-017。

### Round 22：Feat 动态覆盖决策树（等待用户回答）

**问题背景**

Feat 需要从用户提出的功能形式向下追到真实结果，再把全部用户、业务和系统流程映射到选定方案。D-008 已确认 Feat 闭合问题与方案后进入 Plan。

**本轮问题**

`feat/questions.md` 是否采用下面的动态覆盖决策树？

**agent 推荐**

```text
F0 真实结果与类型 Gate
 ↓
F1 用户、角色与权限边界
 ↓
F2 当前流程、问题证据与替代做法
 ↓
F3 范围、非范围与硬约束
 ↓
F4 领域术语、实体、关系与数据所有权
 ↓
F5 端到端用户流程树
 ↓
F6 业务规则、状态机与边界条件
 ↓
F7 系统流程、外部依赖与失败恢复
 ↓
F8 非功能与敏感风险约束

F9 现有系统承接点与冲突
 ↓
F10 真实候选方案与取舍

F11 选定方案的边界、契约与数据流

Feat 全景 → Plan
```

节点要求：

- **F0**：追问用户真正要改变的结果，不把用户提出的实现形式直接当目标；已有行为违反既有权威预期则转 `bug`，仅改变内部结构且行为不变则转 `refactor`。

- **F3**：明确本次范围、非范围、必须保持的旧行为、时间/平台/法规等硬约束；范围变化必须写入 Log。
- **F4**：记录沟通中出现的领域术语，澄清实体、关系、身份、生命周期和数据所有者；歧义术语不得带入后续方案。
- **F5**：逐入口展开 happy path、替代路径、空状态、首次使用、重复操作、中断恢复和角色差异。
- **F6**：把每条流程中的条件、计算、状态迁移、并发、幂等、时间和边界规则显式化。
- **F7**：展开前端、后端、任务、回调和第三方依赖的数据与控制流；每个失败点都要有错误表现、恢复或明确接受。

- **F9**：读取已有实现、测试、文档和已批准决策；记录可复用点、技术约束和冲突，不重复询问仓库事实。
- **F10**：比较机制上真实不同的候选方案；无真实替代时记录单一可行方案的约束证据，不制造伪方案。
- **F11**：确定模块职责、接口契约、数据所有权、状态变化、失败语义和 enforcement point，并映射回 F5–F8。
- **F12**：闭合数据迁移、旧客户端/旧数据兼容、feature flag、灰度、生产观测、回滚和清理条件。
- **F13**：要求每条用户/系统流程都有规则、方案承接、验收和证据方法；每个方案组件也必须有需求来源，双向无孤儿。

条件分支至少包括：

- 多角色或权限 → 权限矩阵与越权路径。

- 零停机要求 → 共存状态、切流和生产观测。
- 性能敏感 → 基线、benchmark 和退化预算。

- **Characterization test**：记录当前既有行为、用于证明重构没有无意改变行为的测试。

### Round 30：代码优雅性可以独立触发 Refactor（已确认）

**用户判断**

不能把「代码看起来不优雅」排除在重构理由之外；代码不优雅可以进行重构。

**修订后的 R1**

R1 从「当前结构痛点与证据」改为「当前代码评价与重构动机」，允许两类合法入口：

1. **结构 / 工程问题**：变更扩散、循环依赖、重复逻辑、测试困难、故障历史、构建或性能问题等。
2. **设计质量 / 优雅性改进**：命名不能表达意图、控制流绕、抽象泄漏、职责不内聚、重复但尚未造成事故、不必要复杂、结构不对称或与项目语言不一致。

优雅性改进不要求提供事故、性能或工期等量化证据，但仍需：

- 点名具体代码或结构，而不是泛称「整体不优雅」。
- 说明希望改善的设计性质，例如可读性、内聚性、对称性、意图表达、简单性或一致性。
- 锁定行为不变量，避免借重构之名静默改变功能。
- 明确范围与停止条件，避免无限美化。

R6 的改善指标也相应放宽：可以是可验证的结构指标，也可以是经用户确认的设计质量判据；不强制所有优雅性改进数字化。

**本轮术语**

- **优雅性**：代码能以较低认知负担表达意图，职责内聚、结构简单一致、抽象与问题匹配。它允许包含专业判断，不要求全部量化。
- **设计质量判据**：用于比较重构前后的可读性、内聚性、对称性、简单性、一致性等判断标准。
- **无限美化**：没有明确范围、行为不变量和停止条件，持续扩大重构范围的行为。

**其余节点**

R0、R2–R5、R7–R13 及条件分支保持 Round 29 的设计不变。

**状态**

用户接受修订后的 R0–R13 Refactor 动态覆盖决策树。已形成 D-023。

### Round 31：devflow 保留哪些最小编排职责（已确认）

**问题背景**

D-001 已确认 devflow 只判断 `bug / feat / refactor` 三种类型；同时 devflow 仍被定位为编排层。需要明确它是否继续复制阶段 sub-steps、维护完整全局计划和逐 Gate 确认，还是只保留最小路由循环。

**本轮问题**

devflow 是否只保留下面四项职责？

1. 判断 `bug / feat / refactor`。
2. 根据类型和当前阶段结果选择下一 Skill。
3. 把 `design.log.md`、阶段产物和用户决定原样传给下一阶段。
4. 处理明确回流，例如 Bug `dev-design → Debug → dev-design`、Verify 失败回 Build。

**agent 推荐**

采用薄路由循环，并从 devflow 删除：

- 八阶段总览中的重复 sub-steps。
- 每阶段完整 Gate 细节。
- 为全部阶段预创建的平台 plan / task。
- 每阶段完成后再次展开下一阶段内部步骤。
- Mini / Standard / Full / Fix 场景矩阵。

阶段 Skill 自己负责内部计划、全景、用户确认、完成证据和失败返回。devflow 只识别统一的最小阶段结果：完成、阻塞、回流目标和下一阶段，不定义新的大型 schema。

为了防止 compact 后丢失位置，devflow 每次 handoff 只在 `design.log.md` 追加一条阶段流转记录，不复制阶段内容：

```text
<时间> <from> → <to>
原因：<已确认决定或 Gate 结果>
产物：<现有文件 / 证据引用>
```

**本轮术语**

- **薄路由循环**：分类、调用、接收结果、选择下一阶段和处理回流的最小编排循环。
- **阶段流转记录**：只记录 from / to、原因和产物引用的持久化导航信息，不复制阶段事实。
- **阶段结果**：阶段 Skill 完成时返回的完成 / 阻塞 / 回流 / 下一阶段信息；具体内容由阶段产物承载。

**状态**

用户接受四项最小职责和薄路由循环。已形成 D-024。

### Round 32：design.log.md 的固定记录协议（已确认）

**问题背景**

D-005 已确认每轮沟通必须先入库。仅追加问答历史虽然可审计，但 compact 或换会话后需要重放全部历史才能还原当前决定；只维护当前摘要又会丢失决定演进。因此需要确认 Log 是否同时维护当前真相和追加历史。

**本轮问题**

`design.log.md` 是否固定维护下面四个同步视图？

1. **当前决定索引**：D-xxx，保存当前有效决定及 superseded 关系。
2. **当前术语表**：术语、定义、状态、首次出现和后续修订。
3. **当前决策树位置**：已闭合节点、当前节点、被回答展开的后续分支。
4. **Round Log**：每轮问答与事实演进的追加历史。

**agent 推荐**

采用四视图。每次用户回答后，必须在提出下一题前完成：

```text
追加本轮 Round
→ 新增 / 修订 D-xxx
→ 更新本轮出现的术语
→ 更新决策树当前位置与未决分支
→ 检查四处一致
→ 才能提出下一题
```

Round 使用固定 Markdown 最小模板：

```markdown
### Round N：<覆盖节点与主题>

**节点与状态**
<type/node-id；waiting / confirmed / n/a / superseded>

**问题背景与已知事实**
<只写影响本题的上下文；事实附来源>

**本轮问题**
<一次一个决策问题>

**agent 推荐及理由**
<推荐答案 + 取舍>

**用户回答**
<原意；修正输入要保留前后关系>

**本轮术语**
<新术语、歧义和定义状态>

**形成决定与流程影响**
<D-xxx；影响哪些流程、节点和下游产物>

**尚未解决 / 下一可提问节点**
<未决分支及依赖>
```

没有内容的字段可以写「无」，不能删除字段导致恢复时无法区分「没有」与「漏记」。阶段流转记录使用 D-024 的简短格式，不强行套完整问答模板。

**本轮术语**

- **当前真相**：从已确认决定、术语和决策树状态汇总出的当前有效设计，不等于最近一轮文本。
- **追加历史**：不覆盖旧 Round 的演进记录；新决定通过 superseded 关系修订旧决定。
- **四视图一致**：决定索引、术语表、决策树状态和 Round Log 对同一事实没有未解释冲突。

**状态**

用户接受四视图和固定 Round 模板。已形成 D-025。

### Round 33：事实证据的最小记录粒度（已确认）

**问题背景**

grilling 要求环境能查到的事实由 agent 自行调查并入库。需要确定不同事实类型的最小证据格式。只记 `path:line` 不够稳定：行号会随修改漂移；只记文件名又无法复核具体结论。

**本轮问题**

是否按来源类型采用下面的最小证据规则？

**agent 推荐**

1. **仓库代码事实**

   ```text
   git commit / scanBase
   path
   symbol、配置键或稳定 section
   读取当时的 line（可得时）
   支持的具体结论
   ```

   `commit + path + symbol` 是耐漂移定位；`line` 是读取时的快速入口，不单独作为唯一锚点。

2. **命令与运行结果**

   ```text
   命令
   workdir / 环境
   执行时间
   与结论相关的输出摘要
   exit code
   ```

3. **项目内部文档**

   ```text
   path
   heading / anchor
   git commit 或文件更新时间（可确认时）
   支持的具体结论
   ```

4. **用户意图与决定**

   ```text
   design.log.md Round N
   对应 D-xxx（形成决定后）
   ```

5. **联网来源**

   遵守 D-021：URL、发布 / 更新时间、本轮访问时间、支持的具体结论。

6. **内部知识库**

   遵守 D-021 / D-022：明确内部数据源、内部数据源时间或「运行时未提供」、未联网核验状态、支持的候选方案。

7. **截图、日志或外部附件**

   ```text
   文件 / artifact 路径或稳定 ID
   生成 / 获取时间
   环境或场景
   支持的具体结论
   ```

所有来源都必须说明“它支持哪条结论”，不能只堆链接或文件路径。事实被后续 commit、命令或用户决定推翻时，旧记录保留并标记 superseded。

**本轮术语**

- **scanBase**：本轮仓库调查所基于的 Git commit。
- **稳定锚点**：在后续编辑中比行号更不易漂移的 symbol、配置键、heading 或显式 anchor。
- **证据绑定**：来源必须点名它支持的结论，避免来源清单与设计断开。

**状态**

用户接受按来源类型记录事实证据并绑定具体结论。已形成 D-026。

### Round 34：术语的确认与变更生命周期（已确认）

**问题背景**

D-006 要求沟通中使用的领域名词进入 Log。需要确定术语何时算确认，以及术语修改后如何回查已经依赖该定义的流程和决定。

**本轮问题**

术语是否采用下面的状态与变更协议？

**agent 推荐**

术语状态：

- `observed`：首次出现，含义尚未判断是否清楚。
- `proposed`：agent 或用户提出了候选定义，尚未确认。
- `confirmed`：定义和边界已由用户确认，或有权威项目来源且不存在冲突。
- `rejected`：候选术语或定义被明确否决。
- `superseded`：曾经有效，后来被新定义或新术语替代。

每个术语最少记录：

```markdown
### <Term>

- 状态：observed | proposed | confirmed | rejected | superseded
- 定义：它是什么
- 边界：包含什么、不包含什么
- 别名 / 禁用说法：同义词、易混词、后续不再使用的模糊词
- 来源：Round、D-xxx、代码或文档证据
- 影响：使用该术语的角色、流程、数据、契约和决定
- 修订：被哪个 Round / 新术语替代
```

确认规则：

- 新业务术语、歧义术语和边界会影响方案的术语必须由用户确认。
- 项目已有权威词汇且代码 / 文档无冲突时，可标记 `confirmed by source`，不重复询问用户，但必须记录来源。
- 通用技术术语按标准含义使用时可直接记录；当前项目使用了非标准含义则必须追问。

变更规则：

1. 不直接覆盖旧定义；旧条目标记 `superseded`。
2. 新定义生成新的当前条目并引用旧条目。
3. 根据旧条目的「影响」字段，回查并更新相关流程、状态、数据、契约和 D-xxx。
4. 被定义变化推翻的决策树节点重新打开，不继续沿旧含义推进。
5. Round Log 保留用户为什么修改术语及其影响。

**本轮术语**

- **confirmed by source**：已有权威项目来源且没有冲突，因此无需重复向用户确认的术语状态来源。
- **术语影响回查**：定义变化后，检查所有使用该术语的流程、数据和决定是否仍成立。
- **禁用说法**：已确认会造成歧义、后续沟通不再使用的词或表达。

**状态**

用户接受术语状态、确认和影响回查协议。已形成 D-027。

### Round 35：重要设计决定何时同步为 ADR（等待用户回答）

**问题背景**

所有决定已经通过 D-xxx 和 Round Log 持久化，但部分架构决定还需要让未来不参与本轮会话的人理解「为什么这样选」。需要确定何时创建独立 ADR，同时避免 Log 与 ADR 成为漂移的双事实源。

**本轮问题**

满足 ADR 条件的决定，是否在用户确认该决定的同一轮立即同步 ADR，而不是等最终全景后批量补写？

**agent 推荐**

采用「Log 全量记录，ADR 条件同步」：

- 每个决定无条件进入 `design.log.md` 的 D-xxx。
- 只有同时满足以下三项才创建 / 更新 ADR：
  1. 以后改变成本高。
  2. 不记录背景，未来读者会觉得这个选择意外或难以理解。
  3. 存在真实替代方案，并做了明确取舍。
- 决定被用户确认的同一轮，先更新 Log，再写 ADR；两者成功后才能进入下一题。
- ADR 引用 `design.log.md` 的 Round 和 D-xxx；Log 反向引用 ADR 路径。
- 后续决定变化时，旧 D-xxx 和旧 ADR 都标记 superseded，新 ADR 引用被替代项，不静默重写历史。
- 不满足 ADR 条件的决定只留在 Log，不制造 ADR 数量膨胀。

ADR 只保存长期有效的背景、候选、决定、理由和后果，不复制完整问答、术语表或流程全景。

**本轮术语**

- **ADR 条件同步**：决定一旦确认且满足 ADR 三条件，就在同一轮同步创建或更新 ADR。
- **双向引用**：Log 点名 ADR，ADR 点名形成它的 Round 与 D-xxx。
- **双事实源漂移**：Log 与 ADR 对同一决定保存了互相冲突的当前结论。

**状态**

用户追问「是否真的需要 ADR」。原推荐暂不确认，进入 Round 36 重新评估。

### Round 36：是否默认维护独立 ADR（已确认）

**用户问题**

这套流程是否需要 ADR？

**agent 重新评估**

默认不需要。当前 `design.log.md` 已经包含决定索引 D-xxx、候选与理由、证据、术语、影响、superseded 历史和最终全景；再同步 ADR 会复制同一决定，增加双事实源漂移和每轮写入成本，与本轮「精简 Skill、单一 Log 防漂移」的目标相冲突。

**修订后的 agent 推荐**

- `design.log.md` 是默认且唯一的设计决定事实源。
- dev-design 不自动创建 ADR，也不把 ADR 作为 grilling 或全景 Gate。
- 只有用户明确要求，或当前仓库有必须维护 ADR 的显式约定时，才从已确认 D-xxx 派生 ADR。
- 派生 ADR 时引用原 Round / D-xxx，Log 反向记录 ADR 路径；ADR 不反过来成为本轮设计的主事实源。
- 需要提升跨任务可发现性时，优先通过设计文档索引链接 `design.log.md`，不靠复制内容解决。

**取舍**

- 放弃默认 ADR，降低长期架构决定的独立摘要能力。
- 保留完整 Log 和最终全景，仍能解释决定；真正需要独立传播时再显式派生 ADR。

**本轮术语**

- **派生 ADR**：按明确需要从已确认 D-xxx 生成的独立摘要，不是默认同步事实源。
- **设计决定事实源**：判定当前决定、理由和替代关系时应读取的权威载体；默认是 `design.log.md`。

**状态**

用户确认默认不维护 ADR，仅保留用户明确要求或仓库强制时的派生能力。已形成 D-028。

### Round 37：最终全景确认与下阶段 handoff 是否合并（已确认）

**问题背景**

三类 panorama 都会从 `design.log.md` 生成最终全景。需要决定用户确认全景后，是否还要单独确认 handoff，及下游如何恢复准确上下文而不创建 `shapeReceipt` 等第二对象。

**本轮问题**

最终全景的确认是否同时授权进入全景中已写明的下一阶段，并在同一份 Log 追加一个简短 Handoff 区块？

**agent 推荐**

采用一次确认：

1. panorama 完整展示当前结论、风险、验证和明确的下一阶段。
2. 用户确认 panorama，即同时确认其中的下一阶段；不再新增第二个 handoff Gate。
3. 主会话先把确认结果和 Handoff 区块写入 `design.log.md`。
4. devflow 读取 Handoff 区块并调用目标 Skill。

Handoff 区块不是新的事实对象，只是同一 Log 中的导航索引：

```markdown
## Handoff

- From：dev-design / <type + phase>
- To：Debug | Plan | Build
- Reason：引用 D-xxx 与 closure 结果
- Read：design.log.md 的 panorama anchor 与关键证据
- Preserve：不得改变的范围、决定、术语、契约和行为不变量
- Open：允许由下一阶段回答的问题；无则写「无」
```

类型差异：

- Bug 问题全景确认 → Debug；Read 包含复现契约、证据与 Debug 调查契约。
- Bug 修复全景确认 → 按 D-016 到 Build 或 Plan；Read 包含根因证据、修复方案和回归设计。
- Feat 全景确认 → Plan；Read 包含完整流程、方案边界和验收闭合。
- Refactor 全景确认 → Plan；Read 包含 Before / After、行为不变量、迁移与验证。

如果用户在确认时修改了全景内容，先把修改作为新 Round 入库并重跑当前类型 closure；不能一边修改一边直接 handoff。

**本轮术语**

- **Handoff 区块**：位于同一 `design.log.md` 内的下阶段导航信息，不承载新的设计事实。
- **一次确认**：用户确认最终全景时同时授权全景中点名的下一阶段，不再重复询问。
- **Preserve**：下游阶段不可自行改变的已确认范围、决定、术语、契约和行为不变量。

**状态**

用户接受一次确认与 Log 内 Handoff 区块。已形成 D-029。

### Round 38：design.log.md 的单写者边界（已确认）

**问题背景**

主 `SKILL.md` 会读取私有 playbook，grilling 还可能调用仓库调查、竞品研究或 Debug。如果多个子流程直接写同一 Log，容易发生覆盖、顺序不确定、术语未经确认就进入当前真相等问题。

**本轮问题**

`design.log.md` 的设计事实是否只允许 dev-design 主协调会话写入，私有子文件、research、Debug 和其它执行单元只返回材料？

**agent 推荐**

采用单写者：

- `dev-design` 主协调会话是设计事实的唯一写入者，负责 Round、D-xxx、术语、决策树位置、panorama 和 Handoff。
- `questions.md / closure.md / panorama.md / grilling.md` 是私有执行指南，不是独立 writer。
- 仓库调查、竞品研究、Debug 或其它 agent / Skill 返回结构化材料和证据，由主协调会话核对后写入 Log。
- 外部材料与现有决定冲突时，主协调会话先记录冲突并追问，不能由材料生产者直接更新当前真相。
- devflow 仅按 D-024 追加最小阶段流转记录，不修改设计决定、术语或 panorama。
- Plan、Build、Verify、Review 写自己的产物；需要修改设计基线时，通过回流重新进入 dev-design，由 dev-design 写 Log。

写入顺序固定为：读取最新文件 → 验证预期当前节点 / revision → 应用本轮更新 → 重新读取验证 → 才输出下一题或 handoff。禁止并行写入。

**本轮术语**

- **单写者**：任一时刻只有 dev-design 主协调会话可以修改设计事实。
- **材料生产者**：research、Debug、仓库调查或其它执行单元；只返回证据，不拥有当前真相。
- **设计基线**：已确认决定、术语、流程、方案和 panorama 的当前有效集合。

**状态**

### Round 52：图的源码载体与可维护性（部分确认，继续追问渲染方案）

**agent 推荐**

采用 Mermaid-first：

- Mermaid 源码直接放在类型专属设计文档中，与正文和 DES ID 一起进入 Git；不另建不可追溯的图事实源。
- `flowchart` 表达流程、分支、架构 / 领域关系和数据流；`sequenceDiagram` 表达调用时序；`stateDiagram-v2` 表达状态生命周期；`erDiagram` 只在数据关系承重时使用。

- ASCII 只用于几步即可读清的局部关系，或目标 Markdown 环境明确不支持 Mermaid 时的降级；不能同时维护 Mermaid 与 ASCII 两份等价规范图。
- SVG / PNG、Open Design 页面等都是从 Markdown 图源生成的派生展示，不允许反向成为设计事实源。
- 图过大时优先拆成总图 + 场景子图，不通过缩小字体或堆叠线条解决。
- Handoff 前对 Mermaid 做可用的语法 / 渲染检查；当前环境没有渲染器时，明确标记「源码已自检、未渲染验证」，不能伪称通过。

**agent 复核与修订建议**

- 规范性图源确定为设计 Markdown 中的 ASCII；它是唯一图事实源。
- HTML 适合作为渲染结果的容器，但 HTML 本身不是图语言。优雅、可交互的图形应主要由页面内联 SVG + CSS 表达；HTML 负责排版、导航、图文组合、DES ID 定位和交互。

- Mermaid 保留为环境已有支持时的可选后端，不再承担默认渲染职责。
- 无论使用哪个后端，渲染节点必须保留相关 DES ID；渲染器不能新增、删除或改写设计关系。

## 当前术语

### devflow

工程任务的薄编排层。当前已确认的首要职责是判断任务属于 `bug / feat / refactor`；其余编排边界待继续讨论。

### bug

现有行为与预期行为不一致的工程任务。具体默认路线和追问树待定义。

### feat

增加新能力或新行为的工程任务。具体默认路线和追问树待定义。

### refactor

在保持约定行为不变量的前提下改变内部结构的工程任务。具体默认路线和追问树待定义。

### grilling

沿决策树持续追问，逐个消解依赖决策，直到共同理解形成。事实由 agent 调查，决策由用户拍板。

### 全景

在追问闭合、流程对齐后生成的整体视图，集中展示问题、流程、方案、风险、验证和后续执行路线。全景不是第一步。

### 入库

在当前讨论中，指把每轮沟通形成的问题、回答、术语、事实、决定、流程影响和未决分支写入 `design.log.md`。是否要求每轮创建 Git commit 尚未提出，也不在当前决定范围内。

### 漂移

因长会话、上下文压缩、换会话、换 agent 或多份事实源导致术语、范围、决定或流程关系发生未授权变化。

### 主干

合并后 Skill 的稳定骨架。只包含三种类型共享且不能省略的流程、硬约束、路由与 Gate。

### 子文件

合并后 Skill 私有目录内的细节协议。由主干按任务类型和当前步骤读取，不作为独立 Skill 对外暴露。
