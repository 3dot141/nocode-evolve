## 1. 背景

`reviewing` 引擎现在的"档位"（轻 / 中 / 重）同时决定两件不相关的事:**审得多深**和**派几路人**。这个焊死的设计带来一个直接后果——方法卡自己描述的执行方式,和骨架规定的路数对不上。

**核心问题**:`perspective-based.md`(视角分工方法)自己写着"重档时每视角派一个独立 subagent 并行深读,避免视角污染",但 `skeleton.md` §4.0 把重档的执行方式钉死成"隔离 subagent 1 路 + Codex 1 路,固定 2 路"——如果选中的方法是 PBR 且要分 3 个视角,到底是"3 视角各一路 + Codex 一路共 4 路"还是"骨架规定的 2 路",两份文件没有单一权威,互相矛盾。

三个辅助问题:

- **验证不是独立步骤**。重档下"仅一路命中"的 finding,现在由主会话在归一汇总那一步顺手拍板要不要算数,不是一个被认真对待的独立环节。
- **"找问题"和"该不该"两类方法混在同一张选择表里**。`skeleton.md` §3 方法选择表把 checklist / threat-modeling 这种缺陷发现方法,跟 red-blue-adversarial 这种对抗决策方法列在同一张表的同一层级,对象命中多行时容易把红蓝也当成"多一路视角"塞进宽度模型,而红蓝有自己独立的执行纪律(蓝军必须主会话做、sequential-thinking 硬 gate、红军默认单跑 codex),硬塞会破坏这套纪律。
- **多领域命中时的处理方式模糊**。`skeleton.md` 已经写了"一个对象可命中多行(如代码 diff 且碰认证 → 同时取代码行 + 安全行的 card)",但命中之后怎么执行——是揉成一张大清单让一个 reviewer 看完,还是分开各自独立看——没有明确规定。

## 2. 调研

### 2.1 现状代码分析

- `[Read skills/reviewing/references/skeleton.md:126-134]` §4.0 主路派发三档表:轻档 1 路(自查)/ 中档 1 路(隔离 subagent)/ 重档 2 路(隔离 subagent + codex,直接双派),路数写死。
- `[Read skills/reviewing/references/methods/perspective-based.md:33]` "PBR 特有:重档 / 多利益相关者对象时每个视角派一个独立 subagent 并行深读,避免单 agent 串行戴多顶帽子导致视角污染"——这句话隐含"路数 = 视角数",与骨架的"路数固定 2"冲突。
- `[Read skills/reviewing/references/methods/dual-review.md:24]` "合并 + 判决 = 当前会话:按 `[location, axis]` 去重——交集 = 高置信;对称差 = 各自盲区,主会话拿完整上下文逐条判成立性"——验证这一动作混在"合并裁决"这一步里,不是独立环节。
- `[Read skills/reviewing/references/skeleton.md:108]` §3 表脚注"一个对象可命中多行……同时取代码行 + 安全行的 card"——只说了"取哪几张卡",没说"取到之后怎么并行执行"。
- `[Read skills/reviewing/references/methods/code-quality-method.md:21-79]` "总览审查清单"(无重复代码 / 代码简洁可读)和"最佳实践"组(格式不一致 / 魔法数字 / 命名差)跟"安全""代码质量""性能"三组硬伤类清单混在同一份维度表里逐项核查——"这里有没有 bug"和"这里能不能写得更好"两类不同性质的问题被同一个 reviewer 一次看完。
- `[Read skills/reviewing/references/methods/checklist.md / error-mechanism.md / threat-modeling.md / red-blue-adversarial.md]` 逐一核对:checklist / perspective-based / red-blue-adversarial 是能跨多个领域复用的通用打法;error-mechanism(只服务代码质量)、threat-modeling(只服务安全)是绑定单一领域的专用打法——这次重构要把"领域(看什么)"和"打法(怎么看)"这两层显式拆开,而不是像现在这样混在方法选择表的同一行里。

### 2.2 外部方案

- `[SOURCE: github.com/Piebald-AI/claude-code-system-prompts]` Claude Code `/code-review` 命令:每个 "finder angle" 是一段**固定写死**的分析指令(逐行扫描 diff / 删除行为审查——"每一行被删或改的代码原本保证了什么不变量,新代码里有没有重新建立" / 跨文件调用链追踪——"改动的函数,找调用方,检查会不会破坏调用点" / 语言坑扫描 / 包装类正确性),外加 5 个清理类角度(reuse / simplification / efficiency / altitude / conventions)。angle 数量随 effort 档位扩展(low=0、medium/high=8、max=10),每个 angle 都完整看一遍同一份 diff,不分片。
- `[SOURCE: 同上]` `/security-review`:三步走(仓库安全模式调研 → 比对分析 → 逐文件漏洞评估),**验证阶段逐条候选各起一个独立子任务**过滤误报,给定 diff + 相关文件 + 这一条候选,返回 CONFIRMED / PLAUSIBLE / REFUTED 三态,置信度阈值 0.8 过滤误报。
- **引用局限声明**(Review 中被指出,如实记录):以上两条来自本次会话内一个 fork agent 对该仓库的检索转述,**未留存具体 commit hash / 文件路径 / 访问日期**——如果后续需要更严格的可复核引用(比如要精确对齐某个 Claude Code 版本号的措辞),需要重新访问该仓库确认,不能仅凭本文复核。这不影响本次决策的方向性依据(启发结论已用于 Q4/Q5/Q7,且这几条决策都有独立于外部引用的内部理由支撑,见对应 Q 的"代价"栏),但引用本身目前不可精确复核。
- 启发:①验证应该是独立、逐条的环节,不该是发现方顺手自己拍板;②多种分析角度可以按对象命中的关注面分别执行,但"角度"本身应该是预先写死的书面约定,不依赖调用方每次补充解释;③"清理类"和"找 bug 类"是两条不同的关注线,该显式分开,不该揉进同一份清单。

## 3. 现状分析

### 3.1 现状结构总图

```
                              评审对象
                                 │
                                 ▼
                    §1 分档:轻 / 中 / 重
             (同时决定"审得多深"和"派几路人")
                                 │
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
      轻档                     中档                      重档
   主会话自查                隔离 subagent            隔离 subagent
    1 路(零独立性)          1 路(§3 选 1 种方法)      + Codex,固定 2 路
                                                            │
                                                            ▼
                                              按 [location,axis] 去重
                                              交集 = 高置信
                                              对称差 → 主会话自己判成立性
                                              ← 问题:验证混在裁决步骤里,
                                                不是独立环节
```

⚠ 已知矛盾:PBR 方法卡自称"重档时每视角一个独立 subagent 并行",但骨架 §4.0 把重档路数写死成 2——两份文件对不上,命中 PBR 且视角数 > 1 时无法决定实际路数。

### 3.2 DDD 视角审视

```
现状的耦合问题:

  §1 分档 同时承担两个职责
    ├─ "审得多深"(独立性档位)         ← 合理,风险驱动
    └─ "派几路人"(执行路数)           ← 不该跟深度焊死,应该由
                                        "这次对象命中了几个关注面"决定

  §3 方法选择表 同时混了两类不同性质的东西
    ├─ "找问题"类方法(checklist/threat-modeling/...)  ← 回答"这份工件有什么问题"
    └─ "该不该"类方法(red-blue-adversarial)           ← 回答"该选哪个",有自己独立的
                                                          执行纪律(蓝军不外派/
                                                          sequential-thinking 硬 gate)
       两者混在同一张表的同一层级,对象命中"该不该"类的行时容易被误当成
       "多一路视角"塞进宽度模型,破坏红蓝自己的执行纪律
```

**诊断**:执行路数(width)应该由"这次对象命中了几个关注面"决定,不该跟审查深度(depth)焊死;"该不该"类的决策方法天生跟"找问题"类方法不是一回事,不该共享同一套宽度/验证机制。

### Q1: 档位的含义 → 决定骨架 §1、§4.0 怎么改

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 维持"轻/中/重 = 1/1/2 路" | 现状不动 | 零改动成本 | 路数写死,跟场景数/方法自身的视角数(PBR)脱钩,现有矛盾(§3.1)不解决 |
| **B. 自审 / Codex 单审 / subagent+codex 双审** | 档位改成"每个场景内部用几路、什么身份的执行者" | 中档从"同源隔离"直接升级成"异源单路"(Codex),独立性比现状更强;跟"执行位数量"概念直接对应,便于后面 Q3 统一打包 | 中档成本从"起 1 个 subagent"变成"起 1 次 Codex 调用",Codex 不可用时走现有降级链(fallback 同源 subagent,标"降级") |

**选 B**。`[已确认]` 现状 A 方案正是本次要解决的矛盾根源。**否决 A**:不改档位含义,PBR 和骨架的路数矛盾无法自然消解,还是要靠特例打补丁。

> **单一权威声明**(Review 发现 C1 后补充):**档位与执行者身份的对应关系,全文只在本 Q1 定义一次,别处一律引用本节,不重复给出具体身份**——凡本文其他地方提到"中档"，其执行者身份**必须**是"Codex 单审"，若读到"中档 = subagent"字样即为本文件内部不一致,以本节为准。（Review 中 Codex 指出 §4.4 Q3、§5 目标图、§6 迁移 Step 1 曾出现"中档 = 1 个 subagent"的错误表述,均已在本版改正为"中档 = Codex 单审"，详见 Review Log。）

### Q2: 顶层执行单位 → 决定要不要引入"场景"这一层

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 维持 §3"评审对象 → 方法"两层 | 现状不动,靠"命中多行"脚注处理多领域 | 零改动 | "看什么"(领域)和"怎么看"(方法)没有拆开,error-mechanism/threat-modeling 这类专用方法容易被误当成可以到处复用的通用方法;多领域命中执行方式模糊(§3.1 辅助问题) |
| **B. 场景 → 视角 → 方法三层** | 场景 = 具名的关注面(安全/数据库/架构决策/代码质量/需求……,大致对应现有 §3 表的行);视角 = 场景内部的子关注点(如代码质量场景下的"正确性"和"清理");方法 = 视角内部的具体打法 | 把"看什么"和"怎么看"显式拆开,error-mechanism/threat-modeling 这类专用打法的适用范围一目了然;多场景命中时,每个场景各自独立处理,不互相干扰 | 概念多了一层,方法卡和骨架都要同步这套新术语 |

**选 B**。`[已确认]` **否决 A**:现有两层结构已经证明会导致"专用方法被当成通用方法误用"和"多领域命中执行方式不清楚"两个问题,继续维持只是把问题往后拖。

### Q3: 多场景命中时怎么执行 → 决定成本模型

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 每个场景各起一路独立执行(含 PBR 每视角各起一路) | 命中 N 个场景就起 N 路并行,PBR 的 K 个子视角额外再展开 | 独立性最强,每一路只关注自己的场景/视角,不互相干扰 | 成本随场景数线性放大,重档下"N 场景 × 2(subagent+codex)"可能是两位数的 agent 调用,PBR 命中还要再乘 K |
| **B. 档位定几个执行位,所有场景打包塞进这几个执行位** | 轻档 0 个执行位(主会话自查)/ 中档 1 个执行位(Codex 单审)/ 重档 2 个执行位(1 个 subagent + 1 个 Codex)。识别出的全部场景(含视角、方法)打包成一份任务,喂给这几个执行位,执行位内部按场景清单逐节顺序过 | **执行阶段**的调用数只跟档位挂钩(0/1/2 次),不随场景数线性放大,可预测 | 中档下(1 个执行位)多个场景挤在同一次调用里顺序看,独立性弱于"每场景各起一路";PBR 的 K 个视角在中档下也是同一个执行位顺序戴帽子,存在"视角污染"风险(见下方 PBR 说明) |

**选 B**。`[已确认]` **否决 A**:场景数量不可控(取决于对象实际内容),成本随之线性放大不可预测,重档下"N 场景 × 2 路"容易演变成两位数级别的 agent 调用,超出"reviewing 是被高频调用的公共底座"这个定位应有的成本纪律。B 方案接受"中档下多场景/多视角顺序挤在一次调用里"的独立性折损,用重档的 subagent+codex 两路交叉来部分补偿——这个折损跟"中档对任何单一场景本来就只给 1 路、独立性本来就弱"是同一个道理,不是新增的妥协。

> **成本模型的诚实边界**(Review 指出 W1 后补充):**只有"执行阶段"的调用数跟档位挂钩、可预测**——Q5 的 Verify 阶段是另一个独立的成本来源,其调用数跟"仅单路命中的候选数量"挂钩,不受档位约束,candidate 多时可能显著增长。本文不假装"总成本可控",Verify 阶段的开销上限问题见 §7 失败预演的缓解措施,当前**接受该风险**、不在本轮设硬性批处理上限(留待实现后观察真实候选量再决定是否需要)。

**PBR 是否例外**:讨论过"PBR 的 K 个 stakeholder 视角要不要独立于档位、始终各自展开",最终定为**不例外**——PBR 并入同一套规则(轻档主会话顺序戴 K 顶帽子 / 中档 Codex 单审顺序戴 K 顶帽子 / 重档 subagent 和 codex 各自独立顺序戴 K 顶帽子、然后对应视角互相 Verify)。PBR 跟其他方法的区别只剩下"这个场景声明了几个具体视角"(PBR 给 K 个,其他方法通常给 1-2 个),不再有执行方式上的特权。

### Q4: 视角来源 → 决定要不要支持外部注入

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 只用 §3 表自动命中 | 现状不动 | 简单 | 调用方/项目没法声明"这次额外要看的关注点",复用性受限 |
| **B. §3 命中 + 调用处传入(复用现有参数) + 项目本地扩展(内部读取)** | 调用 `Skill(nocode:reviewing)` 时声明的"领域维度"参数本来就可以内联自定义内容(见 `SKILL.md`"调用契约"表:"领域维度……内联,或指向调用方自己的 references/xxx-review.md");项目本地(如 `.agents-personal/`)可以声明标准关注点,呼应 Claude Code REVIEW.md 顶层注入的思路 | 灵活,项目能定制而不用改骨架本身,**且不新增调用参数**——"领域维度"参数本身在现有契约里就是自由格式,视角只是这个参数被更明确地按"场景"组织;项目本地扩展是引擎收到调用后自己去读一个约定路径的文件,属于引擎内部动作,不改变调用方要传什么 | 每个视角的定义必须是自包含书面约定(像现有方法卡一样),不能依赖调用方每次补充上下文——否则复用性会打折扣 |

**选 B**。`[已确认]` **否决 A**:限定死板,和已经验证过的 Claude Code REVIEW.md 顶层注入思路相比明显更弱。

> **与"调用契约不变"的一致性说明**(Review 指出 C2 后补充):§5"行为不变性说明"声称调用契约不变,与本 Q "调用处显式传入视角"曾被误读为新增参数——**澄清**:调用方传入的仍然只有 SKILL.md 既有的四项(评审对象 / 领域维度 / 方法 / Context Capsule),**没有新增"视角"这个独立字段**。"调用处传入视角"这件事,落地方式是调用方在已有的"领域维度"参数里更明确地写清楚这次要看哪些场景/视角(这本来就是该参数的自由度,SKILL.md 原文"内联,或指向调用方自己的 references/xxx-review.md"早已允许)。"项目本地扩展"落地方式是引擎收到任意调用后,内部多一步"读一下项目本地是否有扩展视角声明文件"的动作,同样不要求调用方传新参数。约束条件:注入的视角定义必须自包含,不需要额外解释才能生效——这条约束沿用 CLAIM 剥离(skeleton §4.1)"剥结论、留约束"的既有精神,不是新规则。

### Q5: Verify 范围与机制 → 决定验证怎么做

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 全局按 [location, axis] 去重,跨场景验证 | 所有场景的 findings 混在一起去重、验证 | 实现简单 | 不同场景回答的是不同问题(安全 vs 架构),同一位置的两条 finding 即便 axis 不同也可能被误关联;架构视角没资格"确认"安全视角的发现是不是真的 |
| **B. 只在同一场景内部做,跨场景不验证** | 场景内部多条路径(档位给的 subagent+codex,或 PBR 的 K 个子视角)互相比对;不同场景的发现只在最后汇总并列呈现 | 语义正确——验证只在"两条路径回答同一个问题"时才有意义 | 需要在骨架里明确按场景分组再验证,不能一次性拿全部 findings 去重 |
| 机制 A':仅单路命中的候选,回抛给没发现的另一路确认("你怎么看") | 省成本,复用已有的路,不新起 agent | 便宜 | 跟 Claude Code 实证机制不符(它是专门起第三方,不是回抛) |
| **机制 B':仅单路命中的候选,各起一个独立第三方验证者,给 diff/文件/这一条候选,判 confirmed/plausible/refuted** | 贴近已验证的 Claude Code 实证做法,验证者是全新第三方,不带任何一路的既有判断,独立性更强 | 成本比"回抛"高(每条候选多一次 agent 调用),且调用数随候选数增长(见 Q3 补充说明) | — |

**范围选 B,机制选 B'**。`[已确认]` **否决"跨场景验证"**:不同场景回答不同问题,没有互相印证的意义。**否决"回抛"机制**:虽然更省成本,但讨论中查实 Claude Code 的实际做法是"专起第三方逐条判",这次决定采信这个更贴近实证的做法而不是省钱的替代方案——验证环节的独立性价值优先于省下的那次 agent 调用。

### Q6: red-blue-adversarial 的定位 → 决定它进不进新体系

| 方案 | 思路 | 优势 | 代价 |
|---|---|---|---|
| A. 命中"该不该"类场景时,当成一路视角塞进宽度/Verify 体系 | 统一处理,少一个特例 | 会破坏红蓝自己的执行纪律——蓝军必须主会话做(不能塞进"打包进执行位"的统一流程)、sequential-thinking 硬 gate、红军默认单跑 codex 不并行、产出是 verdict.recommendation 不是 findings[] | — |
| **B. 命中的场景整体摘出,完全独立于场景/视角/方法/Verify 体系** | 红蓝按自己原有的独立流程走,不受这次重构影响 | 保持红蓝现有纪律不被破坏 | 一份对象如果同时有"决策类"和"找问题类"关注点,最终呈现的是两份不同性质的产出(findings[] + verdict.recommendation)并列,不合并 |

**选 B**。`[已确认]` **否决 A**:红蓝的执行方式(蓝军不外派、sequential-thinking 硬 gate、红军单跑不并行)跟这次"打包进执行位统一处理"的模型根本不兼容,强行统一只会两边都做不好。

### Q7: "代码质量"场景要不要补充子视角 → 决定要不要新增方法卡

| 方案 | 思路 | 优势 | 代价 |

| A. 维持现有 checklist + error-mechanism 两个方法 | 现状不动 | 零改动 | Claude Code 实证验证过的"回归检查""跨文件影响追踪"这两类关注点现有方法都没覆盖;"找 bug"和"能不能优化"两类不同性质的问题混在 code-quality-method 一张清单里 |

## 5. 目标设计

### 5.1 新旧步骤映射(Review 指出 C3 后新增)

现有骨架是 7 步(`skeleton.md` 现行版:分档 → 对象界定+gate → 评审维度 → 主路审 → 升档重跑 → findings 统一 schema+分级 → 收口/triage)。本次重构不是推翻这 7 步,而是重新划分步骤边界、把其中两步实质性重组。逐项映射:

| 旧步骤 | 新模型里的落点 | 说明 |
|---|---|---|
| 1 分档 | 新 Step 2 分档 | 判据表本身不变(§1 风险/可逆性信号),只是含义从"路数"改成"执行位数量"(Q1) |
| 2 对象界定 + gate | **保留,前移到新 Step 1 之前的隐式前置动作** | 明确评什么、范围多大、前置条件是否满足——这一步**不省略**,是"场景识别"能够展开的前提(不知道评审对象是什么,无法识别场景)。本文档为简洁未在 Before/After 图里单独画出,但实现时 `skeleton.md` 仍须保留这一步,新 Step 1(场景识别)在其后执行 |
| 3 评审维度(调用方传入) | 并入新 Step 1 场景识别 | 调用方传入的"领域维度"现在被引擎用来匹配/生成场景清单(见 Q4),不再是一份孤立的维度表 |
| 4 主路审(按档位执行) | 新 Step 3 执行(打包) | 执行者/路数定义从"三档执行方式表"改成"档位=执行位数量+打包"(Q1、Q3) |
| **5 升档重跑(仅轻/中档,§1a)** | **保留,机制不变,插入点在新 Step 2 分档判定之后、新 Step 3 执行开始之前** | §1a 的升档判据(执行中命中更高档信号必须升档)本次**不改动语义**——仍然是"起始档判完之后,执行过程中读到实际内容命中更高档信号就升档重跑",只是"升档"影响的对象从旧模型的"路数"变成新模型的"执行位数量与身份"(比如中档执行中发现命中重档信号,就从"1 个 Codex 执行位"升级到"1 个 subagent + 1 个 Codex 两个执行位",重新打包执行,不带入旧执行位的结论)。**本文档 Before/After 图未单独画出这一步是本次疏漏,实现时 `skeleton.md` 必须保留这一步的完整定义,不能因为图上没画就丢失** |
| 6 findings 统一 schema + 分级 | 并入新 Step 5 总结 | 不变 |
| 7 收口 / triage / 拍板 | 并入新 Step 5 总结 | 不变 |
| （无对应,新增） | 新 Step 4 Verify | 本次新增的独立验证环节(Q5),旧流程没有对应步骤——旧流程里"验证"隐藏在旧步骤 6 的"合并裁决"里,本次把它拆成独立步骤 |

**结论**:新模型不是"5 步替换 7 步",而是"7 步中的 2 步(旧 4、旧 6)被重新定义 + 1 步(旧 6 里隐藏的验证动作)被拆成独立新步骤 + 其余步骤原样保留"。下方 Before/After 图为了突出这次改动的核心(执行方式 + Verify),只画出发生实质变化的部分,不代表旧步骤 2、5 被删除。

| # | 变更 | 理由(对应 §3 现状问题) |
|---|---|---|
| ① | 档位从"轻/中/重(路数写死 1/1/2)"改成"自审/Codex 单审/subagent+codex 双审(执行位数量,与场景数无关)" | 解决 PBR 与骨架路数矛盾的根源——路数不再跟深度焊死 |
