# 设计文档: 路径驱动的 PRD→Define→Design→Verify 链路改造

> Status: Draft
> Author: 3dot141
> Date: 260625
> Scenario: Full

## 问题

当前 PRD→Define→Design→Verify 链路在用户使用场景覆盖上有四个断裂点：

1. PRD 只有 User Stories（一句话意图），没有展开成具体使用路径，vis 拿不到可设计的交互输入
2. Define 的 restate 不校验路径完整性，SC 是扁平列表，和路径无绑定关系
3. Design 测试目标只从 SC 推导，不以路径为骨架，无 verify 策略产出
4. Verify 纯执行 checklist，不做反向审计，前面漏的后面也漏

唯一成型的跨阶段回链是 evidence → SC。PRD 的 US-N 编号不向下游传递，无路径/领域/约束建模，task 无 covers 回链字段。

## 选定方案

**方案 A：共享约定文档 + 四文件轻量引用**

新建共享 reference 定义 ID 体系和路径格式，四个 SKILL.md 各加消费逻辑引用它。约定单源不散落。

否决的方案：方案 B（PRD 重模板 + 下游内联）——约定重复四处，维护成本高，ID 格式改了要同步四处，漂移风险大。

## 设计详情

### 1. 新建 `skills/references/path-conventions.md`

共享约定文档，定义以下内容：

#### 1.1 ID 体系

| 类型 | 格式 | 例子 | 说明 |
|---|---|---|---|
| 用户故事 | `US-{N}` | US-1, US-2 | PRD 生成，全局递增，不复用 |
| 业务领域 | 中文名 | 订单、支付、物流 | PRD 按需定义，非固定枚举 |
| 领域内路径 | `{领域}.P{N}` | 订单.P1, 支付.P3 | 领域内递增 |
| 跨领域路径 | `跨域.{N}` | 跨域.1 | 全局递增 |
| 系统路径 | `系统.{N}` | 系统.1 | 全局递增 |
| 约束 | `约束.{N}` | 约束.1 | 全局递增 |
| 验收标准 | `SC-{N}` | SC-1 | **Define 独占生成**，PRD 不分配 SC 编号 |
| 测试目标 | `TO-{N}` | TO-1 | Design 生成 |

**铁律**：ID 一经分配不可复用、不可重排。删除的 ID 留空，不回收。改措辞不改 ID。

#### 1.2 路径格式

**使用路径**（outcome 级别，不锁交互）：

```
- {领域}.P{N}: {一句话描述} [{角色}] [CONFIRMED/ASSUMED/TBD]
  来源: US-{X}
  {触发/前置} → {关键步骤} → {结果}
  | 异常: {异常场景}
  | 边界: {在哪结束、和哪个领域交界}
```

角色标注：单角色直接写 `[买家]`；多角色差异用 `[买家: 自助 | 客服: 代操作]`。
`来源: US-{X}` 标注该路径由哪条用户故事展开（可多条）。下游可反查每条 US 是否被路径覆盖。

**跨领域路径**：串联已有领域路径。

```
- 跨域.{N}: {一句话描述} [{角色}]
  {领域}.P{X} → {领域}.P{Y} → {领域}.P{Z}
  | 异常: 任一环节失败的回退链
```

**系统路径**（无用户入口）：

```
- 系统.{N}: {一句话描述}
  {触发条件} → {处理步骤} → {结果}
  | 异常: {异常场景}
```

**约束**（跨路径不变量）：

```
- 约束.{N}: {业务规则描述}
```

#### 1.3 标注状态

路径和约束统一使用 PRD 的三态标注：`[CONFIRMED]` / `[ASSUMED]` / `[TBD]`。

#### 1.4 下游消费协议

| 阶段 | 消费什么 | 产出什么 |
|---|---|---|
| PRD | — | 路径 + 领域 + 约束（含 ID + 状态 + US 来源） |
| vis | PRD 使用路径 | 交互级路径（细化，不改 ID）+ 页面状态覆盖 |
| Define | PRD 路径 + 领域 | 校验完整性 + SC(独占分配) + 路径↔SC 绑定 |
| Design | restate 路径 + SC | TO 覆盖每条路径 + verify 策略(落盘设计文档) + 自审 |
| Plan | TO + 路径 | task 标注 `covers: [路径ID]`（**必填** + 覆盖 Gate） |
| Build | task + covers | 实现 |
| Review | PRD 路径 + TO + 代码 diff | 路径覆盖检查（Spec 轴，含 PRD 原始清单） |
| Verify | verify 策略 + PRD 路径 | 按策略逐层验证 + 反向审计 |

#### 2.2 流程变更

现有 PRD 六步流程重编号为：

| 原步骤 | 新步骤 | 内容 |
|---|---|---|
| Step 1 (加载输入) | Step 1 | 不变 |
| Step 2 (Clarify Gate) | Step 2 | 不变 |
| Step 3 (起草 PRD) | Step 3 | 不变（模板已含新节） |
| *(新增)* | **Step 4: 领域与路径建模** | 见下方 |
| Step 4 (User Stories 确认) | **Step 5: 合批确认** | 改为整份清单一次确认 |
| Step 5 (自审) | Step 6 | 新增路径维度（见 2.3） |
| Step 6 (用户最终确认) | Step 7 | 不变 |
| Step 7 (保存) | Step 8 | 不变 |

**Step 4: 领域与路径建模**

1. 从 User Stories 识别业务领域（按业务面分，不按技术层分）
2. 每个领域下展开使用路径（outcome 级别，格式见 path-conventions）
3. 识别跨领域路径（串联已有领域路径）
4. 识别系统路径（无用户入口的后台行为）
5. 提取约束（跨路径的业务不变量）
6. 每条标注 `[CONFIRMED]/[ASSUMED]/[TBD]`

**Step 5: 合批确认**

不再逐条确认 User Story，而是整份路径清单（含 User Stories + 所有路径 + 约束）一次性展示给用户，用户加减改后一次确认。减少确认疲劳。

#### 2.3 自审新增维度

| 维度 | 检查什么 |
|---|---|
| 路径完整性 | 每条 US 至少展开了一条路径？ |
| 领域覆盖 | 有没有遗漏的业务面？ |
| 角色覆盖 | 涉及多角色时，角色差异是否标注？ |
| 约束覆盖 | 跨路径的业务规则是否提取？ |
| 系统路径 | 有后台行为/回调/定时任务吗？ |

| 原步骤 | 新步骤 | 内容 |
|---|---|---|
| Step 1 (场景分类) | Step 1 | 不变 |
| Step 2 (探索现状) | Step 2 | 不变 |

### 4. vis 改造 (`skills/pd-vis/SKILL.md`)

vis 当前已从 User Story 生成"Key Flows"交互流。改造后消费 PRD 的使用路径（而非 User Story），用路径 ID 关联。

#### 变更点

1. **Step 0（读 PRD）扩展**：除现有 User Story 外，额外读取「业务领域与使用路径」节，作为交互设计的骨架
2. **Step 2（IA + 交互流）改造**：
   - 关键流程从 PRD 使用路径映射而来，保留路径 ID（`订单.P1 → 交互流: ...`）
   - 每条交互流标注对应的路径 ID，不新编号
   - 跨领域路径（`跨域.N`）展开为端到端交互流
   - 系统路径不进 vis（无界面），但 vis 需识别"系统路径触发后用户看到什么"（如支付回调成功后页面状态变化）
3. **Step 5（PRD Coverage）改造**：逐条核对从 User Story 级升级为路径级
   - 每条使用路径都有对应的界面/交互流吗？
   - 系统路径的用户可见反馈覆盖了吗？
4. **`.design.md` 模板变更**：

```markdown
## 关键流程
[每条标注路径 ID]
| 路径 ID | 交互流 | 状态覆盖 |
|---|---|---|
| 订单.P1 | 商品页→购物车→确认→支付 | 正常/库存不足/地址不可配送 |
| 订单.P2 | 订单详情→取消→确认弹窗→结果 | 正常/已发货不可取消 |

## PRD 路径覆盖
| 路径 | 对应界面/流程 | 状态 |
|---|---|---|
| 订单.P1 | 见上方交互流 | ✅ |
| 系统.1 (支付回调) | 支付等待页→成功/失败状态切换 | ✅ (用户可见部分) |
```

### 5. Design 改造 (`skills/dev-design/SKILL.md`)

现有 Design 七步流程重编号为：

| 原步骤 | 新步骤 | 内容 |
|---|---|---|
| Step 1-5 | Step 1-5 | 不变 |
| Step 6 (测试目标) | **Step 6: 测试目标（重构）** | 以路径为骨架 |
| *(新增)* | **Step 7: Verify 策略 + 自审** | 见下方 |
| *(新增)* | **Step 8: 路径覆盖审核** | 方案+TO+策略的完整性检查 |
| Step 7 (写设计文档) | Step 9 | verify 策略写入设计文档固定章节 |

#### 5.1 Step 6 重构: 测试目标以路径为骨架

现有 Step 6 从 SC 推导测试目标。改为：

1. 从 restate 取路径清单 + SC 绑定
2. **每条路径 → 至少一条测试目标(TO)**
3. 每条约束 → 至少一条测试目标
4. 标出可测性约束（需 mock 的外部依赖、需特定环境的行为）
5. 指定测试层级分布（单测 / 集成 / E2E）
6. 跨领域路径的 TO 和领域内路径的 TO 关系要明确：跨域 TO 测端到端串联，领域 TO 测单段逻辑，不重复也不遗漏

产出格式：

```
## 测试目标

| TO | 覆盖路径 | 覆盖约束 | 测试层级 | 说明 |
|---|---|---|---|---|
| TO-1 | 订单.P1 | — | E2E | 下单全流程 |
| TO-2 | 订单.P2 | 约束.1 | 集成 | 取消退款不超实付 |
| TO-3 | 跨域.1 | — | E2E | 下单到签收端到端 |
| TO-4 | 系统.1 | — | 集成 | 支付回调签名校验 |
```

#### 5.2 Step 7: Verify 策略 + 自审

选定方案 + 测试目标后，产出 verify 策略：

1. **按测试层级分组**，逐层说明：
   - E2E：覆盖哪些路径？怎么跑（dev server / browser / CLI）？
   - 集成测试：覆盖哪些跨领域交界？mock 什么、不 mock 什么？
   - 单测：覆盖哪些路径的核心逻辑？
   - 手动验证：哪些路径需要人工确认？为什么不能自动化？
2. **显式列出不测的内容 + 原因**——不能笼统写"测不了"，要说具体是什么限制（无测试环境 / 第三方沙箱不支持 / 成本不合理），附风险评估
3. **风险排序**：高风险路径优先测试

**自审（产出后立即检查）**：

| 维度 | 检查什么 |
|---|---|
| 路径覆盖 | 每条路径都有对应 TO 吗？有没有路径没出现在 TO 表里？ |
| 约束覆盖 | 每条约束都有对应 TO 吗？约束测试需要多条路径组合验证吗？ |
| 层级合理 | E2E/集成/单测分布合理吗？是不是全标了 E2E（太重）或全标了单测（太弱）？ |
| 不测项风险 | 标"不测"的路径风险评估充分吗？高风险路径标"不测"需要额外说明 |
| 跨域不重复 | 跨域 TO 和领域 TO 有没有重复测同一件事？ |

自审通过后，**AskUserQuestion 确认**：整份策略（含 TO 表 + verify 策略 + 不测项）一次展示，用户确认/修改。

#### 5.3 Step 8: 路径覆盖审核

Design Review 阶段（写设计文档前）默认执行路径覆盖检查：

1. **方案 ↔ 路径对齐**：选定方案是否覆盖了 restate 的每条路径？有没有路径在方案里完全没提到？
2. **TO ↔ 路径对齐**：TO 表覆盖了每条路径和约束吗？（和自审重叠，这里是独立复核）
3. **verify 策略 ↔ TO 对齐**：每条 TO 都有对应的测试方案吗？
4. 产出路径覆盖状态表：

```
| 路径 | 方案覆盖 | TO 覆盖 | verify 策略 | 状态 |
|---|---|---|---|---|
| 订单.P1 | ✅ | TO-1 | E2E | ✅ 完整 |
| 订单.P2 | ✅ | TO-2 | 集成 | ✅ 完整 |
| 系统.1 | ✅ | TO-4 | 集成 | ✅ 完整 |
| 约束.1 | ✅ | TO-2 | 集成 | ✅ 完整 |
```

任一路径状态非 ✅ → 回补后再进 Step 9。

#### 5.4 Step 9: 写设计文档

调 `Skill(nocode-evolve:design-doc-writing)`。**verify 策略作为设计文档的固定章节**写入（不只存在于会话文本），章节名 `## 验证策略`，含 TO 表 + 按层级分组的测试方案 + 不测项 + 路径覆盖状态表。

Verify 阶段直接从设计文档读取此章节作为执行依据。

#### 5.5 Exit Gate 新增

- [ ] 测试目标覆盖每条路径和约束
- [ ] verify 策略已产出，自审通过，用户确认
- [ ] 路径覆盖审核通过（覆盖状态表全 ✅）
- [ ] verify 策略已落盘到设计文档的「验证策略」章节

### 6. Review 改造 (`skills/dev-review/SKILL.md`)

#### 6.1 Spec 轴新增路径覆盖检查

在现有 Spec 轴（"回 restate/设计文档核对"）之后，加**路径级粒度检查**：

1. 取 **PRD 原始路径清单**（不只是 Design 的 TO 表）+ restate 路径↔SC 绑定
2. 逐条路径检查：实现是否覆盖？有没有路径在代码里完全没体现？
3. 逐条约束检查：是否有对应的校验逻辑？
4. **对照 PRD 原始清单**：如果 Design 的 TO 表漏了某条 PRD 路径，Review 在这里能发现（Design 漏了 → TO 表没有 → 但 PRD 清单有 → Review 拦住）
5. 产出：路径覆盖率报告（覆盖/部分覆盖/未覆盖），未覆盖项标 reason

这是 Design 之后、Build 之后的两次机会（Design Review + Code Review）。不用等 Verify 才发现漏了。

### 7. Verify 改造 (`skills/dev-verify/SKILL.md`)

#### 7.1 6e（验收逐条核对）扩展

现有 6e 逐条核对 SC。扩展为：逐条核对 **SC + 路径 + 约束**，每条附证据。

#### 7.2 新增 6f: 反向审计

在 6e 之后，拿 PRD 原始路径清单（不只是 Design 的 TO 表）回扫：

1. **按测试方案逐层检查**：
   - E2E 测试：Design 策略说要 E2E 的路径，有没有跑？跑出来的结果能不能真的验出问题？
   - 单测：路径 P1/P2/P3... 都覆盖到了吗？
   - 集成测试：跨领域交界覆盖了吗？
   - 手动验证：标记"手动"的路径，有没有实际验过？
2. **约束验证**：每条约束有没有对应的测试？测试够不够（单条路径通过 ≠ 约束成立，需要多条路径组合）
3. **Design 标的"不测项"复查**：当时说"测不了"的理由现在还成立吗？
4. **产出**：反向审计报告。发现遗漏 → 补测或显式标注"已知未验 + 原因 + 风险"，不静默放过

### 8. Plan 改造 (`skills/dev-plan/SKILL.md` + `references/task-template.md`)

#### 8.1 task 模板加 covers 字段（必填）

```
covers: [订单.P1, 订单.P2, 约束.1]   # 本 task 覆盖的路径/约束（必填）
```

**必填而非可选**。不写 covers 的 task 不通过 Plan 的验证。

#### 8.2 Plan Exit Gate 加覆盖检查

Plan 完成后新增 Gate：

- 汇总所有 task 的 covers 字段
- 对照 restate 路径清单：**每条路径至少被一个 task 覆盖**
- 有路径没被任何 task 覆盖 → 补 task 或说明原因（该路径在当前迭代不实现则标注）
- 产出：路径→task 映射表

## 各环节输入/输出/决策流

### PRD

| | 内容 |
|---|---|
| **输入** | research-memo（可选）+ 用户描述 |
| **输出** | `.prd.md`：用户故事(US-N) + 业务领域 + 使用路径(领域.PN) + 跨领域路径(跨域.N) + 系统路径(系统.N) + 约束(约束.N) + 成功指标 + 不做的事 |
| **决策** | ① 识别哪些业务领域 ② 每个领域的路径是否穷举 ③ 跨域/系统/约束是否遗漏 ④ 用户合批确认整份清单 |

### vis

| | 内容 |
|---|---|
| **输入** | `.prd.md` 的使用路径（按路径 ID） |
| **输出** | `.design.md`：交互流（保留路径 ID）+ wireframe + 视觉方向 + 路径覆盖表 |
| **决策** | ① 每条使用路径怎么翻译成交互步骤 ② 系统路径的用户可见反馈是什么 ③ 状态覆盖（正常/empty/loading/error）④ 路径覆盖核对：PRD 的每条路径都有对应界面吗 |

### Define

| | 内容 |
|---|---|
| **输入** | `.prd.md` 路径清单 + `.design.md`（可选）+ 用户任务描述 |
| **输出** | restate：Outcome + SC(SC-N) + 路径清单（搬入或生成）+ 路径↔SC 绑定表 + 场景分类 |
| **决策** | ① PRD 路径是否完整（按领域逐个检查）② 无 PRD 时现场生成路径（标 ASSUMED）③ 每条路径绑哪条 SC ④ 有路径无 SC → 补 SC；有 SC 无路径 → 补路径 ⑤ 用户确认路径 + SC 绑定 |

### Design

| | 内容 |
|---|---|
| **输入** | restate（含路径清单 + SC 绑定）|
| **输出** | 设计文档（含「验证策略」章节）+ TO 表 + verify 策略 + 路径覆盖状态表 |
| **决策** | ① 方案对比选型 ② TO 以路径为骨架 ③ verify 策略逐层说明 + 不测项 + 风险排序 ④ 自审（5 维检查）⑤ 路径覆盖审核（方案/TO/策略三层对齐）⑥ 用户确认整份策略 |

### Plan

| | 内容 |
|---|---|
| **输入** | 设计文档 + 测试目标表 + 路径清单 |
| **输出** | task 列表（每个 task 必填 `covers: [路径ID]`）+ 路径→task 映射表 |
| **决策** | ① 怎么切 task ② 每个 task 覆盖哪些路径（必填）③ Exit Gate：每条路径至少被一个 task 覆盖 |

### Build

| | 内容 |
|---|---|
| **输入** | task 列表（含 covers 字段）|
| **输出** | 代码实现 + 测试代码 |
| **决策** | 执行层，按 task 的 covers 字段知道自己在覆盖哪条路径 |

### Review

| | 内容 |
|---|---|
| **输入** | 代码 diff + 设计文档 + TO 表 + **PRD 原始路径清单** |
| **输出** | review findings + 路径覆盖报告 |
| **决策** | ① 五轴检查 ② Spec 轴路径级检查：拿 PRD 原始清单（不只 TO 表）逐条比对代码 ③ Design 漏掉的路径在这里兜住 ④ 未覆盖项标 reason |

### Verify

| | 内容 |
|---|---|
| **输入** | verify 策略（Design 产出、用户确认过）+ PRD 原始路径清单 |
| **输出** | 验证证据 + 反向审计报告 |
| **决策** | ① 按 verify 策略逐层执行：E2E 有没有跑？单测 P1-Pn 都覆盖了？集成测试跨域交界覆盖了？② 每层不只看存在，看有效（能不能真抓到回归）③ 反向审计：拿 PRD 原始路径回扫，Design checklist 之外还有没有遗漏 ④ Design 标的"不测项"现在还成立吗 ⑤ 发现遗漏 → 补测或标注"已知未验+原因+风险" |

### 完整性保障

每条路径从 PRD 出生（分配 ID），经过六道关卡：

```
PRD (生成ID) → vis (交互化) → Define (绑SC) → Design (绑TO+策略) → Review (覆盖检查) → Verify (执行+反审)
```

任何一条路径漏了，在六道关卡中至少会被一道拦住。最后一道 Verify 的反向审计直接拿 PRD 原始清单比对，确保前面的关卡没有集体遗漏。
