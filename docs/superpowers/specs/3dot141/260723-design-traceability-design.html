01 / DEFINE RESTATE

罗盘与执行边界

Outcome：修复 nocode 工程流中的设计追踪断链，使日志、安全、Metrics、迁移等规范性设计项不会在 Design 之后无声遗漏。

USER

使用 nocode Devflow 进行复杂工程任务的开发者。

WHY NOW

断点续传案例证明：日志已存在于 Design，后续仍可能遗漏。

SCENARIO

Full；自定义执行路径 Define → Design → Build；Design 不使用 DDD。

FACT SOURCE

单一 approved 设计文档；不引入独立 RTM/manifest。

成功标准 SC-1–SC-8

  1. SC-1 Dev Design 产出可识别的规范性设计项，覆盖 BF、接口、日志、安全、Metrics、迁移、TO 等类型。
  2. SC-2 运行时功能缺少基础日志设计时，Design Gate 必须失败。
  3. SC-3 Plan 能反向检查每个 required 设计项是否对应 task、verify-only 或明确延期。
  4. SC-4 Build/Verify 能保留 Design ID，并提供代码或测试证据。
  5. SC-5 in-review 或不完整的 Design 不能进入下游。
  6. SC-6 “主文档 + 未纳入交接的补充文档”不能绕过覆盖检查。
  7. SC-7 断点续传日志案例回归中，所有日志项都能追踪到实施落点。
  8. SC-8 相关测试、插件版本及双平台生成物保持一致。

约束、范围与假设

CONSTRAINT

不采用 DDD；单一 approved Design 为事实源；本轮不经过独立 Dev Plan，Design 批准后直接 Build。

OUT OF SCOPE

不改断点续传业务项目；不逐句编号；不强制每个日志事件成 task；不建通用需求平台；不引入第二 manifest。

ASSUMPTIONS

规范性设计项影响代码、配置或验证；批准后的实施清单直接作为 Build 输入；虽跳过 Verify，仍修改 dev-verify 协议。

QUALITY BAR

required 全有下游状态；无无解释 orphan；日志案例确定性回归；Skill/模板/Gate/示例一致；测试与双平台检查通过；SemVer minor。

背景与前置调研

主因：现有流程追踪的是 Define 路径和 Plan task，不是 Design 中全部需要实施或验证的规范性设计项。因此，日志已经写进设计文档，仍可能因为没有进入任何 task 而无声遗漏。

  • Design 的 approved: true verdict 与文档 frontmatter 状态没有形成同一个 Gate。
  • 当前单文档契约缺少下游入口校验，“主文档 + 补充文档”可能只被消费一半。
  • Build 和 Verify 只验证已经进入 task/SC 的内容，无法识别上游 orphan。

这不是日志专项问题。日志只是最先暴露断链的横切项；安全、Metrics、迁移、回滚和 eval 都受同一缺口影响。外部工程资料把这类问题称为双向可追踪性：正向确认每项设计有下游，反向识别没有上游或没有承接者的 orphan。本方案采用这一完整性原则，但不引入重型合规工具。

Open Questions：无。已确认执行约束：本轮不走独立 Plan/Verify 阶段，但实现范围仍包含 dev-plan、dev-build、dev-verify 的协议修改。

02 / DECISIONS

三项决定，切断三类盲区

Q1

追踪事实源放在哪里？

A：只补 Plan/Verify checklist，改动小但依赖记忆；C：另建 JSON/YAML manifest，机器校验直接但产生第二事实源。

选择 B：单一设计文档内稳定 ID + 下游双向矩阵。保持单一事实源，并可反向识别 orphan。影响 P1–P4。

Q2

设计项编号到什么粒度？

A：章节级会掩盖局部遗漏；C：逐句/逐字段会把解释文字变成维护噪声。

选择 B：独立可实施、验证、延期或判定不适用的最小单元。影响 SC-1、SC-3、SC-4。

Q3

Gate 覆盖到哪些阶段？

A：只在 Plan 检查仍无法保证输入批准与最终留证；C：所有项立即实现，无法表达合理延期、仅验证或不适用。

选择 B：Design 建清单、Plan 查孤儿、Build 保留映射、Verify 查证据，并使用四态。影响 P1–P4。

06 / BUSINESS FLOWS

BF1–BF4：协议如何运行

BF1 · Design 生成实施设计项清单

function Writing.finalizeDesignDocument(docPath):
  read reviewed document
  collect normative decisions and cross-cuts
  assign or reuse stable IDs
  classify each item into required | verify-only | deferred | n/a
  reject missing status or required rationale
  append Implementation Item Registry
  verify registry ↔ source sections both ways
  set frontmatter status to approved after verdict

异常：未声明补充文档承载规范内容 → 停止 approved 并合并回 docPath；状态无法判断 → Open Questions；Registry 无来源 → 删除错误项或补来源。

BF2 · Plan 建立双向覆盖

function Plan.validateDesignCoverage(designDoc, tasks):
  require designDoc.status == approved
  read Implementation Item Registry
  validate every task.designCovers reference
  for each item in Registry:
    required    → require at least one task covers item.id
    verify-only → require verification method
    deferred/n/a → require rationale and confirmation
  output Design → Task Coverage Matrix

异常：Full 旧文档无 Registry → 回 Design 回填；Standard 无 Design → N/A (Standard)；task 引用未知 ID → 计划与设计版本漂移，停止确认。

BF3 · Build 保留实施映射

function Build.completeTask(task, implementationResult):
  lock task scope and designCovers
  implement and verify task
  collect changed files and test evidence
  report completed designCovers
  reject missing or extra claimed IDs

所有 task 完成后汇总 designCovers。Plan 有、但没有任何已完成 task 报告的 required ID，Build Gate 失败。

BF4 · Verify 建立设计符合性证据

function Verify.auditDesignConformance(designDoc, plan, buildResult):
  read Registry and Coverage Matrix
  for each required or verify-only item:
    identify test, inspection, demo or manual proof
    run or collect fresh evidence
    record pass or fail with evidence
  if any item failed or lacks evidence:
    return to Build

Verify 继续保留现有 SC、路径和约束核对；Design Evidence 是新增维度，不替代 Define 验收。
