# refactor-clean：清理型重构

删死代码、清未用依赖、消除重复。不改架构、不加功能——只做减法。

> 通用方法论参考 everything-claude-code v1.2.0 refactor-cleaner agent (MIT)

## 什么时候用

- 用户说"清理一下 / 删死代码 / 清理依赖 / 去重"
- Review 阶段发现冗余代码，回来清理
- Build 中发现已有代码碍事，先清再继续

## 什么时候不用

- 架构型重构（改设计模式、拆分模块、抽接口）→ 走 dev-design
- 正在赶功能、代码库不稳定、没有测试覆盖 → 先稳住再清理
- 不理解为什么代码存在 → 先搞懂再动手

## 流程

### Step 1: 确认测试基线

跑一遍现有测试，确认当前状态是通过的。重构前测试就挂着，后面分不清是你弄坏的还是本来就坏。

```bash
# 项目的测试命令（npm test / go test / pytest 等）
```

测试不过 → 停。先修测试或和用户确认再继续。

### Step 2: 检测

找出要清理的内容。按类型分批，不混着来：

| 类型 | 找什么 | 通用方法 |
|---|---|---|
| 死代码 | 未使用的函数/类/变量 | grep 引用、静态分析工具 |
| 未用 export | 导出了但没人 import | 搜索 import 语句 |
| 未用依赖 | 装了但没用的包 | 包管理器分析 |
| 重复代码 | 做同一件事的多份实现 | 搜索相似函数名/逻辑 |

如果项目是 JS/TS（有 package.json），Read references/js-refactor-tools.md 获取专用工具链。

### Step 3: 审查

工具报的不一定真该删。逐项检查：

- **动态引用**：`import()` 动态导入、字符串拼接路径、反射调用 → 工具检测不到但在用
- **Public API**：导出给外部消费者的接口，即使内部没用也不能删
- **配置/约定引用**：框架约定的文件名（如 `middleware.ts`、`layout.tsx`）、配置文件引用的路径
- **git history**：最近改过的代码可能是在建的功能，别删人家正在写的

按风险分级：

| 级别 | 判断标准 | 处理 |
|---|---|---|
| **安全** | grep 无引用、非 public API、非动态导入 | 直接删 |
| **谨慎** | 可能有动态引用、框架约定 | 和用户确认再删 |
| **高风险** | Public API、共享工具函数、近期活跃 | 不删，标记留着 |

### Step 4: 最小删除

一次删一类，每类一个 commit：

1. 先删未用依赖（影响面最小）
2. 再删未用 export / 死函数
3. 再删未用文件
4. 最后合并重复代码（影响面最大）

每删一批立即跑 Step 5。不要攒一堆一起删——出问题了定位不到是哪批弄坏的。

### Step 5: 验证

每批删除后：

```bash
# 1. build 还过吗
# 2. 测试还过吗
# 3. 有没有新的 console 报错
```

任何一项不过 → 立即回滚这批，检查哪个删错了。

### Step 6: 记录

commit message 说清楚删了什么、为什么安全：

```
refactor: remove 3 unused utility functions

Removed: formatLegacyDate(), parseLegacyConfig(), migrateLegacyData()
Reason: grep -r 确认无引用，git log 显示最后使用在 6 个月前的
migration commit 中被替换。build + tests pass。
```

如果删除量大，在 commit body 列清单。

## 重复代码合并

发现多份做同一件事的实现时：

1. 找出所有重复版本
2. 选最好的那份（测试最全 / 功能最完整 / 最近维护）
3. 把其他版本的调用方改成用选中的版本
4. 删掉其他版本
5. 跑测试确认

不要"取各家之长合并成新版本"——改得越少越安全。

## 不要

- 不要没跑测试就开始删——Step 1 是硬前置
- 不要一次删多类——一类一 commit，出问题能定位
- 不要工具说删就删——Step 3 审查是关键，动态引用和 public API 工具看不到
- 不要顺手改风格/加功能——这是清理，不是重构 + 改进的混合体
- 不要删不理解的代码——搞不清为什么存在就别动
