# 战术 DDD 建模（条件指南）

> **何时 Read**（writing Step 1 条件触发）：设计涉及 **≥2 个限界上下文**（跨仓 / 跨服务 / 跨独立部署单元），或涉及**持久化数据模型**（新表 / 改表 / 跨表关系）时必读。单上下文、无持久化模型的小改不硬套——决策数量按复杂度，不硬凑。
>
> 战略层原则（域按实体拆 / 高内聚低耦合 / 总分结构）见 `references/writing-principles.md` 准则 1；本文只管**战术层**——上下文里面长什么样、上下文之间怎么引用。

## 术语表

每个术语对应一个它防住的坏行为——用的时候知道为什么用：

| 术语 | 定义 | 防的坏行为 |
|---|---|---|
| 限界上下文 Bounded Context - BC | 一套域语言的适用边界，通常对应一个仓 / 服务 / 独立部署单元。同一名词跨上下文可以有不同语义 | 把跨服务边界画成同一个域，设计出跨库 join / 直读对方表 |
| 聚合根 Aggregate Root - AR | 上下文内一组强一致实体的**身份锚点 + 事务边界**。子实体 FK 只指聚合根；外部只能拿聚合根 ID 引用整个聚合 | 域内表关系平铺、子表 FK 指向混乱，基数演进（1:1 → 1:N）时没有身份锚点可推演 |
| 实体 Entity | 有独立身份、挂在聚合根下的对象（FK → AR） | 所有表平级，看不出一致性边界在哪 |
| 域服务 Domain Service | 不自然归属任何实体的领域操作（跨聚合协调 / 对外解析），以服务形式存在，签名显式 | 操作被硬塞进某个实体类，或散落成 util 无归属 |
| 域语言 Ubiquitous Language | 每个上下文内部一致的命名；跨上下文**不强求统一**，靠映射显式对齐 | 同名字段（如 `project_id`）跨上下文多种语义，没人说得清哪个是哪个 |

## 跨上下文引用四规则

跨上下文的每条引用逐条过：

1. **只存 ID**：引用字段只存被引用上下文的 ID，不冗余存对方业务数据（冗余 = 一致性问题的种子）
2. **各有身份**：每个上下文有自己的聚合根和独立身份——A 上下文的 `agent_id` 与 B 上下文的 `project_id` 各说各的域语言，无命名冲突
3. **不共享实体**：跨上下文通信 = ID 传递 + API 调用；不共享表、不跨库 join、不直读对方存储
4. **映射显式**：同名 / 相近字段跨上下文语义不同时，在文档术语表或引用方向表里显式澄清

## 建模步骤（喂结构骨架 / 域设计）

1. **圈上下文**：列出设计涉及的仓 / 服务 / 部署单元，每个是一个限界上下文；总图节点标注上下文归属
2. **找聚合根**：每个上下文内识别身份锚点 + 事务边界；实体挂根（FK → AR）；UNIQUE 约束显式标出
3. **归位操作**：不归属任何实体的操作 → 域服务（给出签名 + 输入输出）
4. **过引用**：跨上下文引用逐条过四规则，产出**引用方向表**：

   | 引用字段 | 方向 | 被引用上下文 | 传递方式 |
   |---|---|---|---|
   | `project_id` | → | 项目上下文 | 存 ID |
   | `billingProjectId` | → | 账本上下文 | 传值（API 入参，不落库） |

5. **演进检查**：现有唯一约束 / 基数（如 1:1）将来放开（1:N）时，身份设计能否支撑——子表 FK 锚聚合根则天然不受影响；锚了业务键（如复合业务字段）放开时就要连带重构

## 检查清单（Step 3 架构审核 + 全文 Review 共用单源）

- [ ] 每个上下文有且仅有明确聚合根；子实体 FK 锚聚合根，不锚业务键
- [ ] 跨上下文引用只存 ID——出现被引用上下文的业务字段冗余即违规
- [ ] 无跨上下文 join / 直读对方表 / 共享实体表
- [ ] 域服务有显式签名，不散落成 util
- [ ] 同名字段跨上下文语义已在术语表 / 引用方向表澄清
- [ ] 演进路径已检查（唯一约束放开时子表不受影响）

## 示例：三上下文全景（脱敏骨架）

学结构不照搬措辞——节点标上下文归属，聚合根 / 实体 / 域服务各归其位，跨上下文只走 ID：

```
┌─────────────────────────────────────────────────┐
│ Agent 限界上下文（agent 服务）                     │
│                                                 │
│  聚合根: Agent                                   │
│    agent_id    UUID PK   ← 本域身份              │
│    project_id  TEXT      ← 项目上下文引用（只存 ID）│
│    tenant_id / user_id   ← 租户 / 用户上下文引用   │
│    UNIQUE (tenant_id, project_id)  ← 当前 1:1    │
│                                                 │
│  实体: Consumer / Knowledge（FK → agent_id）      │
│  域服务: Billing.resolve(agentId, mode)           │
│          → billingProjectId（传值给账本上下文）     │
└───────────────┬─────────────────────────────────┘
                │ 只传 ID + API 调用，不共享实体
                ▼
┌─────────────────────────────────────────────────┐
│ 项目 限界上下文（project 服务）                     │
│  聚合根: Project（projectId PK / files / 权限）    │
│  权限、文件由本上下文 API 提供，外部不直读表          │
└─────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────┐
│ 用量账本 限界上下文（billing 服务）                  │
│  聚合根: UsageDetail（projectId 归属键 = 传值而来）  │
└─────────────────────────────────────────────────┘
```

**引用方向表**：

| 引用字段 | 方向 | 被引用上下文 | 传递方式 |
|---|---|---|---|
| `Agent.project_id` | → | 项目上下文 | 存 ID |
| `Consumer.consumer_project_id` | → | 项目上下文 | 存 ID |
| `billingProjectId` | → | 账本上下文 | 传值（API 入参） |

**演进检查**：当前 `UNIQUE (tenant_id, project_id)` 限 1:1；放开 1:N 只删约束——Consumer / Knowledge 的 FK 全锚 `agent_id`（聚合根），不受影响。若当初 FK 锚了 `project_id`（业务键），放开时子表全得跟着改。
