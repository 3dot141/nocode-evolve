# 跨仓库只读检查 — 先枚举再进入，不凭记忆挑路径

## 为什么

worktree 约定是「平级目录、每分支一份」——一个逻辑仓库在磁盘上有主仓 + N 份 `<repo>-<branch_flat>/` 拷贝，「仓库名 → 路径」不再一一对应。只读进入若沿用记忆或上下文里残留的路径，很容易进到别的任务留下的 worktree——看到过时 / 错分支的代码，基于它得出的结论整个作废。

## 三步：枚举 → 选择 → 验证

1. **枚举**：`git -C <目标仓库任一已知拷贝> worktree list` 一次列出主仓 + 全部 worktree 及各自分支，以此为**唯一候选集**。连一个已知路径都没有 → `ls <parent>` 找 `<repo>` 前缀目录；仍不确定就问用户，不猜。
2. **选择**：候选集里有与当前工作分支**同名**的 worktree → 进它（跨仓库工作的另一半在那）；没有 → 进主仓看 main。其他用途（看历史 / 对比某分支实现）按需选，但路径必须出自候选集。
3. **验证**：进入后第一条命令核对身份——`git -C <path> branch --show-current`（必要时加 `remote -v`）确认分支符合预期；不符 → 停下报告，不将错就错继续读。

枚举与验证都是只读命令，可以并成一个 Bash call。

## 委派搜索时把已验证路径传下去

跨仓库检索委派给 subagent（semble-search / Explore 等）时，prompt 里**显式写死已验证的目标路径**，不要让 agent 按仓库名自己猜——agent 拿不到本会话的验证结果，会重犯同样的错。

## 与 rule-git-worktree 的分界

- 本条只管**只读**进入（Read / rg / git log / 对照实现），不建 worktree。
- 要去那个仓库**改文件** → 走 rule-git-worktree「跨物理分仓：关联仓库」节（同名分支建 / 复用 worktree）。

## 不要

- 不要沿用上下文早前出现过的 worktree 路径而不重新枚举——那可能是别的任务留下的
- 不要在 parent 目录上层直接 rg / find 扫代码——多份拷贝重复命中，结果混乱；先定位单一正确拷贝再搜
- 不要验证不符还继续读、想着事后补救
