# post-merge — 合并后流转（已并入 dev-land Step 3）

代码合并后的收尾动作。当前：飞书任务流转（状态流转 + 评论修复 + 工时登记三动作）。预留：通知、changelog、部署触发。

## 何时读本文件（两个时机）

1. **材料收集阶段**（SKILL.md Step 2e）：有任务号时读，拿「典型流转映射」+ 查当前状态 → **推定目标状态写进全景计划和定时监控上下文**，合并后不再问
2. **合并后执行**：Merge 路径 merge 成功后 / PR 路径 pr-check 命中 MERGED 后 / 用户直接说「PR 合了 / 流转任务 / 任务状态改一下」

## Step 1: 任务号来源

飞书任务号格式：`#f-xxx` / `#g-xxx` / `#m-xxx`（Meego 工作项 ID）。

- **PR 路径**：监控上下文里已捕获（材料收集时提取），直接用
- **Merge 路径**：材料收集时从 push range 提取
  ```bash
  git log "<base>..HEAD" --format=%B | grep -oE '#[fgm]-[a-z0-9]+' | sort -u
  ```
- 没有任务号 → 全景计划写「无流转」，合并后跳过 Step 2

## Step 2: Lark 任务流转（三动作）

调 `平台原生 Skill 调用`（lark-project）一次传入三动作参数，把任务流转到**全景计划定死的目标状态**：

| 动作 | 参数来源 | 缺省行为 |
|---|---|---|
| 状态流转 | 全景定死的目标状态 | — |
| 评论修复 | 修复摘要（材料收集阶段信息生成，全景已展示）：一句话结论 + 变更规模（N files, +M/-L）+ PR 链接 | 摘要生成不了（信息不足）→ 跳过评论，报告原因 |
| 工时登记 | 分钟数两级来源：默认 = 全景展示的**会话任务段估算**（本次 land 关联任务在会话中的起止时长，用户回「OK」即确认估算）；用户回应带显式值（「OK，工时 3h」→ 180；`45m` → 45；纯数字 → 分钟）则覆盖估算 | 估算不出任务段起止且用户未给值 → 不传，报告原因 |

评论与工时的落地方式由 lark-project 透传契约负责（评论走 meegle `comment add`，工时走 lark-project 内置 worklog 脚本），本 skill 只传参，不直接操作。

- 典型流转映射（材料收集阶段推定用）：缺陷/任务类 `组员开发 → 创建者验收`
- **前置条件**：有任务号 + lark-project 可用。不满足 → 跳过，报告原因，不报错

## Step 3: 其他 post-merge 动作（预留）

扩展位（当前为空）：通知（Slack / 飞书群 / 邮件）、Changelog 条目、部署触发 / 灰度推进。每项独立 try——一项失败不阻塞其余。

## 不要

- 不要在 merge 前进入执行段 — 这是 post-merge 动作（材料收集阶段只读映射做推定，不执行）
- 不要因 MCP 不可用报错阻塞 — 跳过 + 报告，不影响收尾
- 不要对非「组员开发」状态的任务强行流转 — 状态不对时报告让用户判断
- 不要对典型映射覆盖不了的工作项类型硬套流程 — 需求（story）走节点流而非缺陷状态流，且同一任务号可能挂着多支未合分支，推进节点会虚报进度（生产实证）→ 停手报告「需人工判断」，交用户决定
- 工时估算只按会话任务段起止时长（有任务日志/会话记录证据），不按 commit 规模或改动行数折算；估算值必须先在全景展示并经用户确认（「OK」）才登记，未经确认不落
- 不要因评论或工时失败回滚重做状态流转 — 三动作独立 try，各自如实报告结果（「已流转，评论失败」）
