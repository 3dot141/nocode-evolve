# 反馈纪律（Feedback Discipline）

当你**收到** review 反馈在处理时用此模式。核心：技术严谨 > 社交表演。performative 同意会掩盖"还没验证"。

---

## 禁语表（不要说这些）

| 禁语 | 为什么禁 | 改说 |
|---|---|---|
| "Great catch!" | 表演式赞美，掩盖你还没验证它对不对 | 直接说验证结果："已核对，确实是 bug，修法是 X" |
| "You're absolutely right" | 还没验证就先认同 = 假同意 | "核对后确认 / 核对后不成立，因为 Y" |
| "Thanks for the feedback" | 社交填充，无信息 | 直接进入处理："第 1 条：..." |
| "Good point, I'll fix it" | 没说清你是否真同意、怎么修 | "第 2 条成立，改为 X" 或 "第 2 条不成立，理由 Y" |
| "Let me address all your concerns" | 暗示全盘接受，跳过了验证 | 逐条给结论（接受 / 反驳 / 需澄清） |

**原则**：每条反馈的回应是一个**技术结论**（接受+修法 / 反驳+证据 / 需澄清），不是一句情绪。

---

## unclear → 全部停

任何一条反馈看不懂（不确定 reviewer 指的是哪、想要什么、为什么）：

- **停下，问清楚**。不猜。
- **不做部分实现**——把"懂的几条"先改了、"不懂的"留着 = 半成品埋雷。半懂的改动比不改更危险。
- 问法具体："你说的 X 是指 file:line 这里吗？你想要的是 A 还是 B？"

---

## YAGNI check（"以备将来"先 grep）

reviewer 说"加个 X 参数 / flag / 抽象层以备将来扩展"：

```bash
grep -rn "<拟加的符号 / 概念>" .   # 现在真有人要用吗？
```

- 现在没有任何调用方 / 需求 → **push-back**："当前无使用点，按 YAGNI 暂不加，等真有需求再加。"
- 真有近期明确需求 → 加，并指出需求出处。

---

## push-back 协议（技术正确 > 社交舒适）

reviewer 的建议技术上站不住时，礼貌但坚定反驳：

1. **先验证**：跑一下 / 查 spec / 看代码，拿到事实。
2. **给证据**：不是"我觉得不对"，是"按 X 测，结果是 Y，所以这条不成立"。
3. **保持具体**：针对那一条，不否定整个 review。
4. **接受被反驳**：如果你的 push-back 也被证伪，立即认并改。

> push-back 不是对抗，是对正确性负责。reviewer 也会错——你照搬错的建议，bug 是你的。

---

## 外部 review 处理流程

```
收到 review
  → 逐条读，有 unclear → 全部停，问清楚（不部分实现）
  → 每条：先验证（跑 / 查 / 读代码），不先认同
      ├─ 验证成立 → 接受，给修法 → 改 → 回 Build → Verify
      ├─ 验证不成立 → push-back，给证据
      └─ "以备将来"类 → YAGNI grep → 无使用点则 push-back
  → 所有条目有技术结论（无禁语、无表演式同意）
  → 改动完成 → 回 Verify 重测（fix 可能引新 bug）
```

---

## 来源分级（权重不同）

| 来源 | 权重 | 处理 |
|---|---|---|
| **Human partner**（一起干活的人 / 用户） | 高 | 认真对待，但仍验证；不懂就问 |
| **External reviewer**（外部 / 不熟上下文） | 中 | **先验证再实现**，可能缺上下文 |
| **自动 / AI reviewer**（Codex / linter / bot） | 中低 | 一律先验证，误报率高；交集（多源都指出）= 高置信 |

**注**：来源权重影响"先信多少"，**不影响"要不要验证"**——所有来源都要验证后再动手。
