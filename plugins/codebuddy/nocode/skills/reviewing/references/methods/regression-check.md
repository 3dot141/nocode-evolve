# 方法卡：regression-check（回归检查——删除/替换的行为有没有在别处重建）

> reviewing 框架方法库 · 评审方法之一。**适合**：代码 diff——尤其是重构类改动（删代码 / 替换实现 / 挪逻辑位置）。**不适合**：纯新增代码（没有"删除的行为"可核对）、方案选型判断（用 `red-blue-adversarial`）、高层设计评审（用 `perspective-based`）。
>
> ⚠️ 外部实证（前置调研 §2.2）：Claude Code `/code-review` 的固定分析角度之一——"对 diff 删除或替换的每一行，说出它原本保证的不变量/行为是什么，然后到新代码里找这个不变量在哪重新建立"。这类"改动有没有把原有行为弄丢"的问题，现有 `checklist`（看维度全不全）和 `error-mechanism`（看有没有踩常见错误坑）都不专门覆盖，是这次调研发现的真实缺口。

## 一、维度 / 思路

regression-check 不看"新代码写得对不对"，专看"**旧代码被删/被改的那部分,原本承担的职责有没有人接手**"：

1. **定位删除/替换点**：diff 里每一处 `-` 开头的行（或被完整替换的函数/分支），标出它在新代码里对应的位置。
2. **提炼原有不变量**：这行/这段代码原本在保证什么？（例如"确保用户已登录才能继续""这个字段永远不为 null""失败时要回滚"）。
3. **核对新代码是否重建**：去新代码里找——这个不变量现在由谁负责维护？如果找不到对应的保证，就是一处潜在的行为回归。

**纪律**：① 每一处删除/替换都要走完"定位→提炼→核对"三步，不能因为"看起来是无关紧要的旧代码"就跳过；② 找到的回归必须落到 `file:line`（新旧两处都要），说清楚"旧代码在哪保证了什么，新代码现在谁都没管"；③ 单纯的代码搬家（原样挪到另一个文件，逻辑不变）不算回归，只有"不变量本身丢了"才算命中。

## 二、输出契约

产出 `findings[]`，映射 `references/findings-contract.md`：

- 每条 finding：`axis` = `回归检查`；`location` = 新代码里"应该但没有"重建该行为的位置（旧代码位置作为 `evidence` 的一部分给出）；`evidence` = 旧代码原文 + 它保证的不变量描述；`severity` = C/W/S（不变量丢失导致功能缺失或数据错误 → critical；影响范围有限的边缘行为丢失 → warning）；`fix` 给 Structural Remedy（在哪个新位置补回这个不变量）。
- 受 Evidence Gate 约束：必须同时给出旧代码 `location` 和新代码里"应有但缺失"的具体位置，缺其一降 `kind=open-question`。
- `verdict.counts` 汇总。
