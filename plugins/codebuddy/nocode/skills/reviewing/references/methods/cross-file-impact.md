# 方法卡：cross-file-impact（跨文件影响追踪——改动会不会破坏调用方）

> reviewing 框架方法库 · 评审方法之一。**适合**：代码 diff——尤其是改了函数签名 / 返回值语义 / 导出接口 / 公共类字段的改动。**不适合**：纯内部实现细节且未改变对外接口的改动（没有"调用方"需要追踪）、方案选型判断（用 `red-blue-adversarial`）。
>
> ⚠️ 外部实证（前置调研 §2.2）：Claude Code `/code-review` 的固定分析角度之一——"diff 改的每个函数，找它的调用方，检查这次改动会不会破坏调用点原有的假设"。这类"改动本身对不对"之外、"改动波及范围有多大"的问题，现有 `checklist` 和 `error-mechanism` 都是盯着"这段代码本身"，没有专门做"这段代码外面还有谁依赖它"这层检查，是这次调研发现的真实缺口。

## 一、维度 / 思路

cross-file-impact 不看"这个函数改得对不对"，专看"**改了这个函数之后，外面调用它的地方会不会跟着出问题**"：

1. **定位改动的对外接口**：diff 里改动了签名（参数增删/改类型）、返回值语义、导出的类/字段的每一处，都是要追踪的起点。
2. **找调用方**：在代码库里搜索这个函数/类/字段的调用点（不限于本次 diff 涉及的文件）。
3. **核对调用点假设**：逐个调用点检查——它是不是假设了旧的签名/语义？改动后这个调用点还成立吗？会不会编译不过、运行时报错，或者悄悄依赖旧行为却不报错（最危险的一类）。

**纪律**：① 每一处对外接口改动都要真的搜索调用方，不能凭"应该没人这么用"猜测——**这条受 Evidence Gate 约束尤其严**，指控"调用方会出问题"必须实际找到调用点代码；② 找不到调用方不代表安全，可能是搜索范围不够（如反射调用、动态字符串拼接方法名），这种情况标 `open-question` 而不是直接判无风险；③ "悄悄依赖旧行为但不报错"这类沉默故障（比如返回值从"必然非空"改成"可能为 null"，调用方没做判空但恰好没触发过）优先级最高，因为它不会在测试或编译阶段暴露。

## 二、输出契约

产出 `findings[]`，映射 `references/findings-contract.md`：

- 每条 finding：`axis` = `跨文件影响`；`location` = 调用点的 `file:line`（不是改动点本身，是受影响的调用方）；`evidence` = 调用点原文 + 它依赖的旧假设是什么；`severity` = C/W/S（会编译失败或运行时报错 → critical；"悄悄依赖旧行为不报错"的沉默故障 → critical；仅需要留意但不影响正确性 → warning）；`fix` 给 Structural Remedy（改调用点适配新接口，或改接口保持向后兼容）。
- 受 Evidence Gate 约束：必须给出实际找到的调用点 `file:line`，找不到调用方但怀疑存在（如反射/动态调用）→ 降 `kind=open-question`，不直接判定有问题也不直接判定无风险。
- `verdict.counts` 汇总。

> **场景 / 视角 / 派发 / 档位 / 升档 / CLAIM 剥离 / codex 降级见 skeleton §1–§3、§4.0–§4.2，本卡不复述。** 本方法是"代码质量"场景正确性视角下的一种打法，与 `checklist`、`error-mechanism`、`regression-check` 可叠加执行（见 skeleton §3 场景表「代码 diff/代码质量」行）。
