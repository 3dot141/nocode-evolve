# Source Comment Contract

源码注释的职责是保存**代码本身无法表达的知识**，让不了解当前会话的维护者仍能安全修改代码。注释解释 why、约束和失效条件，不逐行翻译语法；零注释不是缺陷，丢失必要理由才是。

## 判定树

```text
这段知识能否用更清楚的命名、类型或结构表达？
  ├─ 能 ──→ 先改代码；不要用注释掩盖可读性问题
  └─ 不能
      │
      ├─ 不写会隐藏约束、理由或失效条件 ──→ 必须写 why-comment
      └─ 只是复述代码正在做什么 ─────────→ 不写
```

测试证明行为成立，但不能自动保存外部契约和历史理由；“测试已绿”不是省略必要注释的理由。

## 必须保留的知识

改动涉及下列任一项，且信息无法从代码直接推出时，必须在最接近约束的稳定位置写注释：

- 顺序要求、一致性边界、并发或幂等不变量
- 外部协议、版本差异、兼容分支、迁移或 sunset 条件
- 失败、恢复、降级、安全或数据保护语义
- 阈值、超时、重试次数、正则等非显然取值的来源与变更条件
- workaround 的根因、适用范围和删除条件
- 生成链、单一事实源或平台适配中容易被“简化”破坏的边界
- 类型或函数签名无法完整表达的公共契约

注释至少回答适用问题中的两个：为什么存在？违反会怎样？依据来自哪里？何时可以修改或删除？

## 放置与写法

- 文件级注释：仅当文件职责、生成关系或不可破坏边界无法从目录和导出项看出时使用。
- API / 类型注释：只补充签名表达不了的调用契约、失败语义和兼容条件。
- 行内或块注释：紧邻被保护的顺序、分支、常量或 workaround，优先写在逻辑前。
- 注释使用项目读者能懂的自然语言，不搬运 `BF1`、`Q2` 等设计文档编号。
- 描述原因和条件，使实现重构后注释仍可能成立；不要写“遍历数组”“返回 enabled”这类语法旁白。
- 不按文件行数、函数数量或“每行一条”追求注释密度。

## 生成文件

生成物禁止手改。需要保留的理由写入单一源码、模板或编译器，并在目标格式支持注释时随生成链传播；JSON 等不支持注释的格式，把理由保存在其生成源码或相邻的规范性文档中，不伪造非法字段。

## 自检

对本次改动逐项检查：

1. 非平凡逻辑中的必要 why-comment 是否齐全。
2. 既有注释是否仍与实现、版本和删除条件一致。
3. 是否用注释掩盖了本可通过命名、类型或拆分解决的问题。
4. 是否新增了只复述语法、可能比代码更快过时的噪音。
