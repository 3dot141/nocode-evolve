# Step 2 展开：逐交互拆解

> 术语（状态覆盖 / 行为规格 / 控件四态）单源在 `{QODER_PLUGIN_ROOT}/skills/references/ix-vd-contract.md`。

## 2a. 提取交互清单

从 PRD 使用路径提取每个需要设计的**交互点**。路径是"用户要完成什么"，交互是"用户在每一步具体做什么操作"。

### 示例

PRD 路径 `订单.P1`（用户下单）拆出交互：

- 订单.P1.1: 浏览商品列表
- 订单.P1.2: 查看商品详情
- 订单.P1.3: 加入购物车
- 订单.P1.4: 编辑购物车（改数量/删除）
- 订单.P1.5: 确认订单（地址/备注）
- 订单.P1.6: 选择支付方式并提交

### 跨域路径

跨域路径（`跨域.N`）展开成端到端交互链——把串联的几条领域路径的交互连成一条用户实际走完的流程。

### 系统路径

系统路径（`系统.N`）无界面不进交互清单，但要识别"触发后用户看到什么"（如支付回调后支付等待页切成成功态），纳入相关交互的状态覆盖。

## 2b. 逐交互五块格式

每个交互写进 `.ix.md` 的格式：

```markdown
### 订单.P1.1: 浏览商品列表

**竞品做法**
- [SOURCE: url] 竞品A: 瀑布流 + 筛选栏左侧固定
- [SOURCE: url] 竞品B: 卡片网格 + 顶部标签筛选

**设计决策**
[我们怎么做 + 为什么（引用竞品 + PRD 约束）。竞品做法分歧 / 无竞品参照 / 核心路径新模式 → 标 [TRADEOFF]]

**线框图**
[ASCII/文字版布局: 区块划分 + 内容清单]

**状态覆盖**
| 状态 | 表现 |
|---|---|
| 正常 | 商品列表正常展示 |
| empty | "暂无商品" + 引导 |
| loading | 骨架屏 |
| error | 加载失败 + 重试 |

**行为规格**
- 触发: 进入页面自动加载；滚动到底部加载下一页
- 规则: 筛选变更即时刷新列表；筛选与排序可叠加
- 退出: N/A——无持续状态
- 反馈: 列表刷新（过渡形式 = 原型参数）
```

### 五块要求

| 块 | 硬约束 |
|---|---|
| 竞品做法 | 每条标 `[SOURCE: url]`，不凭印象编 |
| 设计决策 | 必须引用竞品做法或 PRD 约束作为依据，不拍脑袋；有争议标 `[TRADEOFF]` |
| 线框图 | ASCII 布局，标出区块和内容，不能只文字描述 |
| 状态覆盖 | normal / empty / loading / error 缺一不可 |
| 行为规格 | 触发 / 规则 / 退出 / 反馈 四字段必填；不适用填 `N/A + 一句理由`；只到语义级，不写样式值和时序参数 |

### 行为规格：四字段怎么填

**统一结构，无分级**——所有交互同一套四字段，复杂度由字段内容自然伸缩，不预判"这个交互简单可以少写"（那是官方降级通道）。

| 字段 | 定义 | 注意 |
|---|---|---|
| 触发 | 用户做什么 / 什么条件启动这个交互 | 含 hover 触发的内容变化、disabled 的进入条件 |
| 规则 | 交互进行中的逻辑（展示什么、维持条件、可做什么） | 多步 / 拖拽 / 流式用 ASCII 状态机代替文字 |
| 退出 | 怎么结束 / 取消 / 回退（浮层怎么消失、焦点回落到哪） | 浮层类交互此字段禁填 N/A |
| 反馈 | 用户得到的响应语义（出现 / 消失 / 刷新） | 只写语义；时长 / 曲线等参数由原型定，经回流登记 |

**极简示例**（跳转类，每字段一行封顶，不为填而编内容）：

```markdown
**行为规格**
- 触发: 点击「设置」导航项
- 规则: 跳转设置页
- 退出: N/A——无持续状态
- 反馈: 页面切换
```

**浮层示例**（维持与退出是重灾区，必须写全）：

```markdown
**行为规格**
- 触发: hover 凭证数字
- 规则: 浮层展示来源摘要 + 定位入口；鼠标移入浮层保持显示；浮层内链接可点击
- 退出: 移出数字与浮层后短暂缓冲再消失；Esc 立即关闭
- 反馈: 淡入淡出（时长/曲线 = 原型参数）
```

**N/A 是检查不是逃生口**：写 N/A 前先问"这个交互真的没有持续状态吗？"——hover / 展开 / 拖拽 / 弹层类交互填 N/A 即 Red Flag。

**边界**：hover 变色、按下下沉这类**纯样式反馈**不进行为规格（那是 pd-vd 控件四态的地盘，判据见 ix-vd-contract）；原型阶段发现 IX 漏定义的行为，走 `.ix.md`「下游澄清回流」节登记，不许只落在原型代码里。

## 2c. 分批用户校验

按争议度分两路，不逐个轰炸：

- **`[TRADEOFF]` 交互**（设计决策有争议）→ 逐个展示校验
- **常规交互**（竞品一致、标准模式：列表/表单/toggle）→ 按路径打包，一批一次展示，用户整批锁定或点名抽查

校验反馈的处理：

- "竞品做法对吗？漏了什么？" → 补调研
- "设计方向不对，改成 X" → 调整设计
- "够了 / 没问题" → 锁定（整批锁定 = 批内每个交互锁定）
- 同一交互最多 3 轮

**全部交互锁定后才进 2d。**

## 2d. IA 汇总 + 场景脚本 + 完整性四查

### IA 汇总

从**锁定的交互**汇总出（不是凭空画）：

- 页面/视图清单 + 层级关系
- 导航结构
- 每个页面包含哪些交互
- 页面间的跳转关系

### 场景脚本

每条 PRD 路径至少一个**带具体数据的走查实例**——抽象交互清单让人难审，具体场景一读就知道对不对：

```markdown
### 场景: 订单.P1 用户下单（脚本）
用户: 首次购买的新客小王
1. 打开首页，看到商品瀑布流（订单.P1.1）
2. 点开「无线耳机」详情，查看参数和评价（订单.P1.2）
3. 点「加入购物车」，购物车角标 0→1（订单.P1.3）
4. 进购物车改数量 1→2，合计实时更新（订单.P1.4）
5. 确认收货地址，提交订单进入支付（订单.P1.5 → P1.6）
```

每步引用交互 ID。场景脚本同时是：用户批准 IA 的可读材料、pd-vd 原型 demo 编排的直接来源、dev-verify E2E 场景的骨架。

### 完整性四查

四查判据表在 SKILL.md Step 3。这里是落 `.ix.md` 的格式：

```markdown
## 完整性四查
| # | 查项 | 结果 | 备注 |
|---|---|---|---|
| 正向 | PRD 路径 → 交互 | ✅ 6/6 路径有交互 | |
| 反向 | 交互 → PRD 路径 | ✅ 23/23 交互有归属 | |
| 连通 | 页面入口可达 | ✅ 孤岛 1（404 页，已标注） | |
| 出口 | error/empty 有下一步 | ✅ | 订单.P1.6 支付失败 → 重试/换支付方式 |
```
