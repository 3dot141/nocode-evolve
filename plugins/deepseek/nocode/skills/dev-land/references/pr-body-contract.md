# PR title/body 内容契约

> 单源：本文件是 `dev-land` PR 路径生成 title/body 的唯一定义处，`references/prflow.md` Step 1、`references/examples/example-land-pr.md` 只引用本文件，不重复字段细节——改契约只改本文件。

## 适用场景

`dev-land` PR 路径 Step 2e 材料收集生成 title/body 时；或用户在本 skill 流程内显式要求「总结 push 内容 / 给标题描述 / PR description」。

**不适用**：单纯问"push 完了吗 / push 成功没"等状态查询。

## 输出结构

**标题**: 一行 ≤ 50 字, 概括最大变更轴 (含版本号 if any). 不要逐条罗列 commit, 提炼共同主题.

**描述**：面向 reviewer / 后续读者，信息完整优先于固定字数。简单改动通常控制在 300 字内；复杂改动不设硬上限，以完整保留独立问题轴、关键取舍、评审问题和验证证据为准，超过约 800 字时再压重复信息。

正文固定包含「背景 / 方案 / 重点评审」三个板块。按复杂度选择写法：

| 结构 | 判定 | 写法 |
|---|---|---|
| 简单 | 单一问题轴、单一解法、无跨边界迁移 | 背景/方案各一段；重点评审列 1–2 个真实路径，或明确无特别风险 |
| 复杂 | 有 2 个以上独立问题轴，或涉及迁移、并发、权限、持久化、兼容/回滚等强边界 | 背景用编号拆问题；方案按 `方案 N` 逐项写「问题 → 方案」；重点评审按优先级列真实文件路径 |

```markdown
## 背景
<简单：上下文 + 现状问题及后果>
<复杂：1. 问题/成因/影响；2. ...。只讲问题，不提前写方案>

## 方案
<简单：关键思路、取舍及涉及模块>
<复杂：每个方案项重复以下结构>

### 方案 1：<语义标题>
**问题**：<对应背景编号 + 一句问题，避免整段重复>
**方案**：<具体做法、关键取舍和代码落点>

## 重点评审
> <为什么优先看下面这些位置：覆盖面广、逻辑复杂、数据/权限边界关键、或验证仍薄弱>

1. 看 **<Affected 中的真实文件路径>**：<这处为什么重要 + 要判断什么 + 怎样算有问题>
2. 看 **<真实文件路径或最小跨文件集合>**：<...>
```

复杂改动示例（`<...路径>` 生成时必须替换为本次 Affected 中的真实路径）：

```markdown
## 背景

1. workspace 同时承担会话稳定身份和请求写入位置，两个生命周期被绑在一起。
2. 项目移动会联动权限、Session/JSONL 与迁移围栏，产生对话阻塞和恢复分支。
3. JSONL 需要在 W1 写入、W2 恢复时仍能定位，并在归属不明时拒绝读取。

## 方案

### 方案 1：稳定身份与写入位置
**问题**：对应背景 1，稳定身份会随 workspace 移动而变化。
**方案**：稳定身份改按 tenant / user / project；workspace 降为请求级写入位置。

### 方案 2：权限与迁移
**问题**：对应背景 2，移动流程与权限、重发机制互相耦合。
**方案**：保留 AgentPermission 三域，删除 relocation lease 与自动重发。

### 方案 3：持久化读取
**问题**：对应背景 3，跨 W1/W2 后历史定位可能丢失或串读。
**方案**：JSONL 使用持久化 locator 跨 workspace 读取，无法确认归属时 fail-closed。

## 重点评审
> 优先检查覆盖身份生成、历史定位和 write placement 的高影响路径；机械性改名不重复列出。

1. 看 **<0037 去重迁移的实际路径>**：沿首次提交、重试、恢复三条路径核对同一 logical write 是否收敛到同一去重键；出现两条持久化记录即为失败。
2. 看 **<locator 索引与读取实现的实际路径>**：用 W1 写入、W2 恢复场景核对 locator 是否仍唯一命中原会话；漏读或串读即为失败。
3. 看 **<write placement 实现的实际路径>**：追踪写入位置是否只取当前请求 workspace，稳定身份不得反向决定目录；写入旧 workspace 或其它项目即为失败。
```

「重点评审」是 reviewer 的代码导览，不是 Affected 全量复述。只挑最值得花时间的位置，按以下优先级排序：

- 覆盖面广：公共 API、schema、迁移、配置、跨模块入口
- 逻辑复杂：并发、去重、状态恢复、兼容/回滚、索引关系
- 边界关键：权限、数据归属、持久化写入、安全、不可逆操作
- 验证薄弱：关键假设未测、只测 happy path、缺少跨模块证据

每项必须同时回答：

- **看哪里**：来自本次 Affected 的真实文件路径；跨文件接缝列最小必要路径集合
- **为什么看**：覆盖面、复杂度或风险来源
- **看什么**：具体逻辑、边界、反例或证据
- **怎样算有问题**：失败信号或错误后果

确实没有特别风险时保留该板块，写「无特别风险，常规改动」，不要硬编。

核对 push range（检查描述是否遗漏实质变更，二选一）:

- push 前确认: `git log origin/<branch>..HEAD --oneline`
- push 后回看: `git log <old-sha>..<new-sha> --oneline` (`<old-sha>..<new-sha>` 即 `git push` output 给出的那段 range)

commit 列表不逐条搬进描述——GitHub/Bitbucket PR 页面已展示全部 commit; 描述只提炼有实质意义的变更, 琐碎/机械 commit (typo / 格式) 不单独出现.

## 不要

- 为了短而把复杂改动压成一段——独立问题轴、关键取舍、评审判断不得被字数预算吞掉
- 「背景」写成「怎么解决的」——背景讲现状和问题, 不讲方案
- 「方案」和问题对不上——复杂改动按问题轴逐项对应，避免一段话混写多个解法
- 「重点评审」复制整个 Affected——只选高影响、复杂或高风险路径，不做文件清单
- 只列「0037 / 索引 / write placement」等抽象名词——没有真实路径，reviewer 无法直接落到代码
- 编造或留空文件路径——路径必须来自本次 Affected；拿不到路径时明确写未定位，不得用 `****` 或占位符冒充成品
- 只写「这个文件改了 X」——还要说明为什么优先看、具体看什么、怎样算有问题
- 强行编风险 / 未验证项——真没有就写"无特别风险, 常规改动", 不硬凑
- 把标题写成 commit 列表——标题是主题提炼, 不是 commit 拼接
