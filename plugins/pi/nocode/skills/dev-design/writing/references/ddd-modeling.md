# 战术 DDD 建模（条件指南）

> **何时 Read**：设计涉及 ≥2 个候选限界上下文，或涉及持久化数据模型时必读。单边界、无模型变化的小改不硬套。

战略划分先看业务能力、统一语言和一致性边界。仓、服务、团队、代码包、数据库与部署单元都只是**信号**：它们可能反映边界，也可能只是历史组织方式，不能直接一一映射为限界上下文。

## 术语

| 术语 | 定义 | 防止的问题 |
|---|---|---|
| 限界上下文 Bounded Context - BC | 某套统一语言与模型语义有效的边界，围绕清晰业务能力形成 | 把同名概念在不同业务语境里的含义混为一谈 |
| 聚合 Aggregate | 需要在一个事务 / 一致性边界内维护不变量的一组对象 | 为方便画图把所有表都塞进一个超大事务 |
| 聚合根 Aggregate Root - AR | 单个聚合对外暴露的身份与修改入口 | 外部绕过根直接修改聚合内部对象 |
| 实体 Entity | 由身份区分、在生命周期内变化的对象 | 只看字段相等而忽略身份与生命周期 |
| 值对象 Value Object | 由值定义、通常不可变的对象 | 给没有独立生命周期的数据强造 identity |
| 域服务 Domain Service | 无法自然归属于某个实体 / 值对象的领域操作 | 把领域规则散落到 util 或 controller |
| 统一语言 Ubiquitous Language | 上下文内业务与技术共同使用、语义一致的词汇 | 同一个词在同一边界里各说各话 |

## 建模步骤

1. **识别业务能力与语言**：列出用户 / 业务要完成什么，以及每个关键词在不同语境中的含义。
2. **圈候选上下文**：按语言变化点、业务责任与模型所有权划边界；再用仓 / 服务 / 部署等信号验证，而非反向决定。
3. **找一致性边界**：列出必须原子成立的不变量；围绕不变量形成聚合。**一个限界上下文可以包含多个聚合**。
4. **为每个聚合找根**：根是该聚合的稳定身份与唯一外部修改入口；内部实体不被其他聚合直接持有为可变对象。
5. **设计跨上下文协作**：通过 API / command / event 与稳定身份交互，写清数据 owner、同步语义、失败语义和陈旧容忍度。
6. **演进检查**：验证基数、唯一约束、拆分 / 合并上下文和迁移时，身份与契约是否仍成立。

## 跨上下文协作规则

1. **所有权明确**：每个事实只有一个权威 owner；其他上下文若保存副本，必须标明是 projection / cache / snapshot。
2. **身份稳定**：跨边界传对方公开的稳定 ID，不把内部表主键或完整可变实体当共享模型。
3. **协作显式**：通过 API、事件或消息契约；不跨上下文 join、直写对方表或共享 ORM entity。
4. **复制有语义**：确需冗余数据时写清同步源、最大陈旧度、冲突处理与修复路径。
5. **语言有映射**：同名 / 相近字段在上下文间语义不同时，用 anti-corruption mapping 或引用方向表说明。

引用方向表：

| 字段 / 消息 | 来源上下文 | 消费上下文 | owner | 传递方式 | 一致性 / 陈旧语义 |
|---|---|---|---|---|---|
| `projectId` | 项目 | Agent | 项目 | API 参数 | 强校验身份，不复制项目详情 |
| `ProjectRenamed` | 项目 | 搜索 | 项目 | event | 搜索 projection 最终一致 |

## 聚合设计提醒

- 聚合边界由不变量与事务需要决定，不由 ER 图外键数量决定。
- 一个 BC 可以没有复杂聚合，也可以有多个聚合；**每个聚合**有一个聚合根，不是“每个上下文有且仅有一个根”。
- 聚合内部关系可使用内部身份或对象引用；跨聚合 / 跨上下文引用稳定身份。
- 大聚合导致锁竞争、事务过宽或高冲突时，重新检查哪些不变量真的需要同步保证。
- repository 通常面向聚合根，但 repository / service / deployment 的存在不等于 BC 的存在。

## 检查清单

- [ ] BC 由业务能力、统一语言和模型所有权解释，未机械按仓 / 服务 / 部署单元划分
- [ ] 每个聚合的不变量、事务边界与聚合根明确；一个 BC 中的多个聚合已分别标出
- [ ] 无外部绕过聚合根修改内部对象
- [ ] 跨上下文无共享可变实体、跨库 join 或直写对方存储
- [ ] 数据副本有 owner、同步、陈旧度和修复语义
- [ ] 同名概念的跨上下文映射已说明
- [ ] 基数、唯一约束与未来演进已检查

## 示例骨架

```text
项目限界上下文（业务能力：项目生命周期与权限）
  Project 聚合
    Root: Project
    invariant: 归档项目不可新增成员
  AccessGrant 聚合
    Root: AccessGrant
    invariant: 同一 subject + project 只有一个有效授权

Agent 限界上下文（业务能力：Agent 配置与运行）
  Agent 聚合
    Root: Agent
    projectId: 项目上下文稳定 ID

项目 ── ProjectArchived event ──→ Agent
  owner: 项目
  Agent 动作: 禁用关联 Agent
  consistency: 最终一致
  repair: 消费失败进入重试与对账
```
