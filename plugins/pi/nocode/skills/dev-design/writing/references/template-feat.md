# feat 模板（DDD 全流程，最完整）

> dev-design writing 阶段的场景模板。主 SKILL.md Step 1 按场景路由到本文件；覆盖 Step 2 结构骨架的产出标准 + Step 4 的 detail 子步（4a/4b）。新功能 / 产品设计场景使用。

按 DDD 组织：总图（域关系）→ 边（交互场景 / 表现层）→ 节点（域设计 / 领域层）→ 汇总。

**设计思路**：用 DDD 拆分业务域，域间关系图就是产品设计全貌。边（域间关系）= 交互场景（表现层），节点（域）= 领域设计。先画总图让 reviewer 30 秒看清全局，再逐个展开边和节点。每个域自包含——接口、业务流、文件影响、验证都在域章节内，读一个域不用跳来跳去。

> 产出骨架示例见 `references/example-feat-skeleton.md`。横切章必须 Read `references/cross-cutting-design.md`。

## 章节大纲示例（喂 Step 2）

```
1. 罗盘（Define Restate——已确认 restate 原样承载，writing 不改写）
2. 背景
3. 调研（代码现状 + 竞品分析 + 已有决策）
4. 方案选择（决策速查表 + 逐 Q 反方配平）
5. 领域划分 + 总图（资源域 + Agent 域；节点标 新建/改造/已有·复用）
6. 架构设计（技术架构图 + 数据流）
7. 横切设计（关注点×层矩阵 + provider/consumer 走查；产出标准见 `references/cross-cutting-design.md`）
8. 表现层设计（端到端业务流总图 + 各场景）
9. 领域层设计（各域展开）
10. 文件影响汇总
11. 验证策略汇总
12. 可观测设计（基础日志必写 + 生产监控按需）

```

## 结构骨架（喂 Step 2 → Step 3 架构审核）

feat 的结构骨架 = **领域划分 + 总图**：

1. **划分业务边界**——从业务能力、统一语言和一致性边界识别候选域；实体与名词用于验证模型，不是机械分域规则。**讲清为什么这么拆**：边界内变化高内聚，跨边界通过显式契约协作。
2. **画总图**（先图后文）：
   - **多域** → 域间关系图：节点 = 域 + 核心实体，边 = 交互场景（用户流程）
   - **单域** → 域内模块关系图：节点 = 模块，边 = 调用 / 依赖
   - **节点标状态**：每个节点标 **新建 / 改造 / 已有·复用**；被复用但不改动的已有域（如全站 IAM）也要画进图（建议虚线框），"复用谁"在图上必须可见
3. **总图 = 产品设计全貌**。每条边是表现层（用户看到的流程），每条边应对应 PRD 一条使用路径。
4. **跨限界上下文时**：总图节点标注上下文归属和各聚合的一致性边界；仓 / 服务 / 部署单元只是识别信号，不等同限界上下文。跨上下文的边遵守「稳定 ID + API / 事件协作，不共享可变实体」（见 `references/ddd-modeling.md`）。

```
多域总图示例（节点=域，边=用户流程）：
┌──────────┐   导入流程    ┌──────────┐
│  资源域   │ ───────────→ │ Agent 域  │
│ Resource │ ←─────────── │  Agent   │
└────┬─────┘   同步状态     └──────────┘
     │ 预设管理
     ↓
┌──────────┐
│  预设域   │
│  Preset  │
└──────────┘
```

产出标准：域划分完成（每域标核心实体 + 拆分理由 + 新建/改造/已有·复用状态）+ 总图（先图后文，节点标状态）+ 每条边对应 PRD 使用路径；跨限界上下文时另加上下文归属 + 聚合根标注。→ 交 Step 2 确认、Step 3 架构审核。

## Step 4a: 交互场景设计（边 / 表现层）

**Enter Gate:**
- [ ] 架构审核通过，边已识别

**Core Actions:**
逐条边展开。来自 pd-ix 的交互设计 → 细化为前端组件 + 消费的域接口；无 pd-ix 时从使用路径推导。

每个场景章节自包含：
- **流程图**（先图后文；按调用链形态选媒介，格式单源 `references/writing-principles.md` §4）：
  - 跨 ≥2 服务 / 部署单元（含前后端 + 后端多跳、API 调用链）→ **调用时序图**
  - 单参与者串行步骤 → 普通流程图（节点 + ↓）
  - 豁免只有一条：场景单步且无分支 → 可纯文字，但必须 inline 声明「单步无分支不画图」。**不许默默省掉**——评审按缺失打回
- **前端组件设计**（组件拆分 / 状态 / 关键交互）
- **消费哪些域的哪些接口**（连接表现层和领域层）
- **文件影响**（前端文件）
- **验证方案**（组件测试 / E2E）
- **安全 / 性能**（如涉及，如 SSRF 校验 / 大文件 streaming）

> 纯后端无 UI 时，「交互场景」变为「系统交互场景」（API 调用链 / 事件流 / 定时任务触发），结构同——这类场景的调用链通常跨服务，默认调用时序图。

**Exit Gate:**
- [ ] 每条边展开完毕，每个场景有流程图（跨服务场景 = 调用时序图；纯文字场景必有「单步无分支」inline 声明）
- [ ] 每个场景标注消费的域接口
- [ ] 每个场景有文件影响 + 验证方案

## Step 4b: 域设计（节点 / 领域层）

**Enter Gate:**
- [ ] 交互场景已定（各域的接口需求已明确）

**Core Actions:**
逐个域展开。每个域自包含，内部拆到模块：

1. **域内模块关系图**（总览，先图后文）
   - **战术建模触发时**（≥2 候选限界上下文或有持久化模型）：标出每个聚合的**聚合根 / 一致性边界 / 内部实体 / 域服务**；一个上下文可有多个聚合。跨上下文引用字段列**引用方向表**（引用字段 | 方向 | 被引用上下文 | 传递方式），逐条过 `references/ddd-modeling.md`
2. **每个模块**：
   - 类接口（public 方法签名 + 关键字段）
   - 状态机（实体有状态转换时）
   - 业务流（BF 编号，`function`/`method` 签名 + 函数体 + 每行 `//` 注释，主路径 + 异常路径）
3. **域级接口设计**（四层按需，不只 HTTP）：
   - **对外 API**：HTTP / RPC / GraphQL 端点表（Method / Path / Request / Response / 错误码）
   - **类接口**：模块间 public 方法签名（多类协作画类图）
   - **事件接口**：Event / MQ / WebSocket / SSE
   - **数据契约**：DB schema（多表外键画 ER 图；战术建模触发时标每个聚合的一致性边界，外部引用只指向聚合根的稳定身份）/ 配置格式 / 文件格式
4. **域文件影响**（该域改哪些文件，ASCII 树 + (改)/(NEW)）
5. **域验证方案**（单测 / 集成）
6. **域安全 / 性能考量**（如涉及）

**Exit Gate:**
- [ ] 每域展开完毕，每域有模块关系图
- [ ] 每域接口按四层覆盖（涉及的都展开）
- [ ] 每域有业务流（BF 伪代码）+ 文件影响 + 验证方案
- [ ] 战术建模触发时：聚合根 / 实体 / 域服务已标注，跨上下文引用方向表已列且逐条过四规则
